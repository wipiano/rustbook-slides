Chapter 18 · 18.3 Implementing an Object-Oriented Design Pattern

Each state is responsible for its own rules

We need to set state to None temporarily, rather than writing code like self.state = self.state.request_review();, to get ownership of the state value. This ensures Post can’t use the old state value after we’ve transformed it into a new state.

request_review on Draft returns a new, boxed instance of a new PendingReview struct, the state of a post waiting for a review. PendingReview also implements request_review but doesn’t transform anything: it returns itself, because requesting a review on a post already in PendingReview should keep it there.

Now the advantages of the state pattern start to show: request_review on Post is the same no matter its state value. Each state is responsible for its own rules.

We leave content on Post as is, returning an empty string slice: a Post can now be in PendingReview as well as Draft, and we want the same behavior in both. Listing 18.11 now works up to the second assert_eq! call!
