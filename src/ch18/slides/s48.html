Chapter 18 · 18.3 Implementing an Object-Oriented Design Pattern

Downsides: coupled states and duplicated logic

Coupling. Because the states implement the transitions between states, some states are coupled to each other. Adding a state such as Scheduled between PendingReview and Published would mean changing the code in PendingReview to transition to Scheduled instead. It would be less work if PendingReview didn’t need to change, but that would mean switching to another design pattern.

Duplicated defaults. We might try default implementations of request_review and approve on the State trait that return self. This wouldn’t work: when State is used as a trait object, the trait doesn’t know what the concrete self will be, so the return type isn’t known at compile time. (This is one of the dyn compatibility rules.)

Duplicated delegation. request_review and approve on Post both use Option::take on state and, if it is Some, delegate to the wrapped value’s same-named method and store the result. With many such methods, we might define a macro to remove the repetition (see “Macros” in Chapter 20).
