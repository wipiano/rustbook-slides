Chapter 20 · 20.5 Macros

A separate crate for the procedural macro

The next step is to define the procedural macro. At the time of this writing, procedural macros need to be in their own crate; eventually, this restriction might be lifted. The convention: for a crate named foo, a custom derive procedural macro crate is called foo_derive. Start a new crate called hello_macro_derive inside the hello_macro project:

$ cargo new hello_macro_derive --lib

  • The two crates are tightly related, so the procedural macro crate lives within the directory of hello_macro. If we change the trait definition in hello_macro, we’ll have to change the procedural macro in hello_macro_derive as well.
  • The two crates will need to be published separately, and programmers using them will need to add both as dependencies and bring both into scope.
  • Alternatively, hello_macro could use hello_macro_derive as a dependency and re-export the procedural macro code. But this structure lets programmers use hello_macro even if they don’t want the derive functionality.
