Chapter 21 · 21.3 Graceful Shutdown and Cleanup

Reading the shutdown output

You might see a different ordering of Worker IDs and messages. From the messages: Worker instances 0 and 3 got the first two requests. The server stopped accepting connections after the second connection, and the Drop implementation on ThreadPool starts executing before Worker 3 even starts its job. Dropping the sender disconnects all the Worker instances and tells them to shut down. Each prints a message when it disconnects, and then the thread pool calls join to wait for each Worker thread to finish.

One interesting aspect of this particular execution: the ThreadPool dropped the sender, and before any Worker received an error, we tried to join Worker 0. Worker 0 had not yet gotten an error from recv, so the main thread blocked, waiting for it to finish. Meanwhile, Worker 3 received a job, and then all threads received an error. When Worker 0 finished, the main thread waited for the rest; by then they had all exited their loops and stopped.

Congrats! The project is complete: a basic web server that uses a thread pool to respond asynchronously, with a graceful shutdown that cleans up all the threads in the pool.
