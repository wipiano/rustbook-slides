Chapter 21 · 21.2 From a Single-Threaded to a Multithreaded Server

What changed in Listing 21.15

  • The field on ThreadPool is renamed from threads to workers, because it now holds Worker instances instead of JoinHandle<()> instances.
  • The counter in the for loop is the argument to Worker::new, and each new Worker is stored in the vector named workers.
  • External code (like our server in src/main.rs) doesn’t need to know that ThreadPool uses a Worker struct, so Worker and its new function are private.
  • Worker::new uses the id we give it and stores a JoinHandle<()> created by spawning a new thread with an empty closure.

Remark. If the operating system can’t create a thread because there aren’t enough system resources, thread::spawn will panic. That causes our whole server to panic, even though the creation of some threads might succeed. For simplicity this is fine, but a production thread pool would likely use std::thread::Builder and its spawn method, which returns Result instead.

This compiles and stores the number of Worker instances we passed to ThreadPool::new. But we’re still not processing the closure we get in execute.
