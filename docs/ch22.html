Appendix A has three parts:

  • Keywords currently in use — each listed with its functionality (Table A.1, four slides).
  • Keywords reserved for future use — no functionality yet (Table A.2).
  • Raw identifiers — the r# syntax that lets you use a keyword as an identifier.

Appendix · A Keywords

Raw identifiers: the problem

Definition A.2 (Raw identifier). The syntax that lets you use keywords where they wouldn’t normally be allowed: you prefix a keyword with r#.

For example, match is a keyword. Try to compile a function that uses match as its name:

src/main.rs

fn match(needle: &str, haystack: &str) -> bool {

    haystack.contains(needle)

}

You’ll get this error:

error: expected identifier, found keyword `match`

 --> src/main.rs:4:4

  |

4 | fn match(needle: &str, haystack: &str) -> bool {

  |    ^^^^^ expected identifier, found keyword

The error shows that you can’t use the keyword match as the function identifier. To use match as a function name, you need the raw identifier syntax.

Appendix · A Keywords

Raw identifiers: the fix, and why they exist

src/main.rs

fn r#match(needle: &str, haystack: &str) -> bool {

    haystack.contains(needle)

}

 

fn main() {

    assert!(r#match("foo", "foobar"));

}

This code compiles without any errors. Note the r# prefix on the function name both in its definition and where the function is called in main.

Raw identifiers let you use any word you choose as an identifier, even a reserved keyword. That gives more freedom in naming and lets Rust integrate with programs written in a language where these words aren’t keywords.

Example A.3. Raw identifiers also let you use libraries written in a different Rust edition than your crate. try isn’t a keyword in the 2015 edition but is in the 2018, 2021, and 2024 editions. If you depend on a 2015-edition library that has a try function, you call it as r#try from your code on later editions. (Editions: Appendix E.)

Appendix · C Derivable Traits

The derive attribute

Definition A.6 (derive attribute). An attribute you apply to a struct or enum definition; it generates code that implements a trait, with its own default implementation, on the type you’ve annotated with the derive syntax.

This appendix is a reference of all the traits in the standard library that you can use with derive. Each section covers:

  • What operators and methods deriving this trait will enable
  • What the implementation of the trait provided by derive does
  • What implementing the trait signifies about the type
  • The conditions in which you’re allowed or not allowed to implement the trait
  • Examples of operations that require the trait

If you want different behavior from that provided by derive, consult the standard library documentation for each trait for details on how to implement it manually.

Appendix · C Derivable Traits

Which traits can be derived — and which cannot

The traits listed here are the only ones defined by the standard library that can be implemented on your types using derive. Other standard library traits don’t have sensible default behavior, so it’s up to you to implement them in the way that makes sense for what you’re trying to accomplish.

Example A.7. Display, which handles formatting for end users, can’t be derived. You should always consider the appropriate way to display a type to an end user. What parts of the type should an end user be allowed to see? What parts would they find relevant? What format of the data would be most relevant to them? The Rust compiler doesn’t have this insight, so it can’t provide appropriate default behavior for you.

The list of derivable traits in this appendix is not comprehensive: libraries can implement derive for their own traits, making the list of traits you can use derive with truly open ended.

Remark. Implementing derive involves using a procedural macro, covered in the “Custom derive Macros” section in Chapter 20.

Appendix · C Derivable Traits

Debug for programmer output

The Debug trait enables debug formatting in format strings, which you indicate by adding :? within {} placeholders.

Debug lets you print instances of a type for debugging purposes, so you and other programmers using your type can inspect an instance at a particular point in a program’s execution.

Required by: for example, the assert_eq! macro. It prints the values of the instances given as arguments if the equality assertion fails, so programmers can see why the two instances weren’t equal.

Example A.8. Deriving Debug and PartialEq (next slide) makes a struct printable and usable in assert_eq!.

#[derive(Debug, PartialEq)]

struct Point { x: i32, y: i32 }

let p = Point { x: 1, y: 2 };

println!("{p:?}");                // Point { x: 1, y: 2 }

assert_eq!(p, Point { x: 1, y: 2 });

Appendix · C Derivable Traits

PartialEq and Eq for equality comparisons

PartialEq

Lets you compare instances of a type for equality and enables the == and != operators. Deriving it implements the eq method.

  • On structs: two instances are equal only if all fields are equal, and not equal if any field is not equal.
  • On enums: each variant is equal to itself and not equal to the other variants.

Required by: for example, assert_eq!, which must compare two instances for equality.

Eq

Has no methods. It signals that for every value of the annotated type, the value is equal to itself. Eq can only be applied to types that also implement PartialEq — but not all such types can implement Eq.

Floating-point types are one example: two instances of the not-a-number (NaN) value are not equal to each other.

Required by: keys in a HashMap<K, V>, so it can tell whether two keys are the same.

Appendix · C Derivable Traits

PartialOrd for ordering comparisons

The PartialOrd trait lets you compare instances of a type for sorting purposes. A type that implements PartialOrd can be used with the <, >, <=, and >= operators. You can only apply PartialOrd to types that also implement PartialEq.

Deriving PartialOrd implements the partial_cmp method, which returns an Option<Ordering> that is None when the values given don’t produce an ordering. An example of a value that doesn’t produce an ordering, even though most values of its type can be compared, is the NaN floating-point value: calling partial_cmp with any floating-point number and NaN returns None.

  • On structs: compares two instances by comparing the value in each field, in the order the fields appear in the struct definition.
  • On enums: variants declared earlier in the enum definition are considered less than the variants listed later.

Required by: for example, the gen_range method from the rand crate, which generates a random value in the range specified by a range expression.

Appendix · C Derivable Traits

Ord for total ordering

The Ord trait lets you know that for any two values of the annotated type, a valid ordering will exist. It implements the cmp method, which returns an Ordering rather than an Option<Ordering>, because a valid ordering is always possible.

You can only apply Ord to types that also implement PartialOrd and Eq (and Eq requires PartialEq). When derived on structs and enums, cmp behaves the same way as the derived partial_cmp does with PartialOrd.

Required by: storing values in a BTreeSet<T>, a data structure that stores data based on the sort order of the values.

Example A.9. A derived ordering on an enum follows declaration order, so the whole chain of traits is derived together:

#[derive(PartialEq, Eq, PartialOrd, Ord)]

enum Size { Small, Medium, Large }

assert!(Size::Small < Size::Large);  // declared earlier => less

Appendix · C Derivable Traits

Clone for duplicating values

The Clone trait lets you explicitly create a deep copy of a value; the duplication process might involve running arbitrary code and copying heap data. (More on Clone: “Variables and Data Interacting with Clone”, Chapter 4.)

Deriving Clone implements the clone method, which, when implemented for the whole type, calls clone on each of the parts of the type. This means all the fields or values in the type must also implement Clone to derive Clone.

Required by: calling the to_vec method on a slice. The slice doesn’t own the type instances it contains, but the vector returned from to_vec needs to own its instances, so to_vec calls clone on each item. Thus, the type stored in the slice must implement Clone.

Appendix · C Derivable Traits

Copy for duplicating values cheaply

The Copy trait lets you duplicate a value by only copying bits stored on the stack; no arbitrary code is necessary. (More on Copy: “Stack-Only Data: Copy”, Chapter 4.)

Copy doesn’t define any methods, to prevent programmers from overloading those methods and violating the assumption that no arbitrary code is being run. That way, all programmers can assume that copying a value will be very fast.

You can derive Copy on any type whose parts all implement Copy. A type that implements Copy must also implement Clone, because a Copy type has a trivial implementation of Clone that performs the same task as Copy.

Rarely required: types that implement Copy have optimizations available, meaning you don’t have to call clone, which makes the code more concise.

Remark. Everything possible with Copy you can also accomplish with Clone, but the code might be slower or have to use clone in places.

Appendix · C Derivable Traits

Hash for mapping a value to a value of fixed size

The Hash trait lets you take an instance of a type of arbitrary size and map that instance to a value of fixed size using a hash function.

Deriving Hash implements the hash method. The derived implementation combines the result of calling hash on each of the parts of the type, meaning all fields or values must also implement Hash to derive Hash.

Required by: storing keys in a HashMap<K, V> to store data efficiently.

Example A.10. A type used as a HashMap key needs Hash plus Eq (and so PartialEq):

#[derive(PartialEq, Eq, Hash)]

struct UserId(u32);

let mut names: HashMap<UserId, String> = HashMap::new();

names.insert(UserId(7), String::from("Ferris"));

Appendix · C Derivable Traits

Default for default values

The Default trait lets you create a default value for a type. Deriving Default implements the default function, whose derived implementation calls default on each part of the type — so all fields or values in the type must also implement Default to derive Default.

Default::default is commonly combined with the struct update syntax (“Creating Instances from Other Instances with Struct Update Syntax”, Chapter 5): customize a few fields of a struct, then set and use a default value for the rest with ..Default::default().

Required by: for example, the method unwrap_or_default on Option<T>. If the Option<T> is None, unwrap_or_default returns the result of Default::default for the type T stored in the Option<T>.

Example A.11. Struct update syntax with derived defaults:

#[derive(Default)]

struct Config { verbose: bool, retries: u32, name: String }

let c = Config { retries: 3, ..Default::default() };  // verbose: false, name: ""

Appendix · D Useful Development Tools

Automatic formatting with rustfmt

This appendix covers useful development tools that the Rust project provides: automatic formatting, quick ways to apply warning fixes, a linter, and integration with IDEs.

The rustfmt tool reformats your code according to the community code style. Many collaborative projects use rustfmt to prevent arguments about which style to use when writing Rust: everyone formats their code using the tool.

Rust installations include rustfmt by default, so you should already have the programs rustfmt and cargo-fmt. They are analogous to rustc and cargo: rustfmt allows finer-grained control, and cargo-fmt understands the conventions of a project that uses Cargo. To format any Cargo project:

$ cargo fmt

This reformats all the Rust code in the current crate. It should only change the code style, not the code semantics. More: the rustfmt documentation (github.com/rust-lang/rustfmt).

Fix your code with rustfix: a warning

The rustfix tool is included with Rust installations and can automatically fix compiler warnings that have a clear way to correct the problem that’s likely what you want. Consider this code:

src/main.rs

fn main() {

    let mut x = 42;

    println!("{x}");

}

We define x as mutable but never actually mutate it. Rust warns us about that (right).

warning: variable does not need to be mutable

Fix your code with rustfix: cargo fix

The warning suggests removing the mut keyword. We can apply that suggestion automatically with the rustfix tool by running cargo fix:

Running cargo fix:

    Checking myprogram v0.1.0 (file:///projects/myprogram)

The variable x is now immutable, and the warning no longer appears. You can also use cargo fix to transition your code between different Rust editions (Appendix E).

More lints with Clippy

Definition A.12 (Clippy). A collection of lints that analyze your code so you can catch common mistakes and improve your Rust code. Clippy is included with standard Rust installations.

To run Clippy’s lints on any Cargo project, enter:

$ cargo clippy

For example, say you write a program that uses an approximation of a mathematical constant, such as pi:

src/main.rs

fn main() {

    let x = 3.1415;

    let r = 8.0;

    println!("the area of the circle is {}", x * r * r);

}

To help with IDE integration, the Rust community recommends using rust-analyzer (rust-analyzer.github.io). This tool is a set of compiler-centric utilities that speak the Language Server Protocol.

Definition A.13 (Language Server Protocol). A specification for IDEs and programming languages to communicate with each other (langserver.org).

Different clients can use rust-analyzer, such as the Rust analyzer plug-in for Visual Studio Code.

  1. Visit the rust-analyzer project’s home page (rust-analyzer.github.io) for installation instructions.
  2. Install the language server support in your particular IDE.

Your IDE then gains capabilities such as autocompletion, jump to definition, and inline errors.

Appendix · E Editions

Why Rust has editions

In Chapter 1, cargo new added a bit of metadata about an edition to your Cargo.toml file. This appendix explains what that means.

The Rust language and compiler have a six-week release cycle, so users get a constant stream of new features. Other programming languages release larger changes less often; Rust releases smaller updates more frequently. After a while, all of these tiny changes add up — but from release to release, it can be difficult to look back and say, “Wow, between Rust 1.10 and Rust 1.31, Rust has changed a lot!”

Definition A.14 (Edition). A package, produced by the Rust team every three years or so, that brings together the features that have landed into a clear package with fully updated documentation and tooling. New editions ship as part of the usual six-week release process.

Appendix · E Editions

Choosing an edition

Editions serve different purposes for different people:

  • For active Rust users, a new edition brings together incremental changes into an easy-to-understand package.
  • For non-users, it signals that some major advancements have landed, which might make Rust worth another look.
  • For those developing Rust, it provides a rallying point for the project as a whole.

At the time of this writing, four Rust editions are available: Rust 2015, Rust 2018, Rust 2021, and Rust 2024. The book is written using Rust 2024 edition idioms.

The edition key in Cargo.toml indicates which edition the compiler should use for your code. If the key doesn’t exist, Rust uses 2015 as the edition value, for backward compatibility reasons.

Each project can opt in to an edition other than the default 2015 edition. Editions can contain incompatible changes, such as a new keyword that conflicts with identifiers in code. However, unless you opt in to those changes, your code will continue to compile even as you upgrade the Rust compiler version you use.

Appendix · E Editions

Editions interoperate

All Rust compiler versions support any edition that existed prior to that compiler’s release, and they can link crates of any supported editions together. Edition changes only affect the way the compiler initially parses code.

Example A.15. If you’re using Rust 2015 and one of your dependencies uses Rust 2018, your project will compile and be able to use that dependency. The opposite situation — your project uses Rust 2018 and a dependency uses Rust 2015 — works as well.

To be clear: most features will be available on all editions, and developers using any Rust edition will continue to see improvements as new stable releases are made. However, in some cases, mainly when new keywords are added, some new features might only be available in later editions. You will need to switch editions if you want to take advantage of such features.

Remark. For more details, see The Rust Edition Guide (doc.rust-lang.org/stable/edition-guide), a complete book that enumerates the differences between editions and explains how to automatically upgrade your code to a new edition via cargo fix.

Appendix · G How Rust is Made and Nightly Rust

Stability without stagnation

This appendix is about how Rust is made and how that affects you as a Rust developer.

As a language, Rust cares a lot about the stability of your code. Rust should be a rock-solid foundation you can build on, and if things were constantly changing, that would be impossible.

At the same time, if the Rust team can’t experiment with new features, they may not find out important flaws until after their release, when things can no longer be changed.

Definition A.16 (Stability without stagnation). Rust’s solution to this tension. Its guiding principle: you should never have to fear upgrading to a new version of stable Rust. Each upgrade should be painless, but should also bring you new features, fewer bugs, and faster compile times.

Appendix · G How Rust is Made and Nightly Rust

Choo, choo! Release channels and riding the trains

Rust development operates on a train schedule: all development is done in the main branch of the Rust repository, and releases follow a software release train model, which has been used by Cisco IOS and other software projects.

Definition A.17 (Release channel). One of the three streams in which Rust is released: Nightly, Beta, and Stable. Most Rust developers primarily use the stable channel, but those who want to try out experimental new features may use nightly or beta.

An example of how development and release work: assume the Rust team is working on the release of Rust 1.5. (That release happened in December 2015, but it gives realistic version numbers.) A new feature is added to Rust: a new commit lands on the main branch. Each night, a new nightly version of Rust is produced. Every day is a release day, and these releases are created automatically by the release infrastructure. So as time passes, the releases look like this, once a night:

nightly: * - - * - - *

The trains: beta branches off, regressions get fixed

1. Every six weeks, it’s time to prepare a new release! The beta branch of the Rust repository branches off from the main branch used by nightly. Now there are two releases:

nightly: * - - * - - *

                     |

beta:                *

2. Most Rust users do not use beta releases actively, but test against beta in their CI system to help Rust discover possible regressions. Meanwhile, there’s still a nightly release every night:

nightly: * - - * - - * - - * - - *

                     |

beta:                *

3. Say a regression is found. Good thing there was time to test the beta release before the regression snuck into a stable release! The fix is applied to the main branch, so nightly is fixed; then the fix is backported to the beta branch, and a new beta release is produced:

nightly: * - - * - - * - - * - - * - - *

                     |

beta:                * - - - - - - - - *

Appendix · G How Rust is Made and Nightly Rust

Why the train model works

Definition A.18 (Train model). The release model in which every six weeks a release “leaves the station”, but still has to take a journey through the beta channel before it arrives as a stable release.

Rust releases every six weeks, like clockwork. If you know the date of one Rust release, you can know the date of the next one: it’s six weeks later. A nice aspect of releases scheduled every six weeks is that the next train is coming soon. If a feature happens to miss a particular release, there’s no need to worry: another one is happening in a short time! This helps reduce pressure to sneak possibly unpolished features in close to the release deadline.

Thanks to this process, you can always check out the next build of Rust and verify for yourself that it’s easy to upgrade to: if a beta release doesn’t work as expected, you can report it to the team and get it fixed before the next stable release happens! Breakage in a beta release is relatively rare, but rustc is still a piece of software, and bugs do exist.

Appendix · G How Rust is Made and Nightly Rust

Maintenance time and unstable features

Maintenance time

The Rust project supports the most recent stable version. When a new stable version is released, the old version reaches its end of life (EOL). This means each version is supported for six weeks.

Unstable features

There’s one more catch with this release model: unstable features. Rust uses a technique called “feature flags” to determine what features are enabled in a given release.

Definition A.19 (Feature flag). A flag behind which a feature under active development lands on the main branch — and therefore in nightly. To try out the work-in-progress feature, you must be using a nightly release of Rust and annotate your source code with the appropriate flag to opt in.

Appendix · G How Rust is Made and Nightly Rust

Unstable features stay on nightly

If you’re using a beta or stable release of Rust, you can’t use any feature flags. This is the key that allows practical use of new features before they are declared stable forever. Those who wish to opt into the bleeding edge can do so, and those who want a rock-solid experience can stick with stable and know that their code won’t break. Stability without stagnation.

Example A.20. Opting in to an unstable feature is a crate-level attribute naming the flag; it compiles only on a nightly toolchain, and beta or stable reject it.

#![feature(never_type)]  // at the top of src/main.rs or src/lib.rs

The book only contains information about stable features, as in-progress features are still changing, and surely they’ll be different between when the book was written and when they get enabled in stable builds. You can find documentation for nightly-only features online.

Rustup and the role of Rust nightly

Rustup makes it easy to change between different release channels of Rust, on a global or per-project basis. By default, you’ll have stable Rust installed. To install nightly, for example:

$ rustup toolchain install nightly

Definition A.21 (Toolchain). A release of Rust together with its associated components, as installed and managed by rustup.

You can see all of the toolchains you have installed with rustup as well. Here’s an example on one of the authors’ Windows computers:

> rustup toolchain list

beta-x86_64-pc-windows-msvc

Appendix · G How Rust is Made and Nightly Rust

Using nightly for one project: rustup override

As the list shows, the stable toolchain is the default. Most Rust users use stable most of the time. You might want to use stable most of the time but use nightly on a specific project, because you care about a cutting-edge feature.

To do so, use rustup override in that project’s directory to set the nightly toolchain as the one rustup should use when you’re in that directory:

$ cd ~/projects/needs-nightly

$ rustup override set nightly

Now, every time you call rustc or cargo inside ~/projects/needs-nightly, rustup makes sure that you are using nightly Rust rather than your default of stable Rust. This comes in handy when you have a lot of Rust projects!

Appendix · G How Rust is Made and Nightly Rust

The RFC process and teams

So how do you learn about these new features? Rust’s development model follows a Request For Comments (RFC) process.

Definition A.22 (RFC). A written proposal for an improvement in Rust. Anyone can write RFCs to improve Rust.

The proposals are reviewed and discussed by the Rust team, which is comprised of many topic subteams. There’s a full list of the teams on Rust’s website (rust-lang.org/governance), including teams for each area of the project: language design, compiler implementation, infrastructure, documentation, and more.

The appropriate team reads the proposal and the comments, writes some comments of their own, and eventually there’s consensus to accept or reject the feature.

Appendix · G How Rust is Made and Nightly Rust

From accepted RFC to stable feature

Once a team reaches consensus to accept a feature, it travels the rest of the way like this:

  1. An issue is opened on the Rust repository, and someone can implement it. The person who implements it very well may not be the person who proposed the feature in the first place!
  2. When the implementation is ready, it lands on the main branch behind a feature gate, as discussed in “Unstable features”.
  3. After some time, once Rust developers who use nightly releases have been able to try out the new feature, team members discuss the feature and how it’s worked out on nightly, and decide whether it should make it into stable Rust.
  4. If the decision is to move forward, the feature gate is removed, and the feature is now considered stable! It rides the trains into a new stable release of Rust.
