Chapter 21 · 21.1 Building a Single-Threaded Web Server

The protocols: HTTP over TCP

We start by getting a single-threaded web server working. The details of the protocols involved are beyond the scope of this book, but a brief overview gives the information we need.

Definition 21.2 (Request-response protocol). A protocol in which a client initiates requests and a server listens to the requests and provides a response to the client. The protocol defines the contents of those requests and responses.

The two main protocols involved in web servers are Hypertext Transfer Protocol (HTTP) and Transmission Control Protocol (TCP). Both are request-response protocols.

  • TCP is the lower-level protocol: it describes the details of how information gets from one server to another, but doesn’t specify what that information is.
  • HTTP builds on top of TCP by defining the contents of the requests and responses. It’s technically possible to use HTTP with other protocols, but in the vast majority of cases HTTP sends its data over TCP.

We’ll work with the raw bytes of TCP and HTTP requests and responses.

TcpListener, the address, and bind

Using TcpListener, we listen for TCP connections at the address 127.0.0.1:7878.

  • The section before the colon is an IP address representing your computer. It is the same on every computer and doesn’t represent the authors’ computer specifically.
  • 7878 is the port, chosen for two reasons: HTTP isn’t normally accepted on this port, so our server is unlikely to conflict with any other web server running on your machine; and 7878 is rust typed on a telephone.

Definition 21.3 (Binding to a port). In networking, connecting to a port to listen to it. Hence the name of the bind function, which works like a new function: it returns a new TcpListener instance.

bind returns a Result<T, E>: binding can fail — for example, if we ran two instances of our program and so had two programs listening to the same port. Because this is a basic server just for learning, we won’t handle these kinds of errors; we use unwrap to stop the program if errors happen.

incoming: streams and connection attempts

The incoming method on TcpListener returns an iterator that gives us a sequence of streams — more specifically, streams of type TcpStream.

Definition 21.4 (Stream). An open connection between the client and the server.

Definition 21.5 (Connection). The full request and response process: a client connects to the server, the server generates a response, and the server closes the connection.

So we will read from the TcpStream to see what the client sent, then write our response to the stream to send data back. The for loop processes each connection in turn and produces a series of streams for us to handle.

For now we unwrap each stream (terminating on errors) and print a message. incoming can give errors because we iterate over connection attempts, not connections; they can fail for many, often OS-specific, reasons. E.g. many OSes limit simultaneous open connections, and attempts beyond the limit error until some are closed.

Looking more closely at an HTTP request

HTTP is a text-based protocol, and a request takes this format:

Method Request-URI HTTP-Version CRLF

headers CRLF

message-body

Definition 21.6 (Request line). The first line of an HTTP request, holding information about what the client is requesting: method, request URI and HTTP version.

The first part of the request line is the method being used, such as GET or POST, which describes how the client is making this request. Our client used a GET request, which means it is asking for information.

Definition 21.7 (URI). The uniform resource identifier the client is requesting — here /. A URI is almost, but not quite, the same as a uniform resource locator (URL). The difference isn’t important for our purposes; the HTTP spec uses the term URI, so we can mentally substitute URL for URI here.

HTTP version, CRLF and headers

The last part of the request line is the HTTP version the client uses; then the request line ends in a CRLF sequence.

Definition 21.8 (CRLF sequence). Carriage return and line feed — terms from the typewriter days — written \r\n, where \r is a carriage return and \n is a line feed. It separates the request line from the rest of the request data. When the CRLF is printed, we see a new line start rather than \r\n.

In the request line we received, GET is the method, / is the request URI, and HTTP/1.1 is the version.

After the request line, the remaining lines starting from Host: onward are headers. GET requests have no body.

Try making a request from a different browser, or asking for a different address such as 127.0.0.1:7878/test, to see how the request data changes.

Improving throughput with a thread pool

Definition 21.11 (Thread pool). A group of spawned threads that are ready and waiting to handle a task. When the program receives a new task, it assigns one of the threads in the pool to it, and that thread processes the task. The remaining threads are available for any other tasks that come in meanwhile. When a thread finishes its task, it returns to the pool of idle threads, ready for a new task.

A thread pool lets you process connections concurrently, increasing the throughput of your server.

We limit the number of threads in the pool to a small number to protect against DoS attacks. If the program created a new thread for each request, someone making 10 million requests could wreak havoc by using up all our server’s resources and grinding the processing of requests to a halt.

So, rather than spawning unlimited threads, a fixed number of threads wait in the pool. Incoming requests are sent to the pool, which maintains a queue of them. Each thread pops a request off this queue, handles it, then asks the queue for another. We can process up to N requests concurrently, where N is the number of threads. If every thread is responding to a long-running request, later requests can still back up in the queue — but we’ve increased how many long-running requests we can handle before reaching that point.

First we call lock on the receiver to acquire the mutex, then unwrap to panic on any errors.

Definition 21.13 (Poisoned mutex). The state a mutex is left in when some other thread panicked while holding the lock rather than releasing it. Acquiring a lock on a poisoned mutex fails.

  • On a poisoned mutex, calling unwrap to have this thread panic is the correct action. Feel free to change it to an expect with an error message that is meaningful to you.

Why while let holds the lock too long

The reason is somewhat subtle. The Mutex struct has no public unlock method, because ownership of the lock is based on the lifetime of the MutexGuard<T> within the LockResult<MutexGuard<T>> that the lock method returns. At compile time, the borrow checker can then enforce the rule that a resource guarded by a Mutex cannot be accessed unless we hold the lock. But this can also result in the lock being held longer than intended if we aren’t mindful of the lifetime of the MutexGuard<T>.

let (Listing 21.20) — works

With let job = receiver.lock().unwrap().recv().unwrap();, any temporary values used in the expression on the right of the equal sign are dropped immediately when the let statement ends.

while let (Listing 21.21) — doesn’t

while let (and if let and match) does not drop temporary values until the end of the associated block. The lock stays held during the call to job(), so other Worker instances cannot receive jobs.

join needs ownership of the thread

We can’t call join, because we only have a mutable borrow of each worker, and join takes ownership of its argument. We need to move the thread out of the Worker instance that owns thread, so that join can consume it.

One way: Option and take (as in Listing 18.15)

If Worker held an Option<thread::JoinHandle<()>>, we could call take on the Option to move the value out of the Some variant and leave None in its place. A running Worker would have Some in thread; to clean it up, we’d replace Some with None, so the Worker wouldn’t have a thread to run.

However, the only time this would come up is when dropping the Worker. In exchange, we’d have to deal with an Option<thread::JoinHandle<()>> anywhere we accessed worker.thread. Idiomatic Rust uses Option quite a bit, but when you find yourself wrapping something you know will always be present in an Option as a workaround like this, it’s a good idea to look for alternative approaches that make your code cleaner and less error-prone.

            id,

            thread: Some(thread),

        }

    }

}

Chapter summary

Well done! You’ve made it to the end of the book. In this final project you:

  • listened for TCP connections with TcpListener, read HTTP request lines through a BufReader, and wrote raw HTTP responses (status line, Content-Length, body) to the TcpStream;
