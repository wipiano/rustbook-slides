Chapter 19

Patterns and Matching

Patterns are a special syntax in Rust for matching against the structure of types, both complex and simple. Using patterns in conjunction with match expressions and other constructs gives you more control over a program’s control flow.

This chapter is a reference on all things related to patterns: the valid places to use patterns, the difference between refutable and irrefutable patterns, and the different kinds of pattern syntax that you might see. By the end, you’ll know how to use patterns to express many concepts in a clear way.

Chapter 19 · Introduction

What a pattern is

Definition 19.1 (Pattern). A special syntax in Rust for matching against the structure of types, both complex and simple. In the contexts where patterns are valid, they describe the shape of data.

A pattern consists of some combination of:

  • Literals
  • Destructured arrays, enums, structs, or tuples
  • Variables
  • Wildcards
  • Placeholders

Some example patterns: x, (a, 3), and Some(Color::Red). Our program matches values against the patterns to determine whether it has the correct shape of data to continue running a particular piece of code.

To use a pattern, we compare it to some value. If the pattern matches the value, we use the value parts in our code. Recall the match expressions in Chapter 6, such as the coin-sorting machine: if the value fits the shape of the pattern, we can use the named pieces; if it doesn’t, the code associated with the pattern won’t run.

Chapter 19 · 19.1 All the Places Patterns Can Be Used

match arms

Patterns pop up in many places; you’ve used them a lot without realizing it. A match is the keyword match, a value to match on, and one or more arms: a pattern plus an expression to run if the value matches it.

Formally:

match VALUE {

    PATTERN => EXPRESSION,

    PATTERN => EXPRESSION,

    PATTERN => EXPRESSION,

}

From Listing 6.5, matching an Option<i32> in x; the patterns are None and Some(i), left of each arrow:

match x {

    None => None,

    Some(i) => Some(i + 1),

}

match expressions must be exhaustive: all possibilities for the value must be accounted for. One way is a catch-all pattern in the last arm: a variable name matching any value can never fail and so covers every remaining case.

Definition 19.2 (The _ pattern). A pattern that matches anything but never binds to a variable; often used in the last match arm to ignore any value not specified (more in “Ignoring Values in a Pattern”).

Chapter 19 · 19.1 All the Places Patterns Can Be Used

let statements

Before this chapter we had only explicitly discussed patterns with match and if let, but we’ve used patterns elsewhere too — including in let statements.

A straightforward variable assignment:

let x = 5;

More formally, a let statement looks like this:

let PATTERN = EXPRESSION;

Every time you’ve used a let statement like this, you’ve been using patterns, although you might not have realized it!

  • In let x = 5; the variable name in the PATTERN slot is just a particularly simple form of a pattern.
  • Rust compares the expression against the pattern and assigns any names it finds.
  • x is a pattern that means “bind what matches here to the variable x.” Because the name x is the whole pattern, it effectively means “bind everything to the variable x, whatever the value is.”

Destructuring a tuple with let

Listing 19.1: Using a pattern to destructure a tuple and create three variables at once

fn main() {

    let (x, y, z) = (1, 2, 3);

}

Rust compares the value (1, 2, 3) to the pattern (x, y, z) and sees that the value matches — the number of elements is the same in both — so it binds 1 to x, 2 to y, and 3 to z. Think of this tuple pattern as nesting three individual variable patterns inside it.

If the number of elements in the pattern doesn’t match the number in the tuple, the overall type won’t match and we get a compiler error. Listing 19.2 tries to destructure a three-element tuple into two variables:

Listing 19.2: Incorrectly constructing a pattern whose variables don’t match the number of elements in the tuple

fn main() {

    let (x, y) = (1, 2, 3);

}

Fixing the mismatch; conditional if let expressions

To fix the error, we could ignore one or more of the tuple’s values using _ or .. (see “Ignoring Values in a Pattern”). If the problem is too many variables in the pattern, make the types match by removing variables so that the number of variables equals the number of elements in the tuple.

Conditional if let expressions

Chapter 6 used if let mainly as a shorter way to write the equivalent of a match that only matches one case. Optionally, if let can have a corresponding else containing code to run if the pattern doesn’t match.

You can also mix and match if let, else if, and else if let expressions. This gives more flexibility than a match, which can express only one value to compare with the patterns. And Rust doesn’t require the conditions in a series of if let, else if, and else if let arms to relate to each other.

Shadowing and exhaustiveness in if let

if let can shadow variables

if let can introduce new variables that shadow existing ones, in the same way that match arms can. The line if let Ok(age) = age introduces a new age variable containing the value inside the Ok variant, shadowing the existing age.

  • So the if age > 30 condition must go within that block.
  • We can’t combine the two conditions into if let Ok(age) = age && age > 30: the new age we want to compare to 30 isn’t valid until the new scope starts with the curly bracket.

No exhaustiveness check

The downside of if let expressions is that the compiler doesn’t check for exhaustiveness, whereas with match it does. If we omitted the last else block and so missed handling some cases, the compiler would not alert us to the possible logic bug.

while let conditional loops

Listing 19.4: Using a while let loop to print values for as long as rx.recv() returns Ok

fn main() {

    let (tx, rx) = std::sync::mpsc::channel();

    std::thread::spawn(move || {

        for val in [1, 2, 3] {

            tx.send(val).unwrap();

        }

    });

 

    while let Ok(value) = rx.recv() {

        println!("{value}");

    }

}

Similar in construction to if let, the while let loop lets a while loop run for as long as a pattern continues to match. Listing 19.4 waits on messages sent between threads — checking a Result instead of an Option.

It prints 1, 2, and then 3. recv takes the first message out of the receiver side of the channel and returns Ok(value). In Chapter 16 we unwrapped the error directly, or used the receiver as an iterator in a for loop. We can also use while let: recv returns Ok each time a message arrives, as long as the sender exists, and then Err once the sender side disconnects.

Chapter 19 · 19.2 Refutability: Whether a Pattern Might Fail to Match

Refutable and irrefutable patterns

You’ve now seen several ways to use patterns, but patterns don’t work the same in every place we can use them. In some places the patterns must be irrefutable; in others they can be refutable. Patterns come in these two forms:

Definition 19.4 (Irrefutable pattern). A pattern that will match for any possible value passed. Example: x in let x = 5; matches anything and therefore cannot fail to match.

Definition 19.5 (Refutable pattern). A pattern that can fail to match for some possible value. Example: Some(x) in if let Some(x) = a_value — if a_value is None rather than Some, the pattern will not match.

  • Function parameters, let statements, and for loops can only accept irrefutable patterns, because the program cannot do anything meaningful when values don’t match.
  • if let and while let expressions and the let...else statement accept refutable and irrefutable patterns, but the compiler warns against irrefutable ones: by definition they’re intended to handle possible failure — a conditional’s functionality is its ability to perform differently depending on success or failure.

A refutable pattern where let needs an irrefutable one

Listing 19.8: Attempting to use a refutable pattern with let

fn main() {

  • At compile time, Rust complains that we’ve tried to use a refutable pattern where an irrefutable pattern is required (error on the next slide).

The fix: let...else

If we have a refutable pattern where an irrefutable pattern is needed, we can fix it by changing the code that uses the pattern: instead of let, use let...else. Then, if the pattern doesn’t match, the code in the curly brackets handles the value. Listing 19.9 fixes Listing 19.8.

Listing 19.9: Using let...else and a block with refutable patterns instead of let

fn main() {

    let some_option_value: Option<i32> = None;

    let Some(x) = some_option_value else {

        return;

    };

}

Listing 19.10: Attempting to use an irrefutable pattern with let...else

fn main() {

    let x = 5 else {

        return;

    };

}

We’ve given the code an out! Listing 19.9 is perfectly valid, but it means we cannot use an irrefutable pattern without receiving a warning: if we give let...else a pattern that will always match, such as x in Listing 19.10, the compiler warns.

Refutability in match arms

For this reason, match arms must use refutable patterns, except for the last arm, which should match any remaining values with an irrefutable pattern. Rust allows an irrefutable pattern in a match with only one arm, but this syntax isn’t particularly useful and could be replaced with a simpler let statement.

Example 19.6. Left: the first arm’s literal is refutable; the last arm’s _ is irrefutable and catches every remaining value. Right: a one-arm match with an irrefutable pattern does exactly what the let below it does.

match x {

    1 => println!("one"),

    _ => println!("anything"),

}

match (1, 2) {

    (a, b) => println!("{a} {b}"),

}

let (a, b) = (1, 2);

Matching named variables

Listing 19.11: A match expression with an arm that introduces a new variable which shadows an existing variable y — src/main.rs

fn main() {

    let x = Some(5);

    let y = 10;

 

    match x {

        Some(50) => println!("Got 50"),

        Some(y) => println!("Matched, y = {y}"),

        _ => println!("Default case, x = {x:?}"),

    }

 

    println!("at the end: x = {x:?}, y = {y}");

}

Named variables are irrefutable patterns that match any value, and we’ve used them many times. But there is a complication in match, if let, or while let expressions: each starts a new scope, so variables declared as part of a pattern inside them shadow those with the same name outside, as is the case with all variables.

In Listing 19.11, x has the value Some(5) and y the value 10; then we match on x. Look at the patterns in the arms and the println! at the end, and try to figure out what the code will print before reading further.

Chapter 19 · 19.3 Pattern Syntax

Walking through Listing 19.11

  1. The first arm’s pattern, Some(50), doesn’t match the value of x, so the code continues.
  2. The second arm’s pattern introduces a new variable y that matches any value inside a Some. We’re in a new scope inside the match, so this is a new y, not the y declared at the beginning with the value 10. It binds to the inner value of the Some in x, which is 5, so that arm prints Matched, y = 5.
  3. When the match is done, its scope ends, and so does the inner y’s. The last println! produces at the end: x = Some(5), y = 10.

Had x been None, the first two arms wouldn’t match, so the value would match the underscore. That arm’s pattern introduces no x, so the x in its expression is still the outer, unshadowed x, and the match would print Default case, x = None.

Remark. To compare the values of the outer x and y rather than introduce a new variable that shadows y, we need a match guard conditional instead (“Adding Conditionals with Match Guards”, Listing 19.27).

Chapter 19 · 19.3 Pattern Syntax

Multiple patterns with | and ranges with ..=

Matching multiple patterns

In match expressions, | is the pattern or operator. Below, if x matches either value in the first arm, that arm’s code runs:

fn main() {

    let x = 1;

 

    match x {

        1 | 2 => println!("one or two"),

        3 => println!("three"),

        _ => println!("anything"),

    }

}

This code prints one or two.

Matching ranges of values

The ..= syntax matches an inclusive range of values. When a pattern matches any value within the range, that arm executes:

fn main() {

    let x = 5;

 

    match x {

        1..=5 => println!("one through five"),

        _ => println!("something else"),

    }

}

Chapter 19 · 19.3 Pattern Syntax

Range patterns: numbers and char values

In the previous example, if x is 1, 2, 3, 4, or 5, the first arm matches. A range is more convenient than | for the same idea, which would need 1 | 2 | 3 | 4 | 5. Specifying a range is much shorter, especially to match, say, any number between 1 and 1,000!

An example using ranges of char values:

fn main() {

    let x = 'c';

 

    match x {

        'a'..='j' => println!("early ASCII letter"),

        'k'..='z' => println!("late ASCII letter"),

        _ => println!("something else"),

    }

}

The compiler checks that the range isn’t empty at compile time. The only types for which Rust can tell whether a range is empty are char and numeric values, so ranges are only allowed with numeric or char values.

Rust can tell that 'c' is within the first pattern’s range and prints early ASCII letter.

How each variant’s pattern is shaped

  • No data, like Message::Quit: we can’t destructure the value any further. We can only match on the literal Message::Quit value, and no variables are in that pattern.
  • Struct-like, such as Message::Move: a pattern similar to the one for structs. After the variant name, place curly brackets and list the fields with variables, breaking apart the pieces to use in this arm’s code. Here we use the shorthand form, as in Listing 19.13.
  • Tuple-like, like Message::Write (a tuple with one element) and Message::ChangeColor (three elements): a pattern similar to the one for tuples. The number of variables in the pattern must match the number of elements in the variant we’re matching.

Chapter 19 · 19.3 Pattern Syntax

Ignoring values: an entire value with _

It’s sometimes useful to ignore values in a pattern, as in the last arm of a match, to get a catch-all that doesn’t actually do anything but does account for all remaining possible values. There are a few ways to ignore entire values or parts of values: the _ pattern, _ within another pattern, a name that starts with an underscore, or .. to ignore remaining parts of a value.

The underscore is a wildcard pattern that matches any value but doesn’t bind to it. It’s especially useful as the last arm in a match, but we can use it in any pattern, including function parameters:

Listing 19.17: Using _ in a function signature — src/main.rs

fn foo(_: i32, y: i32) {

    println!("This code only uses the y parameter: {y}");

}

 

fn main() {

    foo(3, 4);

}

An unused variable starting with _

If you create a variable but don’t use it anywhere, Rust usually issues a warning, because an unused variable could be a bug. But sometimes it’s useful to create a variable you won’t use yet, such as when you’re prototyping or just starting a project. Then you can tell Rust not to warn you by starting the variable’s name with an underscore. Listing 19.20 creates two unused variables, but compiling it gives a warning about only one of them.

Listing 19.20: Starting a variable name with an underscore to avoid getting unused variable warnings — src/main.rs

fn main() {

    let _x = 5;

    let y = 10;

}

We get a warning about not using the variable y, but no warning about not using _x.

Remark. There is a subtle difference between using only _ and using a name that starts with an underscore. The syntax _x still binds the value to the variable, whereas _ doesn’t bind at all. Listings 19.21 and 19.22 show a case where this distinction matters.

fn main() {

    let s = Some(String::from("Hello!"));

 

    if let Some(_) = s {

        println!("found a string");

    }

 

    println!("{s:?}");

}

The underscore by itself never binds to the value, so this compiles without errors: we never bind s to anything, so it isn’t moved.

Adding conditionals with match guards

Definition 19.7 (Match guard). An additional if condition, specified after the pattern in a match arm, that must also match for that arm to be chosen. Match guards express more complex ideas than a pattern alone allows. They are only available in match expressions, not in if let or while let expressions.

The condition can use variables created in the pattern. In Listing 19.26 the first arm has the pattern Some(x) and the match guard if x % 2 == 0, which is true if the number is even.

Listing 19.26: Adding a match guard to a pattern

fn main() {

    let num = Some(4);

 

    match num {

        Some(x) if x % 2 == 0 => println!("The number {x} is even"),

        Some(x) => println!("The number {x} is odd"),

        None => (),

    }

}

Chapter 19 · 19.3 Pattern Syntax

How the match guard decides

  • Listing 19.26 prints The number 4 is even. num matches the first arm’s pattern, because Some(4) matches Some(x). Then the match guard checks whether the remainder of dividing x by 2 equals 0; it does, so the first arm is selected.
  • Had num been Some(5), the first arm’s guard would be false (5 divided by 2 leaves 1, not 0). Rust would go to the second arm, which matches because it has no match guard and therefore matches any Some variant.

There is no way to express the if x % 2 == 0 condition within a pattern, so the match guard gives us that ability. The downside of this extra expressiveness: the compiler doesn’t try to check for exhaustiveness when match guard expressions are involved.

Testing against an outer variable

Listing 19.27: Using a match guard to test for equality with an outer variable — src/main.rs

fn main() {

    let x = Some(5);

    let y = 10;

 

    match x {

        Some(50) => println!("Got 50"),

        Some(n) if n == y => println!("Matched, n = {n}"),

        _ => println!("Default case, x = {x:?}"),

    }

 

    println!("at the end: x = {x:?}, y = {y}");

}

This code now prints Default case, x = Some(5). The second arm’s pattern doesn’t introduce a new y that would shadow the outer y, so we can use the outer y in the match guard. Instead of Some(y), we specify Some(n): a new variable n that shadows nothing, because there is no n outside the match.

Remark. The match guard if n == y is not a pattern and therefore doesn’t introduce new variables. This y is the outer y rather than a new one shadowing it, so we can look for a value equal to the outer y by comparing n to y.

Match guards with multiple patterns

You can also use the or operator | in a match guard to specify multiple patterns; the match guard condition applies to all the patterns. Listing 19.28 shows the precedence when combining a pattern that uses | with a match guard. The important part: the if y match guard applies to 4, 5, and 6, even though it might look like if y only applies to 6.

Listing 19.28: Combining multiple patterns with a match guard

fn main() {

    let x = 4;

    let y = false;

 

    match x {

        4 | 5 | 6 if y => println!("yes"),

        _ => println!("no"),

    }

}

Chapter 19 · 19.3 Pattern Syntax

Precedence of a match guard over |

The arm in Listing 19.28 matches only if x equals 4, 5, or 6 and y is true. When the code runs, the first arm’s pattern matches because x is 4, but the match guard if y is false, so the first arm is not chosen. The code moves on to the second arm, which does match, and the program prints no. The if condition applies to the whole pattern 4 | 5 | 6, not just to the last value 6.

The precedence behaves like this:

(4 | 5 | 6) if y => ...

rather than this:

4 | 5 | (6 if y) => ...

After running the code, the precedence behavior is evident: if the match guard applied only to the final value in the list specified with the | operator, the arm would have matched and the program would have printed yes.

Chapter 19 · Summary

Chapter summary

Rust’s patterns are very useful in distinguishing between different kinds of data. When used in match expressions, Rust ensures that your patterns cover every possible value, or your program won’t compile. Patterns in let statements and function parameters make those constructs more useful, enabling the destructuring of values into smaller parts and assigning those parts to variables. We can create simple or complex patterns to suit our needs.

  • Places: match arms, let, if let, while let, for, function and closure parameters.
  • Refutability: let, for and parameters need irrefutable patterns; conditionals and let...else take refutable ones.
  • Syntax: literals, named variables, |, ..= ranges, destructuring, _, _name, .., match guards, and @ bindings.
