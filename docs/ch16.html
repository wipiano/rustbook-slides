Chapter 16

Fearless Concurrency

Handling concurrent programming safely and efficiently is another of Rust’s major goals. Historically, programming with threads has been difficult and error-prone; Rust uses its ownership and type systems to turn many concurrency errors into compile-time errors. This chapter covers:

  • 16.1 Using Threads to Run Code Simultaneously — how to create threads to run multiple pieces of code at the same time
  • 16.2 Transfer Data Between Threads with Message Passing — message-passing concurrency, where channels send messages between threads
  • 16.3 Shared-State Concurrency — shared-state concurrency, where multiple threads have access to some piece of data
  • 16.4 Extensible Concurrency with Send and Sync — the traits that extend Rust’s concurrency guarantees to user-defined types as well as types provided by the standard library

Chapter 16 · Introduction

Concurrency, parallelism and “fearless concurrency”

Definition 16.1 (Concurrent programming). Programming in which different parts of a program execute independently.

Definition 16.2 (Parallel programming). Programming in which different parts of a program execute at the same time.

Both are becoming increasingly important as more computers take advantage of their multiple processors. Historically, programming in these contexts has been difficult and error-prone. Rust hopes to change that.

The Rust team first thought memory safety and preventing concurrency problems were two separate challenges needing different methods. Over time they discovered that the ownership and type systems help manage memory safety and concurrency problems. By leveraging ownership and type checking, many concurrency errors are compile-time errors in Rust rather than runtime errors: instead of spending lots of time reproducing the exact circumstances of a runtime concurrency bug, incorrect code refuses to compile and presents an error explaining the problem. You fix your code while working on it, not after it has shipped to production.

Definition 16.3 (Fearless concurrency). The nickname for this aspect of Rust: it lets you write code that is free of subtle bugs and is easy to refactor without introducing new bugs.

Chapter 16 · Introduction

A variety of tools, not one dogma

Remark. For simplicity’s sake, the book refers to many of the problems as concurrent rather than being more precise by saying concurrent and/or parallel. For this chapter, mentally substitute concurrent and/or parallel whenever it says concurrent. In the next chapter, where the distinction matters more, it is more specific.

Many languages are dogmatic about the solutions they offer for handling concurrent problems. For example, Erlang has elegant functionality for message-passing concurrency but has only obscure ways to share state between threads.

  • Supporting only a subset of possible solutions is a reasonable strategy for higher-level languages, because a higher-level language promises benefits from giving up some control to gain abstractions.
  • Lower-level languages, however, are expected to provide the solution with the best performance in any given situation, and have fewer abstractions over the hardware.

Therefore, Rust offers a variety of tools for modeling problems in whatever way is appropriate for your situation and requirements: threads, message passing, shared state, and the Send and Sync traits.

Chapter 16 · 16.1 Using Threads to Run Code Simultaneously

Processes, threads and the problems they bring

Definition 16.4 (Process). In most current operating systems, the unit in which an executed program’s code is run; the OS manages multiple processes at once.

Definition 16.5 (Thread). The feature that runs independent parts of a program simultaneously, within one program.

For example, a web server could have multiple threads so that it can respond to more than one request at the same time. Splitting the computation into multiple threads to run multiple tasks at the same time can improve performance, but it also adds complexity. Because threads can run simultaneously, there’s no inherent guarantee about the order in which parts of your code on different threads will run. This can lead to problems, such as:

  • Race conditions, in which threads are accessing data or resources in an inconsistent order;
  • Deadlocks, in which two threads are waiting for each other, preventing both threads from continuing;
  • Bugs that only happen in certain situations and are hard to reproduce and fix reliably.

The 1:1 threading model, and thread::spawn

Rust attempts to mitigate the negative effects of threads, but multithreaded programming still takes careful thought and a code structure different from that of single-threaded programs.

Languages implement threads in a few different ways; many operating systems provide an API the language can call to create new threads.

Definition 16.6 (1:1 model). The model of thread implementation used by the Rust standard library, whereby a program uses one operating system thread per one language thread.

Crates implement other threading models with different trade-offs. (Rust’s async system, in the next chapter, is another approach to concurrency as well.)

Spawning a thread alongside the main thread

Listing 16.1: Creating a new thread to print one thing while the main thread prints something else — src/main.rs

use std::thread;

use std::time::Duration;

 

fn main() {

    thread::spawn(|| {

        for i in 1..10 {

            println!("hi number {i} from the spawned thread!");

            thread::sleep(Duration::from_millis(1));

        }

    });

 

    for i in 1..5 {

        println!("hi number {i} from the main thread!");

        thread::sleep(Duration::from_millis(1));

    }

}

Running Listing 16.1: no guaranteed order

When the main thread of a Rust program completes, all spawned threads are shut down, whether or not they have finished running. The output might be a little different every time, but it will look similar to this:

hi number 1 from the main thread!

hi number 1 from the spawned thread!

hi number 2 from the main thread!

hi number 2 from the spawned thread!

hi number 3 from the main thread!

hi number 3 from the spawned thread!

hi number 4 from the main thread!

hi number 4 from the spawned thread!

hi number 5 from the spawned thread!

The calls to thread::sleep force a thread to stop its execution for a short duration, allowing a different thread to run. The threads will probably take turns, but that isn’t guaranteed: it depends on how your operating system schedules the threads.

  • In this run, the main thread printed first, even though the spawned thread’s print statement appears first in the code.
  • Although the spawned thread was told to print until i is 9, it only got to 5 before the main thread shut down.

Remark. If you only see output from the main thread, or no overlap, increase the numbers in the ranges to give the OS more opportunities to switch between the threads.

Waiting for all threads to finish: JoinHandle<T>

Listing 16.1 has two problems:

  • most of the time, the spawned thread is stopped prematurely because the main thread ends;
  • because there is no guarantee on the order in which threads run, we can’t even guarantee that the spawned thread will get to run at all!

Both are fixed by saving the return value of thread::spawn in a variable. Its return type is JoinHandle<T>.

Definition 16.7 (JoinHandle<T>). The owned value returned by thread::spawn. Calling the join method on it waits for its thread to finish.

Listing 16.2 (next slides) uses the JoinHandle<T> of the thread created in Listing 16.1 and calls join to make sure the spawned thread finishes before main exits.

Using move closures with threads

We’ll often use the move keyword with closures passed to thread::spawn, because the closure then takes ownership of the values it uses from the environment, thus transferring ownership of those values from one thread to another.

Chapter 13 (“Capturing References or Moving Ownership”) discussed move in the context of closures. Here the focus is on the interaction between move and thread::spawn.

Why borrowing v is rejected

Rust infers a borrow of v (println! only needs a reference), but it can’t tell how long the spawned thread will run, so it doesn’t know if the reference will always be valid. Listing 16.4 makes that more likely:

Listing 16.4: A thread with a closure that attempts to capture a reference to v from a main thread that drops v — src/main.rs

fn main() {

    let v = vec![1, 2, 3];

 

    let handle = thread::spawn(|| {

        println!("Here's a vector: {v:?}");

    });

 

    drop(v); // oh no!

 

    handle.join().unwrap();

}

The danger, and the compiler’s advice

If Rust allowed Listing 16.4 to run, the spawned thread might be immediately put in the background without running at all. The spawned thread has a reference to v inside, but the main thread immediately drops v, using the drop function from Chapter 15. Then, when the spawned thread starts to execute, v is no longer valid, so a reference to it is also invalid. Oh no!

To fix the compiler error in Listing 16.3, use the error message’s advice:

help: to force the closure to take ownership of `v` (and any other referenced variables),

    use the `move` keyword

  |

6 |     let handle = thread::spawn(move || {

  |                                ++++

Adding the move keyword before the closure forces the closure to take ownership of the values it’s using, rather than allowing Rust to infer that it should borrow them. Listing 16.5 (next slide) will compile and run as intended.

Chapter 16 · 16.2 Transfer Data Between Threads with Message Passing

Message passing and channels

One increasingly popular approach to ensuring safe concurrency is message passing, where threads or actors communicate by sending each other messages containing data. The idea, in a slogan from the Go language documentation: “Do not communicate by sharing memory; instead, share memory by communicating.” For message-sending concurrency, Rust’s standard library provides an implementation of channels.

Definition 16.9 (Channel). A general programming concept by which data is sent from one thread to another. A channel has two halves: a transmitter and a receiver. A channel is said to be closed if either the transmitter or receiver half is dropped.

Example 16.10. Imagine a channel as a directional channel of water, such as a stream or a river. Put a rubber duck into the river and it travels downstream to the end of the waterway. The transmitter is the upstream location where you put the duck in; the receiver is where the duck ends up downstream. One part of your code calls methods on the transmitter with the data you want to send; another part checks the receiving end for arriving messages.

mpsc: multiple producer, single consumer

A new channel is created with the mpsc::channel function.

Definition 16.11 (mpsc). Short for multiple producer, single consumer: the way Rust’s standard library implements channels, a channel can have multiple sending ends that produce values but only one receiving end that consumes those values.

Imagine multiple streams flowing together into one big river: everything sent down any of the streams will end up in one river at the end. We start with a single producer, and add multiple producers once this example works.

  • mpsc::channel returns a tuple: the first element is the sending end — the transmitter — and the second is the receiving end — the receiver.
  • The abbreviations tx and rx are traditionally used in many fields for transmitter and receiver, so the variables are named that way.
  • The let statement uses a pattern that destructures the tuple (patterns: Chapter 19) — a convenient way to extract the pieces of the tuple returned by mpsc::channel.

Move the transmitter into a spawned thread and send one string to the main thread — like putting a rubber duck in the river upstream, or sending a chat message to another thread.

Chapter 16 · 16.2 Transfer Data Between Threads with Message Passing

send, recv and try_recv

The transmitter has a send method that takes the value to send. It returns a Result<T, E>: if the receiver has already been dropped and there’s nowhere to send a value, the send operation returns an error. Here we call unwrap to panic in case of an error; a real application would handle it properly (Chapter 9).

The receiver has two useful methods:

recv

Short for receive. Blocks the main thread’s execution and waits until a value is sent down the channel; once one is sent, recv returns it in a Result<T, E>. When the transmitter closes, recv returns an error to signal that no more values will be coming.

try_recv

Doesn’t block: returns a Result<T, E> immediately — Ok holding a message if one is available, Err if there aren’t any this time. Useful if the thread has other work to do while waiting: a loop can call try_recv every so often, handle a message if one is available, and otherwise do other work until checking again.

Chapter 16 · 16.3 Shared-State Concurrency

Communicating by sharing memory

Having seen how channels work, we turn to a different method of concurrency. Message passing is a fine way to handle concurrency, but it’s not the only way. Another method is for multiple threads to access the same shared data. Consider this part of the Go slogan again: “Do not communicate by sharing memory.”

What would communicating by sharing memory look like? And why would message-passing enthusiasts caution not to use memory sharing?

Channels ≈ single ownership

In any programming language, once you transfer a value down a channel, you should no longer use that value.

Shared memory ≈ multiple ownership

Multiple threads can access the same memory location at the same time.

As Chapter 15 showed with smart pointers, multiple ownership can add complexity because these different owners need managing. Rust’s type system and ownership rules greatly assist in getting this management correct. An example: mutexes, one of the more common concurrency primitives for shared memory.

Chapter 16 · 16.3 Shared-State Concurrency

Controlling access with mutexes

Definition 16.12 (Mutex). Abbreviation for mutual exclusion: a mutex allows only one thread to access some data at any given time. To access the data, a thread must first signal that it wants access by asking to acquire the mutex’s lock.

Definition 16.13 (Lock). A data structure that is part of the mutex and keeps track of who currently has exclusive access to the data. The mutex is therefore described as guarding the data it holds via the locking system.

Mutexes have a reputation for being difficult to use because you have to remember two rules:

  1. You must attempt to acquire the lock before using the data.
  2. When you’re done with the data that the mutex guards, you must unlock the data so that other threads can acquire the lock.

Chapter 16 · 16.3 Shared-State Concurrency

A mutex is a panel with one microphone

Example 16.14. Imagine a panel discussion at a conference with only one microphone.

  • Before a panelist can speak, they have to ask or signal that they want to use the microphone.
  • When they get the microphone, they can talk for as long as they want to and then hand the microphone to the next panelist who requests to speak.
  • If a panelist forgets to hand the microphone off when they’re finished with it, no one else is able to speak.
  • If management of the shared microphone goes wrong, the panel won’t work as planned!

Management of mutexes can be incredibly tricky to get right, which is why so many people are enthusiastic about channels. However, thanks to Rust’s type system and ownership rules, you can’t get locking and unlocking wrong.

Chapter 16 · 16.3 Shared-State Concurrency

new, lock, and why you can’t forget to lock

  • As with many types, a Mutex<T> is created with the associated function new.
  • To access the data inside the mutex, use the lock method to acquire the lock. This call blocks the current thread so that it can’t do any work until it’s our turn to have the lock.
  • The call to lock would fail if another thread holding the lock panicked. In that case, no one would ever be able to get the lock, so the code chooses to unwrap and have this thread panic if it is in that situation.
  • After acquiring the lock, the return value, named num here, can be treated as a mutable reference to the data inside.

Remark. The type system ensures that we acquire a lock before using the value in m. The type of m is Mutex<i32>, not i32, so we must call lock to be able to use the i32 value. We can’t forget; the type system won’t let us access the inner i32 otherwise.

MutexGuard releases the lock automatically

The call to lock returns a type called MutexGuard, wrapped in a LockResult that Listing 16.12 handles with the call to unwrap.

Definition 16.15 (MutexGuard). The smart pointer returned by lock. It implements Deref to point at the inner data, and has a Drop implementation that releases the lock automatically when the MutexGuard goes out of scope.

  • In Listing 16.12 the guard goes out of scope at the end of the inner scope, so the lock is released there.
  • As a result, we don’t risk forgetting to release the lock and blocking the mutex from being used by other threads, because the lock release happens automatically.
  • After dropping the lock, we can print the mutex value and see that we were able to change the inner i32 to 6.

Chapter 16 · 16.3 Shared-State Concurrency

Atomic reference counting with Arc<T>

Unfortunately, Rc<T> is not safe to share across threads. It adds to the reference count for each call to clone and subtracts when each clone is dropped, but it doesn’t use any concurrency primitives to make sure that changes to the count can’t be interrupted by another thread. This could lead to wrong counts — subtle bugs that could in turn lead to memory leaks or a value being dropped before we’re done with it. We need a type exactly like Rc<T>, but that changes the reference count in a thread-safe way.

Definition 16.16 (Arc<T>). A type like Rc<T> that is safe to use in concurrent situations. The a stands for atomic: it’s an atomically reference-counted type.

Atomics are an additional kind of concurrency primitive not covered in detail here (see the standard library documentation for std::sync::atomic). For now, just know that atomics work like primitive types but are safe to share across threads.

Chapter 16 · 16.3 Shared-State Concurrency

Mutex<T> and the risk of deadlocks

Rust can’t protect you from all kinds of logic errors when you use Mutex<T>. Recall from Chapter 15 that using Rc<T> came with the risk of creating reference cycles, where two Rc<T> values refer to each other, causing memory leaks. Similarly, Mutex<T> comes with the risk of creating deadlocks.

Definition 16.17 (Deadlock). A situation that occurs when an operation needs to lock two resources and two threads have each acquired one of the locks, causing them to wait for each other forever.

If you’re interested in deadlocks, try creating a Rust program that has a deadlock; then research deadlock mitigation strategies for mutexes in any language and have a go at implementing them in Rust. The standard library API documentation for Mutex<T> and MutexGuard offers useful information.

Chapter 16 · 16.4 Extensible Concurrency with Send and Sync

Concurrency in the language: the marker traits

Interestingly, almost every concurrency feature in this chapter so far has been part of the standard library, not the language. Your options for handling concurrency are not limited to the language or the standard library; you can write your own concurrency features or use those written by others.

However, among the key concurrency concepts embedded in the language rather than the standard library are the std::marker traits Send and Sync.

Transferring ownership between threads

Definition 16.18 (Send). The marker trait indicating that ownership of values of the type implementing Send can be transferred between threads.

Almost every Rust type implements Send, with some exceptions, including Rc<T>: if you cloned an Rc<T> value and tried to transfer ownership of the clone to another thread, both threads might update the reference count at the same time. So Rc<T> is implemented for single-threaded situations where you don’t want to pay the thread-safe performance penalty.

Accessing from multiple threads: Sync

Definition 16.19 (Sync). The marker trait indicating that it is safe for the type implementing Sync to be referenced from multiple threads. In other words, any type T implements Sync if &T (an immutable reference to T) implements Send, meaning the reference can be sent safely to another thread.

Implementing Send and Sync manually is unsafe

  • Types composed entirely of other types that implement Send and Sync automatically implement Send and Sync too, so we don’t have to implement those traits manually.

Chapter 16 · Summary

Chapter summary

  • The Rust standard library provides channels for message passing and smart pointer types, such as Mutex<T> and Arc<T>, that are safe to use in concurrent contexts.
  • The type system and the borrow checker ensure that code using these solutions won’t end up with data races or invalid references. Once your code compiles, you can rest assured that it will happily run on multiple threads without the kinds of hard-to-track-down bugs common in other languages.
  • Because very little of how Rust handles concurrency is part of the language, many concurrency solutions are implemented as crates. These evolve more quickly than the standard library, so search online for the current, state-of-the-art crates to use in multithreaded situations.

Concurrent programming is no longer a concept to be afraid of: go forth and make your programs concurrent, fearlessly!
