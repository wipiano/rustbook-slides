Chapter 11

Writing Automated Tests

In his 1972 essay “The Humble Programmer,” Edsger W. Dijkstra said that “program testing can be a very effective way to show the presence of bugs, but it is hopelessly inadequate for showing their absence.” That doesn’t mean we shouldn’t try to test as much as we can!

Testing is a complex skill: one chapter cannot cover every detail of writing good tests, so this chapter covers the mechanics of Rust’s testing facilities — the annotations and macros available when writing tests, the default behavior and options for running them, and how to organize tests into unit tests and integration tests.

Chapter 11 · Introduction

Correctness, and why the type system is not enough

Definition 11.1 (Correctness). The extent to which our code does what we intend it to do.

Rust is designed with a high degree of concern about the correctness of programs, but correctness is complex and not easy to prove. Rust’s type system shoulders a huge part of this burden, but it cannot catch everything. As such, Rust includes support for writing automated software tests.

Example 11.2. Say we write a function add_two that adds 2 to whatever number is passed to it: it accepts an integer parameter and returns an integer. When we compile it, Rust does all the type checking and borrow checking to ensure, for instance, that we aren’t passing a String value or an invalid reference to it. But Rust can’t check that it does precisely what we intend — return the parameter plus 2 rather than, say, the parameter plus 10 or the parameter minus 50! That’s where tests come in.

We can write tests that assert, for example, that when we pass 3 to add_two, the returned value is 5. We can run these tests whenever we change our code, to make sure any existing correct behavior has not changed.

Chapter 11 · 11.1 How to Write Tests

What a test is

Definition 11.3 (Test). A Rust function that verifies that the non-test code is functioning in the expected manner.

The bodies of test functions typically perform these three actions:

  1. Set up any needed data or state.
  2. Run the code you want to test.
  3. Assert that the results are what you expect.

Rust provides features specifically for writing tests that take these actions:

  • the test attribute;
  • a few macros (assert!, assert_eq!, assert_ne!);
  • the should_panic attribute.

Chapter 11 · 11.1 How to Write Tests

Structuring test functions: the test attribute

Definition 11.4 (Attribute). Metadata about pieces of Rust code — for example the derive attribute used with structs in Chapter 5.

At its simplest, a test is a function annotated with the test attribute: add #[test] on the line before fn. When you run cargo test, Rust builds a test runner binary that runs the annotated functions and reports whether each one passes or fails.

Whenever we make a new library project with Cargo, a test module with a test function in it is generated for us — a template, so you don’t have to look up the exact structure and syntax each time. You can add as many test functions and test modules as you want! We first experiment with the template, then write real tests of our own code. Create a library project adder that will add two numbers:

The generated test module

Listing 11.1: The code generated automatically by cargo new — src/lib.rs

pub fn add(left: u64, right: u64) -> u64 {

    left + right

}

 

#[cfg(test)]

mod tests {

    use super::*;

 

    #[test]

    fn it_works() {

        let result = add(2, 2);

        assert_eq!(result, 4);

    }

}

The file starts with an example add function so that we have something to test.

Focus on it_works. The #[test] annotation tells the test runner to treat this function as a test. The tests module might also hold non-test functions that set up common scenarios or perform common operations, so we always need to indicate which functions are tests.

The body uses the assert_eq! macro to assert that result — the result of calling add with 2 and 2 — equals 4. This assertion is an example of the format of a typical test.

A test that fails: calling panic!

Tests fail when something in the test function panics. Each test is run in a new thread, and when the main thread sees that a test thread has died, the test is marked as failed. The simplest way to panic is to call the panic! macro (Chapter 9). Add a test named another:

Checking results with assert!

The assert! macro, provided by the standard library, ensures that some condition in a test evaluates to true. We give it an argument that evaluates to a Boolean. If the value is true, nothing happens and the test passes. If the value is false, assert! calls panic! to cause the test to fail. It helps us check that our code functions the way we intend.

Testing equality with assert_eq! and assert_ne!

A common way to verify functionality is to test for equality between the result of the code under test and the value you expect it to return. You could pass assert! an expression using the == operator — but this test is so common that the standard library provides a pair of macros to do it more conveniently:

  • assert_eq! compares two arguments for equality;
  • assert_ne! compares two arguments for inequality.

They also print the two values if the assertion fails, which makes it easier to see why the test failed. Conversely, assert! only indicates that it got a false value for the == expression, without printing the values that led to the false value.

In Listing 11.7 (next slide), we write a function named add_two that adds 2 to its parameter, and then test it using assert_eq!.

Chapter 11 · 11.1 How to Write Tests

Left and right, and when to use assert_ne!

Argument order does not matter

In some languages and test frameworks, the parameters to equality assertion functions are called expected and actual, and the order in which we specify the arguments matters. In Rust, they’re called left and right, and the order of the expected value and the value the code produces doesn’t matter. We could write assert_eq!(4, result), which would give the same failure message, assertion `left == right` failed.

assert_ne!

assert_ne! passes if the two values we give it are not equal and fails if they are equal. It is most useful when we’re not sure what a value will be, but we know what it definitely shouldn’t be.

Example 11.5. We test a function that is guaranteed to change its input in some way, but how the input changes depends on the day of the week we run our tests. The best thing to assert might be that the function’s output is not equal to its input.

What assert_eq! and assert_ne! require: PartialEq and Debug

Under the surface, assert_eq! and assert_ne! use the operators == and !=, respectively. When the assertions fail, these macros print their arguments using debug formatting. So the values being compared must implement two traits:

  • PartialEq — to assert equality of the values;
  • Debug — to print the values when the assertion fails.

All primitive types and most of the standard library types implement these traits. For structs and enums that you define yourself, you’ll need to implement both. Because both are derivable traits (Listing 5-12 in Chapter 5), this is usually as straightforward as adding an annotation to your struct or enum definition:

#[derive(PartialEq, Debug)]

See Appendix C, “Derivable Traits,” for more details about these and other derivable traits.

Adding custom failure messages

You can add a custom message to be printed with the failure message as optional arguments to assert!, assert_eq!, and assert_ne!. Any arguments after the required ones are passed along to the format! macro (Chapter 8, “Concatenating with + or format!”), so you can pass a format string with {} placeholders and values to go in them. Custom messages document what an assertion means; when a test fails, you’ll have a better idea of what the problem is.

For example, a function greets people by name, and we test that the name we pass in appears in the output:

src/lib.rs

pub fn greeting(name: &str) -> String {

    format!("Hello {name}!")

}

 

#[cfg(test)]

mod tests {

    use super::*;

 

    #[test]

    fn greeting_contains_name() {

        let result = greeting("Carol");

        assert!(result.contains("Carol"));

    }

}

What cargo test does by default

Now that you know several ways to write tests, let’s look at what happens when we run them and explore the options we can use with cargo test.

Just as cargo run compiles your code and then runs the resultant binary, cargo test compiles your code in test mode and runs the resultant test binary. By default, that binary runs all the tests in parallel and captures output generated during test runs, preventing it from being displayed and making the output related to the test results easier to read. Command line options change this default behavior.

Some options go to cargo test, and some go to the resultant test binary. To separate them, list the arguments for cargo test, then the separator --, then the ones for the test binary. $ cargo test -- --help

Chapter 11 · 11.2 Controlling How Tests Are Run

Running tests in parallel: no shared state

When you run multiple tests, by default they run in parallel using threads, meaning they finish running more quickly and you get feedback sooner.

Because the tests are running at the same time, you must make sure your tests don’t depend on each other or on any shared state, including a shared environment, such as the current working directory or environment variables.

Example 11.8. Each of your tests runs some code that creates a file on disk named test-output.txt and writes some data to it. Then each test reads the data in that file and asserts that the file contains a particular value, which is different in each test. Because the tests run at the same time, one test might overwrite the file between when another test writes and reads it. The second test will then fail — not because the code is incorrect, but because the tests interfered with each other while running in parallel.

One solution is to make sure each test writes to a different file; another solution is to run the tests one at a time.

Running tests consecutively with --test-threads

If you don’t want to run the tests in parallel, or if you want more fine-grained control over the number of threads used, send the --test-threads flag and the number of threads you want to use to the test binary:

$ cargo test -- --test-threads=1

We set the number of test threads to 1, telling the program not to use any parallelism. Running the tests using one thread will take longer than running them in parallel, but the tests won’t interfere with each other if they share state.

Remark. --test-threads comes after the -- separator because it is an option of the test binary, not of cargo test.

To run all tests whether they’re ignored or not, run cargo test -- --include-ignored.

Chapter 11 · 11.3 Test Organization

Two categories: unit tests and integration tests

As mentioned at the start of the chapter, testing is a complex discipline, and different people use different terminology and organization. The Rust community thinks about tests in terms of two main categories:

Definition 11.9 (Unit tests). Small, more focused tests that test one module in isolation at a time, and can test private interfaces.

Definition 11.10 (Integration tests). Tests entirely external to your library that use your code in the same way any other external code would — using only the public interface and potentially exercising multiple modules per test.

Writing both kinds of tests is important to ensure that the pieces of your library are doing what you expect them to, separately and together.

Chapter 11 · 11.3 Test Organization

Unit tests and the #[cfg(test)] tests module

The purpose of unit tests is to test each unit of code in isolation from the rest of the code, to quickly pinpoint where code is and isn’t working as expected. You put unit tests in the src directory, in each file with the code that they’re testing. The convention is to create a module named tests in each file to contain the test functions and to annotate the module with cfg(test).

The #[cfg(test)] annotation on the tests module tells Rust to compile and run the test code only when you run cargo test, not when you run cargo build. This saves compile time when you only want to build the library, and saves space in the resultant compiled artifact because the tests are not included.

  • Integration tests go in a different directory, so they don’t need the #[cfg(test)] annotation.
  • Unit tests go in the same files as the code, so you use #[cfg(test)] to specify that they shouldn’t be included in the compiled result.

What cfg(test) means

Generated by Cargo for adder — src/lib.rs

pub fn add(left: u64, right: u64) -> u64 {

    left + right

}

 

#[cfg(test)]

mod tests {

    use super::*;

    fn it_works() {

        assert_eq!(result, 4);

    }

}

Recall the code Cargo generated for the new adder project in the first section of this chapter (left).

On the generated tests module, the attribute cfg stands for configuration: it tells Rust that the following item should only be included given a certain configuration option. Here the option is test, which Rust provides for compiling and running tests.

So Cargo compiles our test code only if we actively run the tests with cargo test — including any helper functions within this module, in addition to the functions annotated with #[test].

Testing private functions

There’s debate within the testing community about whether private functions should be tested directly, and other languages make it difficult or impossible to test them. Regardless of which testing ideology you adhere to, Rust’s privacy rules do allow you to test private functions — such as internal_adder here.

Chapter 11 · 11.3 Test Organization

Why the private test compiles; integration tests

In Listing 11.12, internal_adder is not marked as pub. Tests are just Rust code, and the tests module is just another module. As discussed in “Paths for Referring to an Item in the Module Tree” (Chapter 7), items in child modules can use the items in their ancestor modules. The test brings all of the items of the tests module’s parent into scope with use super::*, and then it can call internal_adder. If you don’t think private functions should be tested, there’s nothing in Rust that will compel you to do so.

Integration tests

In Rust, integration tests are entirely external to your library. They use your library in the same way any other code would, so they can only call functions that are part of your library’s public API. Their purpose is to test whether many parts of your library work together correctly: units of code that work correctly on their own could have problems when integrated, so test coverage of the integrated code is important as well. To create integration tests, you first need a tests directory.

Chapter 11 · 11.3 Test Organization

Integration tests for binary crates

If our project is a binary crate that only contains a src/main.rs file and doesn’t have a src/lib.rs file, we can’t create integration tests in the tests directory and bring functions defined in src/main.rs into scope with a use statement. Only library crates expose functions that other crates can use; binary crates are meant to be run on their own.

This is one of the reasons Rust projects that provide a binary have a straightforward src/main.rs file that calls logic that lives in the src/lib.rs file.

  • Using that structure, integration tests can test the library crate with use to make the important functionality available.
  • If the important functionality works, the small amount of code in src/main.rs will work as well, and that small amount of code doesn’t need to be tested.

Chapter 11 · Summary

Chapter summary

Rust’s testing features provide a way to specify how code should function, to ensure that it continues to work as you expect, even as you make changes.

  • Unit tests exercise different parts of a library separately and can test private implementation details.
  • Integration tests check that many parts of the library work together correctly, and use the library’s public API to test the code the same way external code will use it.
  • Even though Rust’s type system and ownership rules help prevent some kinds of bugs, tests are still important to reduce logic bugs having to do with how your code is expected to behave.

Toolbox: #[test], assert!, assert_eq!, assert_ne!, custom messages, #[should_panic(expected = …)], Result<T, E> tests, #[ignore], #[cfg(test)], and the tests directory.
