Chapter 20 · 20.1 Unsafe Rust

A second language hidden inside Rust

All the code so far has had Rust’s memory safety guarantees enforced at compile time. However, Rust has a second language hidden inside it that doesn’t enforce these guarantees.

Definition 20.1 (Unsafe Rust). A part of Rust that works just like regular Rust but doesn’t enforce the memory safety guarantees, giving us extra superpowers.

Why it exists

  1. Static analysis is conservative. When the compiler tries to determine whether code upholds the guarantees, it’s better to reject some valid programs than to accept some invalid ones. Code that might be okay is rejected if the compiler lacks the information to be confident. Unsafe code tells the compiler, “Trust me, I know what I’m doing.” You use it at your own risk: used incorrectly, it can cause memory unsafety problems such as null pointer dereferencing.
  2. The hardware is inherently unsafe. Without unsafe operations you couldn’t do certain tasks. Rust needs to allow low-level systems programming — directly interacting with the operating system, or even writing your own operating system — which is one of the goals of the language.

Chapter 20 · 20.1 Unsafe Rust

Performing unsafe superpowers

To switch to unsafe Rust, use the unsafe keyword and then start a new block that holds the unsafe code.

Definition 20.2 (Unsafe superpowers). The five actions you can take in unsafe Rust that you can’t in safe Rust.

  1. Dereference a raw pointer.
  2. Call an unsafe function or method.
  3. Access or modify a mutable static variable.
  4. Implement an unsafe trait.
  5. Access fields of unions.

unsafe doesn’t turn off the borrow checker or disable any of Rust’s other safety checks: if you use a reference in unsafe code, it will still be checked. The keyword only gives you access to these five features, which are then not checked by the compiler for memory safety. You still get some degree of safety inside an unsafe block.

Chapter 20 · 20.1 Unsafe Rust

What unsafe does not mean

unsafe does not mean the code inside the block is necessarily dangerous or that it will definitely have memory safety problems. The intent is that you, the programmer, ensure that the code inside an unsafe block accesses memory in a valid way.

People are fallible and mistakes will happen, but because these five operations must be inside blocks annotated with unsafe, you’ll know that any errors related to memory safety must be within an unsafe block. Keep unsafe blocks small; you’ll be thankful later when you investigate memory bugs.

Safe abstractions

To isolate unsafe code as much as possible, enclose it within a safe abstraction and provide a safe API (shown later with unsafe functions and methods). Parts of the standard library are implemented as safe abstractions over unsafe code that has been audited. Wrapping unsafe code in a safe abstraction prevents uses of unsafe from leaking out into all the places that you or your users might want to use the functionality, because using a safe abstraction is safe.

Next: each of the five superpowers in turn, plus some abstractions that provide a safe interface to unsafe code.

Chapter 20 · 20.1 Unsafe Rust

Superpower 1: dereferencing a raw pointer

Chapter 4 (“Dangling References”) noted that the compiler ensures references are always valid. Unsafe Rust has two new types, similar to references:

Definition 20.3 (Raw pointers). Pointer types written *const T (immutable) and *mut T (mutable). The asterisk isn’t the dereference operator; it’s part of the type name. Here, immutable means the pointer can’t be directly assigned to after being dereferenced.

Different from references and smart pointers, raw pointers:

  • are allowed to ignore the borrowing rules by having both immutable and mutable pointers or multiple mutable pointers to the same location;
  • aren’t guaranteed to point to valid memory;
  • are allowed to be null;
  • don’t implement any automatic cleanup.

By opting out of having Rust enforce these guarantees, you give up guaranteed safety in exchange for greater performance or the ability to interface with another language or hardware where Rust’s guarantees don’t apply.

Creating raw pointers in safe code

Listing 20.1 creates an immutable and a mutable raw pointer.

Listing 20.1: Creating raw pointers with the raw borrow operators

fn main() {

    let mut num = 5;

 

    let r1 = &raw const num;

    let r2 = &raw mut num;

}

  • There is no unsafe keyword here. We can create raw pointers in safe code; we just can’t dereference raw pointers outside an unsafe block, as you’ll see in a bit.
  • The raw borrow operators: &raw const num creates a *const i32 immutable raw pointer, and &raw mut num creates a *mut i32 mutable raw pointer.
  • Because we created them directly from a local variable, we know these particular raw pointers are valid — but we can’t make that assumption about just any raw pointer.

A raw pointer to an arbitrary address

Next, a raw pointer whose validity we can’t be so certain of: instead of a raw borrow operator, we use the keyword as to cast a value. Listing 20.2 creates a raw pointer to an arbitrary location in memory.

Listing 20.2: Creating a raw pointer to an arbitrary memory address

fn main() {

    let address = 0x012345usize;

    let r = address as *const i32;

}

Trying to use arbitrary memory is undefined: there might be data at that address or there might not, the compiler might optimize the code so that there is no memory access, or the program might terminate with a segmentation fault.

Remark. Usually there is no good reason to write code like this, especially where you can use a raw borrow operator instead — but it is possible.

Dereferencing raw pointers in an unsafe block

Listing 20.3: Dereferencing raw pointers within an unsafe block

fn main() {

    let mut num = 5;

 

    let r1 = &raw const num;

    let r2 = &raw mut num;

 

    unsafe {

        println!("r1 is: {}", *r1);

        println!("r2 is: {}", *r2);

    }

}

Reading the data a raw pointer points to needs the dereference operator *, which requires an unsafe block.

Creating a pointer does no harm; only accessing the value it points at might mean dealing with an invalid value.

In Listings 20.1 and 20.3, *const i32 and *mut i32 both point to where num is stored. With an immutable and a mutable reference to num, the code would not compile. With raw pointers we can change data through the mutable pointer, potentially creating a data race. Be careful!

Why use raw pointers at all? One major use case is interfacing with C code (next section). Another is building up safe abstractions that the borrow checker doesn’t understand — shown after unsafe functions are introduced.

Superpower 2: calling an unsafe function or method

Definition 20.4 (Unsafe function). A function or method that looks exactly like a regular one but has an extra unsafe before the rest of the definition. The keyword indicates the function has requirements we need to uphold when we call it, because Rust can’t guarantee we’ve met them.

By calling an unsafe function within an unsafe block, we’re saying that we’ve read this function’s documentation and we take responsibility for upholding the function’s contracts. Here is an unsafe function named dangerous that doesn’t do anything in its body:

unsafe fn dangerous() {}

 

unsafe {

    dangerous();

}

We must call dangerous within a separate unsafe block. Calling it without the unsafe block is an error (next slide).

Creating a safe abstraction over unsafe code

A function that contains unsafe code doesn’t need to be marked unsafe as a whole. In fact, wrapping unsafe code in a safe function is a common abstraction.

Example: split_at_mut from the standard library, which requires some unsafe code. This safe method is defined on mutable slices: it takes one slice and makes it two by splitting the slice at the index given as an argument.

Listing 20.4: Using the safe split_at_mut function

fn main() {

    let mut v = vec![1, 2, 3, 4, 5, 6];

 

    let r = &mut v[..];

 

    let (a, b) = r.split_at_mut(3);

 

    assert_eq!(a, &mut [1, 2, 3]);

    assert_eq!(b, &mut [4, 5, 6]);

}

We can’t implement this function using only safe Rust. An attempt might look like Listing 20.5, which won’t compile. For simplicity, it implements split_at_mut as a function rather than a method, and only for slices of i32 values rather than for a generic type T.

Reaching for unsafe: split_at_mut

The borrow checker can’t understand that we’re borrowing different parts of the slice; it only knows we’re borrowing from the same slice twice. Borrowing non-overlapping parts is fundamentally okay, but Rust isn’t smart enough to know this. Why this is an appropriate use of unsafe

  • slice::from_raw_parts_mut is unsafe because it takes a raw pointer and must trust that this pointer is valid.
  • The add method on raw pointers is also unsafe, because it must trust that the offset location is also a valid pointer.
  • Therefore we had to put an unsafe block around the calls to slice::from_raw_parts_mut and add so that we could call them.

By looking at the code and by adding the assertion that mid must be less than or equal to len, we can tell that all the raw pointers used within the unsafe block will be valid pointers to data within the slice. This is an acceptable and appropriate use of unsafe.

We don’t need to mark the resultant split_at_mut function as unsafe, and we can call it from safe Rust. We’ve created a safe abstraction to the unsafe code: the implementation uses unsafe code in a safe way, because it creates only valid pointers from the data this function has access to.

In contrast: a slice from an arbitrary location

The use of slice::from_raw_parts_mut in Listing 20.7 would likely crash when the slice is used. This code takes an arbitrary memory location and creates a slice 10,000 items long.

Listing 20.7: Creating a slice from an arbitrary memory location

fn main() {

    let values: &[i32] = unsafe { slice::from_raw_parts_mut(r, 10000) };

We don’t own the memory at this arbitrary location, and there is no guarantee that the slice this code creates contains valid i32 values. Attempting to use values as though it’s a valid slice results in undefined behavior.

Using extern functions to call external code

Sometimes Rust code needs to interact with code written in another language. For this, Rust has the keyword extern.

Definition 20.5 (Foreign Function Interface, FFI). A way for a programming language to define functions and enable a different (foreign) programming language to call those functions.

Listing 20.8 sets up an integration with the abs function from the C standard library.

Listing 20.8: Declaring and calling an extern function defined in another language — src/main.rs

unsafe extern "C" {

        println!("Absolute value of -3 according to C: {}", abs(-3));

    }

}

Chapter 20 · 20.1 Unsafe Rust

The ABI, and safe functions in unsafe extern blocks

Functions declared within extern blocks are generally unsafe to call from Rust, so extern blocks must also be marked unsafe: other languages don’t enforce Rust’s rules and guarantees, and Rust can’t check them, so responsibility falls on the programmer.

Within the unsafe extern "C" block, we list the names and signatures of external functions from another language we want to call. The "C" part defines which ABI the external function uses.

Definition 20.6 (Application binary interface, ABI). The definition of how to call a function at the assembly level. The "C" ABI is the most common and follows the C programming language’s ABI. All the ABIs Rust supports are listed in the Rust Reference.

Every item declared within an unsafe extern block is implicitly unsafe. However, some FFI functions are safe to call. For example, abs from C’s standard library has no memory safety considerations, and we know it can be called with any i32.

Marking an FFI function as safe

For a function like abs, the safe keyword says that this specific function is safe to call even though it is in an unsafe extern block. Once we make that change, calling it no longer requires an unsafe block.

Listing 20.9: Explicitly marking a function as safe within an unsafe extern block and calling it safely — src/main.rs

unsafe extern "C" {

    safe fn abs(input: i32) -> i32;

}

 

fn main() {

    println!("Absolute value of -3 according to C: {}", abs(-3));

}

Remark. Marking a function as safe does not inherently make it safe! Instead, it is like a promise you are making to Rust that it is safe. It is still your responsibility to make sure that promise is kept!

Calling Rust functions from other languages

extern can also create an interface that lets other languages call Rust functions. Instead of a whole extern block, add the extern keyword and the ABI just before the fn keyword of the function, plus an #[unsafe(no_mangle)] annotation telling the compiler not to mangle its name.

Definition 20.7 (Mangling). A compiler changing the name we’ve given a function to a different name that contains more information for other parts of the compilation process to consume but is less human readable.

Every compiler mangles names slightly differently, so for a Rust function to be nameable by other languages, we must disable Rust’s name mangling. This is unsafe because there might be name collisions across libraries without the built-in mangling: it is our responsibility to make sure the name we choose is safe to export without mangling.

Here call_from_c becomes accessible from C code, after it’s compiled to a shared library and linked from C. This usage of extern requires unsafe only in the attribute, not on the extern block.

#[unsafe(no_mangle)]

pub extern "C" fn call_from_c() {

    println!("Just called a Rust function from C!");

}

Superpower 3: static variables

Definition 20.8 (Static variable). Rust’s name for a global variable. Rust supports them, but they can be problematic with Rust’s ownership rules: if two threads are accessing the same mutable global variable, it can cause a data race.

Listing 20.10: Defining and using an immutable static variable — src/main.rs

static HELLO_WORLD: &str = "Hello, world!";

 

fn main() {

    println!("value is: {HELLO_WORLD}");

}

  • Static variables are similar to constants (Chapter 3, “Declaring Constants”). Their names are in SCREAMING_SNAKE_CASE by convention.
  • They can only store references with the 'static lifetime, so the compiler can figure out the lifetime and we needn’t annotate it.
  • Accessing an immutable static variable is safe.

Constants versus static variables

A subtle difference between constants and immutable static variables is that values in a static variable have a fixed address in memory: using the value will always access the same data. Constants, on the other hand, are allowed to duplicate their data whenever they’re used. Chapter 20 · 20.1 Unsafe Rust

Rules for mutable static variables

  • As with regular variables, mutability is specified with mut. Any code that reads or writes COUNTER must be within an unsafe block.
  • Listing 20.11 compiles and prints COUNTER: 3 as expected because it’s single threaded. Multiple threads accessing COUNTER would likely result in data races, so it is undefined behavior. Therefore the entire function is marked unsafe, with the safety limitation documented, so callers know what they are and are not allowed to do safely.
  • Whenever we write an unsafe function, it is idiomatic to write a comment starting with SAFETY explaining what the caller needs to do to call it safely; whenever we perform an unsafe operation, a SAFETY comment explains how the safety rules are upheld.
  • A compiler lint denies by default any attempt to create references to a mutable static. Either opt out with #[allow(static_mut_refs)] or access it via a raw pointer from a raw borrow operator — including where a reference is created invisibly, as in this listing’s println!. This makes the safety requirements more obvious.

Globally accessible mutable data makes data races hard to rule out — hence mutable statics are unsafe. Where possible, prefer Chapter 16’s concurrency techniques and thread-safe smart pointers, so the compiler checks cross-thread access.

Superpower 4: implementing an unsafe trait

Definition 20.9 (Unsafe trait). A trait at least one of whose methods has some invariant that the compiler can’t verify. It is declared by adding unsafe before trait, and its implementation must be marked unsafe too.

Listing 20.12: Defining and implementing an unsafe trait

unsafe trait Foo {

    // methods go here

}

 

unsafe impl Foo for i32 {

    // method implementations go here

}

 

fn main() {}

By using unsafe impl, we’re promising that we’ll uphold the invariants that the compiler can’t verify.

Example: the Send and Sync marker traits (Chapter 16). The compiler implements them automatically for types composed entirely of Send and Sync types. To mark a type that contains a non-Send/Sync type, such as raw pointers, as Send or Sync, we must use unsafe: Rust can’t verify the guarantees, so we check them manually.

Superpower 5: union fields — and checking with Miri

Accessing fields of a union

Definition 20.10 (Union). A type similar to a struct, but only one declared field is used in a particular instance at one time.

Unions are primarily used to interface with unions in C code. Accessing union fields is unsafe because Rust can’t guarantee the type of the data currently stored in the union instance (more: the Rust Reference).

Using Miri to check unsafe code

Definition 20.11 (Miri). An official Rust tool for detecting undefined behavior. Whereas the borrow checker is a static tool that works at compile time, Miri is a dynamic tool that works at runtime: it runs your program, or its test suite, and detects when you violate the rules it understands about how Rust should work.

Miri is one of the best ways to check that unsafe code you’ve written actually is safe and correct.

What Miri can and cannot tell you

Why default type parameters; same-named methods

You’ll use default type parameters in two main ways:

  1. To extend a type without breaking existing code: if you add a type parameter to an existing trait, a default allows extending the trait’s functionality without breaking the existing implementation code.
  2. To allow customization in specific cases most users won’t need. The standard library’s Add is an example: usually you add two like types, but Add lets you customize beyond that. With the default, you don’t have to specify the extra parameter most of the time — a bit of implementation boilerplate isn’t needed, making the trait easier to use.

Disambiguating between identically named methods

Nothing in Rust prevents a trait from having a method with the same name as another trait’s method, nor implementing both traits on one type. A type can also have a method of its own with the same name. When calling methods with the same name, you need to tell Rust which one you want. Implementing external traits with the newtype pattern

Chapter 10 (“Implementing a Trait on a Type”) introduced the orphan rule: we may implement a trait on a type only if the trait or the type, or both, are local to our crate. The newtype pattern gets around this restriction.

Definition 20.17 (Newtype pattern). Creating a new type in a tuple struct (Chapter 5) with one field: a thin wrapper around the type for which we want to implement a trait. The wrapper type is local to our crate, so we can implement the trait on it. Newtype is a term that originates from the Haskell programming language.

  • There is no runtime performance penalty for using this pattern: the wrapper type is elided at compile time.
  • Example: we want to implement Display on Vec<T>, which the orphan rule prevents directly because Display and Vec<T> are both defined outside our crate.
  • Instead we make a Wrapper struct that holds an instance of Vec<T>, then implement Display on Wrapper and use the Vec<T> value (Listing 20.24, next slide).

Wrapper is a new type, so it doesn’t have the methods of the value it’s holding. Three options:

Rust needs to know certain details about its types, such as how much space to allocate for a value of a particular type. This leaves one corner of its type system a little confusing at first:

Chapter 20 · 20.3 Advanced Types

str is a dynamically sized type

Consider str, used throughout the book. That’s right: not &str, but str on its own, is a DST. In many cases, such as when storing text entered by a user, we can’t know how long the string is until runtime. So we can’t create a variable of type str, nor take an argument of type str. This code does not work:

fn main() {

    let s1: str = "Hello there!";

    let s2: str = "How's it going?";

}

Rust needs to know how much memory to allocate for any value of a particular type, and all values of a type must use the same amount of memory. If Rust allowed this code, these two str values would need to take up the same amount of space. But they have different lengths: s1 needs 12 bytes of storage and s2 needs 15. This is why it’s not possible to create a variable holding a dynamically sized type.

Putting DSTs behind a pointer

So what do we do? You already know the answer: make the type of s1 and s2 a string slice (&str) rather than str.

  • Recall from Chapter 4 (“String Slices”) that the slice data structure only stores the starting position and the length of the slice.
  • Although &T is a single value that stores the memory address of where the T is located, a string slice is two values: the address of the str and its length.
  • So we can know the size of a string slice value at compile time: it’s twice the length of a usize. We always know the size of a string slice, no matter how long the string it refers to is.
  • In general, this is how dynamically sized types are used in Rust: they have an extra bit of metadata that stores the size of the dynamic information.

Remark. The golden rule of dynamically sized types: we must always put values of dynamically sized types behind a pointer of some kind.

The difference between macros and functions

Definition 20.26 (Metaprogramming). Writing code that writes other code — fundamentally, what macros are.

Appendix C discusses the derive attribute, which generates an implementation of various traits for you; we’ve also used the println! and vec! macros throughout the book. All of these macros expand to produce more code than the code you’ve written manually.

Metaprogramming is useful for reducing the amount of code you have to write and maintain, which is also one of the roles of functions. However, macros have some additional powers that functions don’t have:

  • A function signature must declare the number and type of its parameters. Macros can take a variable number of parameters: println!("hello") with one argument or println!("hello {}", name) with two.
  • Macros are expanded before the compiler interprets the meaning of the code, so a macro can, for example, implement a trait on a given type. A function can’t, because it gets called at runtime and a trait needs to be implemented at compile time.

Reading the macro pattern

Macro pattern syntax differs from the pattern syntax of Chapter 19, because macro patterns are matched against Rust code structure rather than values. The pieces of the pattern ( $( $x:expr ),* ) in Listing 20.35 (full syntax: the Rust Reference):

  • A set of parentheses encompasses the whole pattern.
  • A dollar sign ($) declares a variable in the macro system that will contain the Rust code matching the pattern; it makes clear this is a macro variable, not a regular Rust variable.
  • Next, a set of parentheses captures values that match the pattern within them, for use in the replacement code. Within $() is $x:expr, which matches any Rust expression and gives it the name $x.
  • The comma following $() means a literal comma separator must appear between each instance of the code matching $(). The * means the pattern matches zero or more of whatever precedes it.

A separate crate for the procedural macro

The next step is to define the procedural macro. At the time of this writing, procedural macros need to be in their own crate; eventually, this restriction might be lifted. The convention: for a crate named foo, a custom derive procedural macro crate is called foo_derive. Start a new crate called hello_macro_derive inside the hello_macro project:

$ cargo new hello_macro_derive --lib

  • The two crates are tightly related, so the procedural macro crate lives within the directory of hello_macro. If we change the trait definition in hello_macro, we’ll have to change the procedural macro in hello_macro_derive as well.
  • The two crates will need to be published separately, and programmers using them will need to add both as dependencies and bring both into scope.
  • Alternatively, hello_macro could use hello_macro_derive as a dependency and re-export the procedural macro code. But this structure lets programmers use hello_macro even if they don’t want the derive functionality.

quote! and stringify!

  • The quote! macro lets us define the Rust code that we want to return. The compiler expects something different from the direct result of quote!, so we convert it to a TokenStream by calling into, which consumes this intermediate representation and returns a value of the required TokenStream type.
  • quote! also provides templating: we can enter #name, and quote! replaces it with the value in the variable name. It can even do repetition similar to regular macros (see the quote crate’s docs).
  • The macro generates an implementation of HelloMacro for the annotated type, #name. Its one function, hello_macro, prints Hello, Macro! My name is and then the name of the annotated type.
  • stringify! is built into Rust: it takes a Rust expression, such as 1 + 2, and at compile time turns it into a string literal, such as "1 + 2". Unlike format! or println!, it doesn’t evaluate the expression first. The #name input might be an expression to print literally, so we use stringify!; it also saves an allocation by converting #name to a string literal at compile time.

Attribute-like macros

Attribute-like macros are similar to custom derive macros, but instead of generating code for the derive attribute, they allow you to create new attributes. They’re also more flexible: derive only works for structs and enums; attributes can be applied to other items as well, such as functions.

Example: a web framework’s route attribute on a function, and the signature of its procedural macro definition:

#[route(GET, "/")]

fn index() {

#[proc_macro_attribute]

pub fn route(attr: TokenStream, item: TokenStream) -> TokenStream {

There are two parameters of type TokenStream. The first is for the contents of the attribute: the GET, "/" part. The second is the body of the item the attribute is attached to: here, fn index() {} and the rest of the function’s body. Other than that, attribute-like macros work the same way as custom derive macros: create a crate with the proc-macro crate type and implement a function that generates the code you want!

Function-like macros

Function-like macros define macros that look like function calls. Like macro_rules! macros, they’re more flexible than functions; for example, they can take an unknown number of arguments. But macro_rules! macros can only be defined using the match-like syntax of “Declarative Macros for General Metaprogramming”. Function-like macros take a TokenStream parameter, and their definition manipulates that TokenStream using Rust code, as the other two types of procedural macros do. Example: an sql! macro that might be called like so:

let sql = sql!(SELECT * FROM posts WHERE id=1);

This macro would parse the SQL statement inside it and check that it’s syntactically correct — much more complex processing than a macro_rules! macro can do. It would be defined like this:

#[proc_macro]

pub fn sql(input: TokenStream) -> TokenStream {

This is similar to the custom derive macro’s signature: we receive the tokens inside the parentheses and return the code we wanted to generate.
