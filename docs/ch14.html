Chapter 14

More About Cargo and Crates.io

So far we’ve used only the most basic features of Cargo to build, run, and test our code, but it can do a lot more. This chapter discusses some of its other, more advanced features, to show you how to:

  • customize your build through release profiles (14.1);
  • publish libraries on crates.io (14.2);
  • organize large projects with workspaces (14.3);
  • install binaries from crates.io (14.4);
  • extend Cargo using custom commands (14.5).

Cargo can do even more than this chapter covers; for a full explanation of all its features, see its documentation (doc.rust-lang.org/cargo).

Chapter 14 · 14.1 Customizing Builds with Release Profiles

Release profiles: dev and release

Definition 14.1 (Release profile). One of Rust’s predefined, customizable profiles with different configurations that give a programmer more control over various options for compiling code. Each profile is configured independently of the others.

Cargo has two main profiles:

  • the dev profile, which Cargo uses when you run cargo build — defined with good defaults for development;
  • the release profile, which Cargo uses when you run cargo build --release — with good defaults for release builds.

These profile names might be familiar from the output of your builds:

$ cargo build

    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.00s

$ cargo build --release

    Finished `release` profile [optimized] target(s) in 0.32s

The dev and release shown here are these different profiles used by the compiler.

Chapter 14 · 14.1 Customizing Builds with Release Profiles

Default settings and the opt-level setting

Cargo has default settings for each profile that apply when you haven’t explicitly added any [profile.*] sections to the project’s Cargo.toml. By adding [profile.*] sections for any profile you want to customize, you override any subset of the default settings. For example, these are the defaults for opt-level:

Cargo.toml

[profile.dev]

opt-level = 0

 

[profile.release]

opt-level = 3

Definition 14.2 (opt-level). The profile setting that controls the number of optimizations Rust will apply to your code, in a range of 0 to 3.

  • Applying more optimizations extends compiling time.
  • In development you compile often, so you want fewer optimizations to compile faster, even if the resulting code runs slower: the default opt-level for dev is 0.
  • For release it’s best to spend more time compiling: you compile in release mode once but run the program many times, so release mode trades longer compile time for faster code — the default for release is 3.

Chapter 14 · 14.1 Customizing Builds with Release Profiles

Overriding a default setting

You override a default by adding a different value for it in Cargo.toml. For example, to use optimization level 1 in the development profile, add these two lines to the project’s Cargo.toml:

Cargo.toml

[profile.dev]

opt-level = 1

  • This overrides the default setting of 0.
  • Now cargo build uses the defaults for the dev profile plus our customization to opt-level.
  • Because opt-level is 1, Cargo applies more optimizations than the default, but not as many as in a release build.

Remark. For the full list of configuration options and defaults for each profile, see Cargo’s documentation (doc.rust-lang.org/cargo/reference/profiles.html).

Chapter 14 · 14.2 Publishing a Crate to Crates.io

Sharing code, and documentation comments

We’ve used packages from crates.io as dependencies of our projects, but you can also share your code with other people by publishing your own packages. The crate registry at crates.io distributes the source code of your packages, so it primarily hosts code that is open source.

Rust and Cargo have features that make your published package easier for people to find and use. We look at some of them first, and then at how to publish a package.

Making useful documentation comments

Accurately documenting your packages helps other users know how and when to use them, so it’s worth investing the time to write documentation. Chapter 3 showed ordinary comments with two slashes, //. Rust also has a particular kind of comment for documentation:

Definition 14.3 (Documentation comment). A comment written with three slashes, ///, instead of two, that supports Markdown notation for formatting the text and is placed just before the item it documents. It generates HTML documentation, which displays the documentation comments of public API items for programmers interested in knowing how to use your crate as opposed to how your crate is implemented.

Documenting add_one, and generating the docs

Listing 14.1 shows documentation comments for an add_one function in a crate named my_crate.

Listing 14.1: A documentation comment for a function — src/lib.rs

/// # Examples

We describe what add_one does, start a section with the heading Examples, and then provide code that demonstrates how to use add_one.

cargo doc generates the HTML documentation from this comment: it runs the rustdoc tool distributed with Rust and puts the HTML in the target/doc directory.

For convenience, cargo doc --open builds the HTML for your crate (and for all of its dependencies) and opens it in a web browser. Navigate to add_one to see the rendered text (the book’s Figure 14-1).

Commonly used documentation sections

The # Examples Markdown heading in Listing 14.1 creates a section in the HTML titled “Examples.” Crate authors commonly use these other sections too:

Table 14.1: Common sections of a documentation comment

SectionWhat it describes
PanicsThe scenarios in which the documented function could panic. Callers who don’t want their programs to panic should make sure they don’t call the function in these situations.
ErrorsIf the function returns a Result: the kinds of errors that might occur and the conditions that cause them, so callers can write code to handle different kinds of errors in different ways.
SafetyIf the function is unsafe to call (unsafety: Chapter 20): why it is unsafe, and the invariants the function expects callers to uphold.

Most documentation comments don’t need all of these sections, but this is a good checklist of the aspects of your code users will be interested in knowing about.

Documentation comments as tests

Example code blocks in your documentation comments demonstrate how to use your library — with an additional bonus: running cargo test runs the code examples in your documentation as tests!

Nothing is better than documentation with examples. But nothing is worse than examples that don’t work because the code has changed since the documentation was written. Running cargo test with the documentation of add_one from Listing 14.1 shows a section like this in the test results:

   Doc-tests my_crate

 

running 1 test

test src/lib.rs - add_one (line 5) ... ok

 

test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.27s

Now, if we change either the function or the example so that the assert_eq! in the example panics, and run cargo test again, the doc tests catch that the example and the code are out of sync with each other!

Contained item comments: //!

Definition 14.4 (Contained item comment). A doc comment written //!. It adds documentation to the item that contains the comments rather than to the items following the comments. It is typically used inside the crate root file (src/lib.rs by convention) or inside a module, to document the crate or the module as a whole.

Chapter 14 · 14.2 Publishing a Crate to Crates.io

Exporting a convenient public API

The structure of your public API is a major consideration when publishing a crate. People who use your crate are less familiar with the structure than you are, and might have difficulty finding the pieces they want to use if your crate has a large module hierarchy.

Chapter 7 covered making items public with the pub keyword and bringing items into a scope with use. But the structure that makes sense to you while developing a crate might not be convenient for your users. If you organize your structs in a hierarchy of multiple levels, people who want a type defined deep in it might have trouble finding out that the type exists. They might also be annoyed at having to enter use my_crate::some_module::another_module::UsefulType; rather than use my_crate::UsefulType;.

The good news: if the structure isn’t convenient for others to use from another library, you don’t have to rearrange your internal organization. Instead, you can re-export items with pub use to make a public structure that’s different from your private structure.

Definition 14.5 (Re-exporting). Taking a public item in one location and making it public in another location, as if it were defined in the other location instead.

The author of the code in Listing 14.4 had to figure out that PrimaryColor is in the kinds module and mix is in the utils module.

Chapter 14 · 14.2 Publishing a Crate to Crates.io

When and why to use pub use

  • Where there are many nested modules, re-exporting the types at the top level with pub use can make a significant difference in the experience of people who use the crate.
  • Another common use of pub use is to re-export definitions of a dependency in the current crate, to make that crate’s definitions part of your crate’s public API.

Creating a useful public API structure is more an art than a science, and you can iterate to find the API that works best for your users. Choosing pub use gives you flexibility in how you structure your crate internally, and decouples that internal structure from what you present to your users.

Remark. Look at some of the code of crates you’ve installed to see whether their internal structure differs from their public API.

Chapter 14 · 14.2 Publishing a Crate to Crates.io

Setting up a crates.io account

Before you can publish any crates, you need an account on crates.io and an API token:

  1. Visit the home page at crates.io and log in via a GitHub account. (A GitHub account is currently a requirement, but the site might support other ways of creating an account in the future.)
  2. Once logged in, visit your account settings at crates.io/me/ and retrieve your API key.
  3. Run the cargo login command and paste your API key when prompted:

$ cargo login

abcdefghijklmnopqrstuvwxyz012345

This informs Cargo of your API token and stores it locally in ~/.cargo/credentials.toml.

Remark. This token is a secret: do not share it with anyone else. If you do share it with anyone for any reason, revoke it and generate a new token on crates.io.

Adding metadata: a unique crate name

Say you have a crate you want to publish. Before publishing, you need to add some metadata in the [package] section of the crate’s Cargo.toml file. First, your crate needs a unique name:

  • While working on a crate locally, you can name it whatever you like.
  • Crate names on crates.io, however, are allocated on a first-come, first-served basis: once a name is taken, no one else can publish a crate with that name.
  • Before attempting to publish, search for the name you want to use. If it has been used, find another name and edit the name field under [package] to use the new name for publishing:

Cargo.toml

[package]

name = "guessing_game"

Even with a unique name, running cargo publish at this point gives you a warning and then an error (next slide).

Adding a description and a license

  • description: just a sentence or two, because it appears with your crate in search results.
  • license: you need to give a license identifier value.

Definition 14.6 (License identifier value). A standard identifier naming a license; the Linux Foundation’s Software Package Data Exchange (SPDX, spdx.org/licenses) lists the identifiers you can use.

For example, to specify that you’ve licensed your crate using the MIT License, add the MIT identifier:

Cargo.toml

[package]

name = "guessing_game"

license = "MIT"

To use a license that doesn’t appear in the SPDX, place the text of that license in a file, include the file in your project, and then use license-file to specify the name of that file instead of using the license key.

Chapter 14 · 14.2 Publishing a Crate to Crates.io

Publishing to crates.io is permanent

Now that you’ve created an account, saved your API token, chosen a name for your crate, and specified the required metadata, you’re ready to publish! Publishing a crate uploads a specific version to crates.io for others to use.

Be careful: a publish is permanent

  • The version can never be overwritten, and the code cannot be deleted except in certain circumstances.
  • One major goal of crates.io is to act as a permanent archive of code, so that builds of all projects that depend on crates from crates.io will continue to work. Allowing version deletions would make fulfilling that goal impossible.
  • However, there is no limit to the number of crate versions you can publish.

Chapter 14 · 14.2 Publishing a Crate to Crates.io

New versions, and deprecating old ones

Publishing a new version of an existing crate

When you’ve made changes to your crate and are ready to release a new version, change the version value in your Cargo.toml and republish. Use the Semantic Versioning rules (semver.org) to decide on an appropriate next version number, based on the kinds of changes you’ve made. Then run cargo publish to upload the new version.

Deprecating versions from crates.io

Although you can’t remove previous versions of a crate, you can prevent any future projects from adding them as a new dependency. This is useful when a crate version is broken for one reason or another. For such situations, Cargo supports yanking a crate version.

Definition 14.7 (Yanking). Preventing new projects from depending on a published crate version while allowing all existing projects that depend on it to continue. Essentially, all projects with a Cargo.lock will not break, and any future Cargo.lock files generated will not use the yanked version.

Chapter 14 · 14.2 Publishing a Crate to Crates.io

Yanking and unyanking with cargo yank

To yank a version, run cargo yank in the directory of the crate you previously published, and specify which version to yank. For example, having published guessing_game version 1.0.1, we’d run this in the project directory for guessing_game:

$ cargo yank --vers 1.0.1

    Updating crates.io index

        Yank guessing_game@1.0.1

Adding --undo to the command undoes a yank and allows projects to start depending on that version again:

$ cargo yank --vers 1.0.1 --undo

    Updating crates.io index

      Unyank guessing_game@1.0.1

Remark. A yank does not delete any code. It cannot, for example, delete accidentally uploaded secrets. If that happens, you must reset those secrets immediately.

Workspaces: several packages developed together

In Chapter 12 we built a package that included a binary crate and a library crate. As your project develops, the library crate might keep getting bigger, and you may want to split your package further into multiple library crates. Cargo’s workspaces help manage multiple related packages that are developed in tandem.

Definition 14.8 (Workspace). A set of packages that share the same Cargo.lock and output directory.

Chapter 14 · 14.3 Cargo Workspaces

One shared target directory

  • The workspace has one target directory at the top level, into which the compiled artifacts are placed; the adder package doesn’t have its own target directory.
  • Even if we run cargo build from inside the adder directory, the compiled artifacts still end up in add/target rather than add/adder/target.

Why Cargo structures it this way

The crates in a workspace are meant to depend on each other. If each crate had its own target directory, each crate would have to recompile each of the other crates in the workspace to place the artifacts in its own target directory. By sharing one target directory, the crates avoid unnecessary rebuilding.

Chapter 14 · 14.3 Cargo Workspaces

Depending on an external package

The workspace has only one Cargo.lock file, at the top level, rather than one in each crate’s directory, so all crates use the same version of all dependencies. If we add the rand package to both adder/Cargo.toml and add_one/Cargo.toml, Cargo resolves both to one version of rand and records that in the one Cargo.lock. Using the same dependencies means the crates in the workspace will always be compatible with each other.

Add the rand crate to the [dependencies] section of add_one/Cargo.toml, so that the add_one crate can use it:

add_one/Cargo.toml

[dependencies]

rand = "0.10.1"

Now add use rand; to add_one/src/lib.rs. Running cargo build in the add directory brings in and compiles the rand crate, with one warning because we don’t refer to the rand we brought into scope (next slide).

Chapter 14 · 14.3 Cargo Workspaces

Each crate must declare its own dependencies

The top-level Cargo.lock now records that add_one depends on rand. But other crates in the workspace can’t use rand unless we add it to their Cargo.toml files as well. Adding use rand; to adder/src/main.rs gives an error:

$ cargo build

  --snip--

   Compiling adder v0.1.0 (file:///projects/add/adder)

error[E0432]: unresolved import `rand`

 --> adder/src/main.rs:2:5

  |

2 | use rand;

  |     ^^^^ no external crate `rand`

To fix this, list rand as a dependency in the adder package’s Cargo.toml too. Building adder then adds rand to its dependencies in Cargo.lock, but no additional copies are downloaded: every crate in the workspace using rand uses the same version, as long as they specify compatible versions — saving space and keeping the crates compatible.

Remark. If crates in the workspace specify incompatible versions of the same dependency, Cargo resolves each of them, but still tries to resolve as few versions as possible.

When to use a workspace

  • Keeping the crates in a workspace can make coordination between them easier if they are often changed at the same time.

Chapter 14 · 14.4 Installing Binaries with cargo install

Installing binaries with cargo install

The cargo install command lets you install and use binary crates locally. It isn’t intended to replace system packages; it’s a convenient way for Rust developers to install tools that others have shared on crates.io. You can only install packages that have binary targets.

Definition 14.10 (Binary target). The runnable program created if the crate has a src/main.rs file or another file specified as a binary — as opposed to a library target, which isn’t runnable on its own but is suitable for including within other programs.

Usually, a crate’s README file says whether the crate is a library, has a binary target, or both.

All binaries installed with cargo install are stored in the installation root’s bin folder. If you installed Rust using rustup.rs and have no custom configurations, this directory is $HOME/.cargo/bin. Ensure that this directory is in your $PATH to be able to run programs you’ve installed with cargo install.

Chapter 14 · 14.5 Extending Cargo with Custom Commands

Extending Cargo with custom commands

Cargo is designed so that you can extend it with new subcommands without having to modify it.

Definition 14.11 (Custom Cargo command). A binary in your $PATH named cargo-something, which you can run as if it were a Cargo subcommand by running cargo something.

  • Custom commands like this are also listed when you run cargo --list.
  • Being able to use cargo install to install extensions and then run them just like the built-in Cargo tools is a super-convenient benefit of Cargo’s design!

Chapter 14 · Summary

Chapter summary

Sharing code with Cargo and crates.io is part of what makes the Rust ecosystem useful for many different tasks. Rust’s standard library is small and stable, but crates are easy to share, use, and improve on a timeline different from that of the language. Don’t be shy about sharing code that’s useful to you on crates.io; it’s likely to be useful to someone else as well! In this chapter:

  • release profiles (dev, release) and [profile.*] overrides such as opt-level;
  • /// and //! doc comments, cargo doc, doc tests, and pub use re-exports for a convenient public API;
  • cargo login, required metadata, cargo publish (permanent) and cargo yank;
  • workspaces: one Cargo.lock and target, path dependencies, -p to run, test or publish one crate;
  • cargo install for binary crates, and cargo-something binaries as custom commands.
