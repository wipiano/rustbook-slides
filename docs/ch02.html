Chapter 2

Programming a Guessing Game

Let’s jump into Rust by working through a hands-on project together. This chapter introduces a few common Rust concepts by showing how to use them in a real program: let, match, methods, associated functions, external crates, and more. The following chapters explore these ideas in more detail; here you just practice the fundamentals.

We implement a classic beginner problem, a guessing game. The program generates a random integer between 1 and 100, then prompts the player to enter a guess. After each guess it says whether the guess is too low or too high. If the guess is correct, the game prints a congratulatory message and exits.

Storing values with variables

Next, create a variable to store the user input. There’s a lot going on in this little line:

let mut guess = String::new();

Definition 2.2 (Variable). A name created with the let statement and bound to a value. In Rust, variables are immutable by default: once the variable is given a value, the value won’t change (Chapter 3, “Variables and Mutability”).

Another example: this line creates a new variable named apples and binds it to the value 5.

let apples = 5;

To make a variable mutable, add mut before the variable name:

let apples = 5; // immutable

let mut bananas = 5; // mutable

Remark. The // syntax starts a comment that continues until the end of the line. Rust ignores everything in comments. Chapter 3 discusses comments in more detail.

Binding guess to a new, empty String

let mut guess = String::new();

let mut guess introduces a mutable variable named guess. The equal sign (=) tells Rust we want to bind something to the variable now. On its right is the value guess is bound to: the result of calling String::new, a function that returns a new instance of a String.

String is a string type provided by the standard library that is a growable, UTF-8 encoded bit of text.

Definition 2.3 (Associated function). A function that’s implemented on a type, here String. The :: syntax in the ::new line indicates that new is an associated function of the String type.

This new function creates a new, empty string. You’ll find a new function on many types, because it’s a common name for a function that makes a new value of some kind.

In full, the line has created a mutable variable that is currently bound to a new, empty instance of a String. Whew!

Receiving user input with stdin and read_line

We included the input/output functionality with use std::io; on the first line. Now we call the stdin function from the io module, which lets us handle user input:

io::stdin()

    .read_line(&mut guess)

    .expect("Failed to read line");

Without use std::io; at the beginning of the program, we could still call the function by writing std::io::stdin. The stdin function returns an instance of std::io::Stdin, a type that represents a handle to the standard input for your terminal.

Next, .read_line(&mut guess) calls the read_line method on the standard input handle to get input from the user. The argument &mut guess tells it what string to store the input in: the full job of read_line is to take whatever the user types into standard input and append it to that string (without overwriting its contents). The string argument needs to be mutable so that the method can change the string’s content.

Chapter 2 · 2.2 Processing a Guess

The Result enum and its expect method

read_line puts whatever the user enters into the string we pass to it, but it also returns a Result value.

Definition 2.5 (Enumeration). A type that can be in one of multiple possible states, often called an enum; each possible state is a variant. Result is an enum (enums are covered in Chapter 6).

The purpose of Result types is to encode error-handling information. Result’s variants are:

  • Ok — the operation was successful; it contains the successfully generated value.
  • Err — the operation failed; it contains information about how or why it failed.

Like values of any type, a Result has methods, such as expect. If the Result is an Err value, expect causes the program to crash and displays the message passed to it; an Err from read_line would likely come from the underlying operating system. If it is an Ok value, expect takes the value Ok is holding and returns just that value for you to use — here, the number of bytes in the user’s input.

A secret number from the rand crate

Next we generate a secret number for the user to guess. It should be different every time, so that the game is fun to play more than once, and between 1 and 100, so that the game isn’t too difficult. Rust doesn’t yet include random number functionality in its standard library, but the Rust team provides a rand crate (crates.io/crates/rand) with that functionality.

Increasing functionality with a crate

Remember that a crate is a collection of Rust source code files.

Definition 2.7 (Binary crate). A crate that is an executable, like the project we’ve been building.

Definition 2.8 (Library crate). A crate, like rand, containing code intended to be used in other programs; it can’t be executed on its own.

Coordinating external crates is where Cargo really shines. To use rand, first add it as a dependency: put the line shown next beneath the [dependencies] header in Cargo.toml. Specify rand exactly so, with this version number, or the code examples may not work.

Declaring the dependency with a SemVer version

Cargo.toml

[dependencies]

rand = "0.10.1"

In Cargo.toml, everything after a header is part of that section until another section starts. [dependencies] tells Cargo which external crates your project depends on and which versions you require — here rand, with the semantic version specifier 0.10.1.

Definition 2.9 (Semantic Versioning). A standard for writing version numbers (semver.org), sometimes called SemVer, which Cargo understands.

  • The specifier 0.10.1 is shorthand for ^0.10.1: any version that is at least 0.10.1 but below 0.11.0.
  • Cargo considers these versions to have public APIs compatible with 0.10.1, so you get the latest patch release that will still compile with the code in this chapter.
  • Any version 0.11.0 or greater is not guaranteed to have the same API as the following examples use.

What Cargo did: the registry and dependencies

You may see different version numbers (all compatible with the code, thanks to SemVer!) and different lines (depending on the operating system), and the lines may be in a different order.

Definition 2.10 (Registry). A copy of data from Crates.io, from which Cargo fetches the latest versions of everything an external dependency needs. Crates.io is where people in the Rust ecosystem post their open source Rust projects for others to use.

After updating the registry, Cargo checks the [dependencies] section and downloads any listed crates that aren’t already downloaded. Although we only listed rand, Cargo also grabbed the other crates that rand depends on to work. After downloading the crates, Rust compiles them and then compiles the project with the dependencies available.

If you immediately run cargo build again without making any changes, you get no output aside from the Finished line. Cargo knows it has already downloaded and compiled the dependencies, and you haven’t changed anything about them in Cargo.toml. It also knows you haven’t changed your code, so it doesn’t recompile that either. With nothing to do, it simply exits.

Ensuring reproducible builds

Cargo has a mechanism that ensures you can rebuild the same artifact every time you or anyone else builds your code: it uses only the versions of the dependencies you specified until you indicate otherwise. Say that next week version 0.10.2 of rand comes out with an important bug fix, but also a regression that will break your code. To handle this, Rust creates the Cargo.lock file the first time you run cargo build, so we now have this file in the guessing_game directory.

Cargo.lock and updating a crate

  • On the first build, Cargo figures out all the versions of the dependencies that fit the criteria and writes them to the Cargo.lock file.
  • On later builds, Cargo sees that Cargo.lock exists and uses the versions specified there rather than figuring out versions again. This gives you a reproducible build automatically: the project stays at 0.10.1 until you explicitly upgrade.
  • Because Cargo.lock is important for reproducible builds, it’s often checked into source control with the rest of the code in your project.

Updating a crate to get a new version

When you do want to update a crate, Cargo provides the command update. It ignores the Cargo.lock file, figures out all the latest versions that fit your specifications in Cargo.toml, and writes those versions to Cargo.lock. By default, Cargo only looks for versions greater than 0.10.1 and less than 0.11.0. If the rand crate has released the two new versions 0.10.2 and 0.999.0, running cargo update shows what follows on the next slide.

Chapter 2 · 2.3 Generating a Secret Number

rand::rng and random_range

let secret_number = rand::rng().random_range(1..=100);

  • The rand::rng function gives us the particular random number generator we use: one that is local to the current thread of execution and is seeded by the operating system.
  • Then we call the random_range method on the generator. It is defined by the RngExt trait, part of the rand::prelude module that use rand::prelude::*; brought into scope.
  • random_range takes a range expression as an argument and generates a random number in the range. The form start..=end is inclusive on the lower and upper bounds, so 1..=100 requests a number between 1 and 100.

The cmp method and the match expression

Five new lines at the bottom use the Ordering type. The cmp method compares two values and can be called on anything that can be compared. It takes a reference to whatever you want to compare with: here, it compares guess to secret_number. It returns a variant of the Ordering enum we brought into scope with the use statement.

A match expression decides what to do next based on which variant of Ordering was returned from the call to cmp with the values in guess and secret_number.

Definition 2.11 (Arm). One branch of a match expression. An arm consists of a pattern to match against, and the code that should be run if the value given to match fits that arm’s pattern.

Rust takes the value given to match and looks through each arm’s pattern in turn. Patterns and the match construct are powerful Rust features: they let you express a variety of situations your code might encounter, and they make sure you handle them all. They are covered in detail in Chapter 6 and Chapter 19, respectively.

Walking through a match

Example 2.12. Say the user has guessed 50 and the randomly generated secret number this time is 38.

match guess.cmp(&secret_number) {

    Ordering::Less => println!("Too small!"),

    Ordering::Greater => println!("Too big!"),

    Ordering::Equal => println!("You win!"),

}

  1. Comparing 50 to 38, the cmp method returns Ordering::Greater, because 50 is greater than 38.
  2. The match expression gets the Ordering::Greater value and starts checking each arm’s pattern. The first arm’s pattern, Ordering::Less, does not match Ordering::Greater, so it ignores the code in that arm and moves to the next arm.
  3. The next arm’s pattern, Ordering::Greater, does match! The associated code in that arm executes and prints Too big! to the screen.
  4. The match expression ends after the first successful match, so it won’t look at the last arm in this scenario.

Why the types don’t match

The core of the error states that there are mismatched types. Rust has a strong, static type system. However, it also has type inference.

Definition 2.13 (Type inference). Rust working out a type you didn’t write. From let mut guess = String::new(), Rust inferred that guess should be a String and didn’t make us write the type.

The secret_number, on the other hand, is a number type.

Table 2.1: A few of Rust’s number types that can hold a value between 1 and 100

TypeDescription
i32a 32-bit number
u32an unsigned 32-bit number
i64a 64-bit number

There are others as well. Unless otherwise specified, Rust defaults to an i32, which is the type of secret_number unless you add type information elsewhere that would cause Rust to infer a different numerical type. The reason for the error is that Rust cannot compare a string and a number type.

Shadowing guess and trimming the input

Definition 2.14 (Shadowing). Declaring a new variable with the name of an existing one, so that the new value shadows the previous one. It lets us reuse the guess variable name rather than forcing us to create two unique variables, such as guess_str and guess.

Chapter 3 covers shadowing in more detail; for now, know that it is often used when you want to convert a value from one type to another type.

We bind the new variable to the expression guess.trim().parse(). The guess in the expression refers to the original guess variable that contained the input as a string.

  • The trim method on a String instance eliminates any whitespace at the beginning and end. We must do this before converting the string to a u32, which can only contain numerical data.
  • The user must press enter to satisfy read_line and input their guess, which adds a newline character to the string. Typing 5 and pressing enter makes guess look like 5\n, where \n represents “newline.” (On Windows, enter results in a carriage return and a newline, \r\n.)
  • trim eliminates \n or \r\n, resulting in just 5.

Chapter 2 · 2.4 Comparing the Guess to the Secret Number

parse, the u32 annotation, and failure

The parse method on strings converts a string to another type — here, from a string to a number. We tell Rust the exact number type we want with let guess: u32: the colon (:) after guess tells Rust we’ll annotate the variable’s type.

Rust has a few built-in number types; u32 is an unsigned, 32-bit integer, a good default choice for a small positive number (other number types: Chapter 3).

The u32 annotation and the comparison with secret_number mean Rust infers that secret_number should be a u32 as well. So now the comparison is between two values of the same type!

parse only works on characters that can logically be converted into numbers, so it can easily cause errors: a string such as A👍% cannot be converted to a number. Because it might fail, parse returns a Result, much as read_line does, and we treat it the same way, with expect:

  • Err (no number could be created from the string): expect crashes the game and prints the message we give it.
  • Ok (the conversion succeeded): expect returns the number that we want from the Ok value.

Chapter 2 · 2.5 Allowing Multiple Guesses with Looping

How the match handles Ok and Err

If parse is able to turn the string into a number, it returns an Ok value that contains the resultant number. That Ok value matches the first arm’s pattern, and the match expression just returns the num value that parse produced and put inside the Ok value. That number ends up right where we want it, in the new guess variable we’re creating.

If parse is not able to turn the string into a number, it returns an Err value that contains more information about the error. The Err value does not match the Ok(num) pattern in the first arm, but it does match the Err(_) pattern in the second arm.

Definition 2.15 (Catch-all value). The underscore, _, in a pattern. Err(_) says we want to match all Err values, no matter what information they have inside them.

So the program executes the second arm’s code, continue, which tells the program to go to the next iteration of the loop and ask for another guess. Effectively, the program ignores all errors that parse might encounter!

Chapter summary

This project was a hands-on way to introduce many new Rust concepts: let, match, functions, the use of external crates, and more. Along the way the guessing game used:

  • variables, immutable by default, made mutable with mut, and shadowing to convert a value’s type;
  • associated functions (String::new), methods, and references (&mut guess);
  • Result with Ok/Err, handled by expect or by a match;
  • the rand crate as a dependency, SemVer specifiers, Cargo.lock and cargo update;
  • Ordering and cmp, loop, break and continue.

Remark. The next few chapters cover these concepts in more detail. Chapter 3 covers concepts that most programming languages have, such as variables, data types, and functions, and shows how to use them in Rust. Chapter 4 explores ownership, a feature that makes Rust different from other languages. Chapter 5 discusses structs and method syntax, and Chapter 6 explains how enums work.
