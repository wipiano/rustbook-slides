Chapter 18

Object-Oriented Programming Features

Object-oriented programming (OOP) is a way of modeling programs. Objects as a programmatic concept were introduced in the language Simula in the 1960s. Those objects influenced Alan Kay’s programming architecture in which objects pass messages to each other; to describe it, he coined the term object-oriented programming in 1967. Many competing definitions describe what OOP is: by some of them Rust is object oriented, by others it is not.

This chapter explores characteristics commonly considered object oriented and how they translate to idiomatic Rust. It then implements an object-oriented design pattern in Rust and discusses the trade-offs versus a solution that uses some of Rust’s strengths instead.

Chapter 18 · 18.1 Characteristics of Object-Oriented Languages

What makes a language object oriented?

There is no consensus in the programming community about what features a language must have to be considered object oriented. Rust is influenced by many paradigms, including OOP (Chapter 13 explored the features that came from functional programming). Arguably, OOP languages share certain common characteristics — namely, objects, encapsulation, and inheritance. Let’s see what each means and whether Rust supports it.

Objects contain data and behavior

Design Patterns: Elements of Reusable Object-Oriented Software by Gamma, Helm, Johnson, and Vlissides (Addison-Wesley, 1994), colloquially the Gang of Four book, is a catalog of object-oriented design patterns. It defines OOP this way:

Definition 18.1 (Object). “Object-oriented programs are made up of objects. An object packages both data and the procedures that operate on that data. The procedures are typically called methods or operations.”

By this definition Rust is object oriented: structs and enums have data, and impl blocks provide methods on them. Even though structs and enums with methods aren’t called objects, they provide the same functionality.

Encapsulation that hides implementation details

Definition 18.2 (Encapsulation). The implementation details of an object aren’t accessible to code using that object. The only way to interact with an object is through its public API; code using the object shouldn’t be able to reach into its internals and change data or behavior directly. This lets the programmer change and refactor an object’s internals without changing the code that uses the object.

Chapter 7 showed how to control encapsulation: the pub keyword decides which modules, types, functions, and methods are public; by default everything else is private. For example, a struct AveragedCollection can hold a vector of i32 values plus a field with their average, so the average needn’t be computed on demand — the struct caches the calculated average.

Public methods guard the private fields

The struct is marked pub so other code can use it, but its fields stay private. That matters here: whenever a value is added to or removed from the list, the average must also be updated. We do this by implementing add, remove, and average methods on the struct.

Listing 18.2: Implementations of the public methods add, remove, and average on AveragedCollection — src/lib.rs

pub struct AveragedCollection {

    list: Vec<i32>,

    average: f64,

}

 

impl AveragedCollection {

    pub fn add(&mut self, value: i32) {

        self.list.push(value);

        self.update_average();

    }

    pub fn remove(&mut self) -> Option<i32> {

        let result = self.list.pop();

        match result {

            Some(value) => {

                self.update_average();

                Some(value)

            }

            None => None,

        }

    }

Reading the average, updating it privately

Why the fields stay private

We leave the list and average fields private so external code has no way to add or remove items in the list field directly; otherwise the average field might get out of sync when the list changes. The average method returns the value of the average field, so external code can read the average but not modify it.

Because the implementation details are encapsulated, we can easily change aspects such as the data structure later. For instance, the list field could use a HashSet<i32> instead of a Vec<i32>. As long as the signatures of the public methods add, remove, and average stay the same, code using AveragedCollection wouldn’t need to change.

If list were public instead, this wouldn’t necessarily hold: HashSet<i32> and Vec<i32> have different methods for adding and removing items, so external code that modified list directly would likely have to change.

Remark. If encapsulation is a required aspect for a language to be considered object oriented, Rust meets that requirement: the option to use pub or not for different parts of code enables encapsulation of implementation details.

Inheritance as a type system and as code sharing

Definition 18.3 (Inheritance). A mechanism whereby an object can inherit elements from another object’s definition, thus gaining the parent object’s data and behavior without you having to define them again.

If a language must have inheritance to be object oriented, Rust is not such a language: there is no way to define a struct that inherits the parent struct’s fields and method implementations without using a macro. But if inheritance is in your toolbox, Rust has other solutions, depending on why you reached for it.

There are two main reasons. The first is reuse of code:implement behavior for one type, then reuse it for a different type. Rust allows this in a limited way with default trait method implementations — as in Listing 10.14, where the Summary trait got a default summarize method. Any type implementing Summary has summarize without further code, like a child class inheriting a parent’s method. Overriding the default when implementing Summary is like a child class overriding an inherited method.

Inheritance for the type system: polymorphism

The other reason to use inheritance relates to the type system: to enable a child type to be used in the same places as the parent type. This is also called polymorphism.

Definition 18.4 (Polymorphism). You can substitute multiple objects for each other at runtime if they share certain characteristics. More generally, polymorphism refers to code that can work with data of multiple types.

Polymorphism

To many people, polymorphism is synonymous with inheritance. But it’s actually a more general concept that refers to code that can work with data of multiple types. For inheritance, those types are generally subclasses.

Definition 18.5 (Bounded parametric polymorphism). Rust’s approach instead: generics abstract over different possible types, and trait bounds impose constraints on what those types must provide.

Why Rust does not offer inheritance

Rust has chosen a different set of trade-offs by not offering inheritance. Inheritance has these risks:

  • It is often at risk of sharing more code than necessary. Subclasses shouldn’t always share all characteristics of their parent class but will do so with inheritance, which can make a program’s design less flexible.
  • It introduces the possibility of calling methods on subclasses that don’t make sense or that cause errors because the methods don’t apply to the subclass.
  • Some languages only allow single inheritance (a subclass can inherit from only one class), further restricting the flexibility of a program’s design.

For these reasons, Rust takes the different approach of using trait objects instead of inheritance to achieve polymorphism at runtime. The next section looks at how trait objects work.

When the set of types must stay open

Chapter 8 noted that vectors can store elements of only one type. Listing 8.9 worked around this with a SpreadsheetCell enum whose variants hold integers, floats, and text, so a vector could represent a row of cells. That is a perfectly good solution when the interchangeable items are a fixed set of types known when the code is compiled.

Sometimes, though, we want the library user to be able to extend the set of valid types. Example: a GUI tool that iterates through a list of items, calling a draw method on each to draw it to the screen — a common technique for GUI tools. We’ll create a library crate called gui with the structure of a GUI library. It might include types such as Button or TextField, and gui users will want to create their own drawable types: one programmer might add an Image, another a SelectBox.

When writing the library, we can’t know and define every type other programmers might create. But we do know that gui must keep track of many values of different types and call draw on each. It doesn’t need to know what exactly happens when draw is called — only that the value has that method available.

From a Component base class to a Draw trait

In a language with inheritance, we might define a class Component with a method draw. Other classes such as Button, Image, and SelectBox would inherit from Component and thus inherit draw. Each could override draw with custom behavior, while the framework treats all of them as Component instances and calls draw on them. Rust has no inheritance, so gui needs another structure that lets users create new compatible types.

Defining a trait for common behavior

We’ll define a trait named Draw with one method named draw. Then we can define a vector that takes a trait object.

Definition 18.6 (Trait object). A value that points to both an instance of a type implementing a specified trait and a table used to look up trait methods on that type at runtime. It is written as some sort of pointer (a reference or a Box<T> smart pointer), then the dyn keyword, then the trait — e.g. Box<dyn Draw>.

Chapter 18 · 18.2 Using Trait Objects to Abstract over Shared Behavior

What trait objects guarantee — and what they are not

We can use trait objects in place of a generic or concrete type. Wherever a trait object is used, Rust’s type system ensures at compile time that any value used in that context implements the trait object’s trait. Consequently, we don’t need to know all the possible types at compile time.

Remark. Why trait objects must use a pointer is explained in “Dynamically Sized Types and the Sized Trait” in Chapter 20.

In Rust we refrain from calling structs and enums “objects” to distinguish them from other languages’ objects. In a struct or enum, the data in the fields and the behavior in impl blocks are separated, whereas other languages often label data and behavior combined into one concept an object.

Trait objects differ from objects in other languages in that we can’t add data to a trait object. They aren’t as generally useful as objects in other languages: their specific purpose is to allow abstraction across common behavior.

Like duck typing, but checked at compile time

Definition 18.7 (Duck typing). In dynamically typed languages, being concerned only with the messages a value responds to rather than the value’s concrete type: if it walks like a duck and quacks like a duck, then it must be a duck!

The concept of trait objects is similar. In the implementation of run on Screen in Listing 18.5, run doesn’t need to know the concrete type of each component. It doesn’t check whether a component is a Button or a SelectBox; it just calls draw on it. By specifying Box<dyn Draw> as the type of the values in the components vector, we’ve defined Screen to need values that we can call the draw method on.

The advantage of using trait objects and Rust’s type system to write code similar to duck typing: we never have to check at runtime whether a value implements a particular method, or worry about errors if a value doesn’t implement a method but we call it anyway. Rust won’t compile our code if the values don’t implement the traits that the trait objects need.

Chapter 18 · 18.2 Using Trait Objects to Abstract over Shared Behavior

Performing dynamic dispatch

Recall from “Performance of Code Using Generics” in Chapter 10 the monomorphization process the compiler performs on generics: it generates nongeneric implementations of functions and methods for each concrete type used in place of a generic type parameter.

Definition 18.8 (Static dispatch). The compiler knows what method you’re calling at compile time. The code that results from monomorphization does static dispatch.

Definition 18.9 (Dynamic dispatch). The compiler can’t tell at compile time which method you’re calling. Instead, it emits code that at runtime will know which method to call.

When we use trait objects, Rust must use dynamic dispatch. The compiler doesn’t know all the types that might be used with the code that’s using trait objects, so it doesn’t know which method implemented on which type to call. Instead, at runtime, Rust uses the pointers inside the trait object to know which method to call.

The cost of dynamic dispatch

  • The runtime lookup incurs a cost that doesn’t occur with static dispatch.
  • Dynamic dispatch also prevents the compiler from choosing to inline a method’s code, which in turn prevents some optimizations.
  • Rust has rules about where you can and cannot use dynamic dispatch.

Definition 18.10 (Dyn compatibility). Rust’s rules about where you can and cannot use dynamic dispatch. They are beyond the scope of this chapter; the Rust Reference (doc.rust-lang.org/reference/items/traits.html#dyn-compatibility) describes them.

However, we did get extra flexibility in the code we wrote in Listing 18.5 and were able to support in Listing 18.9, so it’s a trade-off to consider.

Chapter 18 · 18.3 Implementing an Object-Oriented Design Pattern

The state pattern

Definition 18.11 (State pattern). An object-oriented design pattern whose crux is that we define a set of states a value can have internally. The states are represented by a set of state objects, and the value’s behavior changes based on its state.

The example is a blog post struct with a field holding its state: a state object from the set “draft,” “review,” or “published.”

The state objects share functionality — in Rust, of course, we use structs and traits rather than objects and inheritance. Each state object is responsible for its own behavior and for governing when it should change into another state. The value that holds a state object knows nothing about the different behavior of the states or when to transition between them.

The advantage: when the program’s business requirements change, we won’t need to change the code of the value holding the state or the code that uses the value. We’ll only need to update the code inside one of the state objects to change its rules, or perhaps add more state objects.

Chapter 18 · 18.3 Implementing an Object-Oriented Design Pattern

The blog post workflow we will build

First we implement the state pattern in a more traditional object-oriented way; then we use an approach that’s a bit more natural in Rust. We build the blog post workflow incrementally. The final functionality:

  1. A blog post starts as an empty draft.
  2. When the draft is done, a review of the post is requested.
  3. When the post is approved, it gets published.
  4. Only published blog posts return content to print, so unapproved posts can’t accidentally be published.

Any other changes attempted on a post should have no effect. For example, if we try to approve a draft blog post before we’ve requested a review, the post should remain an unpublished draft.

Chapter 18 · 18.3 Implementing an Object-Oriented Design Pattern

What the API promises its users

We want to allow the user to create a new draft blog post with Post::new and to add text to it. If we try to get the post’s content immediately, before approval, we shouldn’t get any text, because the post is still a draft.

Next, we want to enable a request for a review of the post, and we want content to return an empty string while waiting for the review. When the post receives approval, it should get published, meaning the text of the post will be returned when content is called.

The only type we interact with from the crate is Post. It uses the state pattern and holds a value that is one of three state objects — draft, review, or published. Changing from one state to another is managed internally within Post: the states change in response to the methods users call on the Post instance, but users don’t manage the state changes directly. Users also can’t make a mistake with the states, such as publishing a post before it’s reviewed.

Chapter 18 · 18.3 Implementing an Object-Oriented Design Pattern

Consuming the old state: self: Box<Self> and take

Post gets a public method request_review that takes a mutable reference to self. It calls an internal request_review method on the current state of Post, and this second request_review consumes the current state and returns a new state.

We add request_review to the State trait, so all implementing types must now implement it. Its first parameter is not self, &self, or &mut self but self: Box<Self>: the method is only valid when called on a Box holding the type. This syntax takes ownership of Box<Self>, invalidating the old state so that the Post’s state value can transform into a new state.

To consume the old state, request_review needs ownership of the state value. That is where the Option in Post’s state field comes in: we call take to take the Some value out of the state field and leave a None in its place, because Rust doesn’t let us have unpopulated fields in structs. This lets us move the state value out of Post rather than borrowing it. Then we set the post’s state to the result of this operation.

Each state is responsible for its own rules

We need to set state to None temporarily, rather than writing code like self.state = self.state.request_review();, to get ownership of the state value. This ensures Post can’t use the old state value after we’ve transformed it into a new state.

request_review on Draft returns a new, boxed instance of a new PendingReview struct, the state of a post waiting for a review. PendingReview also implements request_review but doesn’t transform anything: it returns itself, because requesting a review on a post already in PendingReview should keep it there.

Now the advantages of the state pattern start to show: request_review on Post is the same no matter its state value. Each state is responsible for its own rules.

We leave content on Post as is, returning an empty string slice: a Post can now be in PendingReview as well as Draft, and we want the same behavior in both. Listing 18.11 now works up to the second assert_eq! call!

We then call unwrap, which we know will never panic: the methods on Post ensure that state always contains a Some value when they are done. Why not an enum? Evaluating the state pattern

Why not an enum?

An enum with the possible post states as variants is certainly a possible solution — try it and compare the end results to see which you prefer! One disadvantage: every place that checks the value of the enum needs a match expression or similar to handle every possible variant, which could get more repetitive than this trait object solution.

Evaluating the state pattern

Rust can implement the object-oriented state pattern to encapsulate the different kinds of behavior a post should have in each state. The methods on Post know nothing about the various behaviors. To know the different ways a published post can behave, we look in only one place: the implementation of State on Published.

Without the state pattern, we might use match expressions in the methods on Post, or even in main, that check the state and change behavior there. Then we would have to look in several places to understand all the implications of a post being published.

Downsides: coupled states and duplicated logic

Coupling. Because the states implement the transitions between states, some states are coupled to each other. Adding a state such as Scheduled between PendingReview and Published would mean changing the code in PendingReview to transition to Scheduled instead. It would be less work if PendingReview didn’t need to change, but that would mean switching to another design pattern.

Duplicated defaults. We might try default implementations of request_review and approve on the State trait that return self. This wouldn’t work: when State is used as a trait object, the trait doesn’t know what the concrete self will be, so the return type isn’t known at compile time. (This is one of the dyn compatibility rules.)

Duplicated delegation. request_review and approve on Post both use Option::take on state and, if it is Some, delegate to the wrapped value’s same-named method and store the result. With many such methods, we might define a macro to remove the repetition (see “Macros” in Chapter 20).

Encoding states and behavior as types

By implementing the state pattern exactly as it’s defined for object-oriented languages, we’re not taking as full advantage of Rust’s strengths as we could. Some changes to the blog crate can make invalid states and transitions into compile-time errors.

We rethink the state pattern to get a different set of trade-offs. Rather than encapsulating the states and transitions completely so that outside code has no knowledge of them, we encode the states into different types. Consequently, Rust’s type-checking system prevents attempts to use draft posts where only published posts are allowed, by issuing a compiler error.

The state now lives in the type

Both Post and DraftPost have a private content field that stores the blog post text. The structs no longer have a state field, because the encoding of the state moves to the types of the structs. Post represents a published post, and its content method returns the content.

The workflow encoded into the type system

The request_review and approve methods take ownership of self, consuming the DraftPost and PendingReviewPost instances and transforming them into a PendingReviewPost and a published Post, respectively. So no DraftPost instances linger after we’ve called request_review on them, and so forth.

PendingReviewPost has no content method, so attempting to read its content is a compiler error, as with DraftPost. The only way to get a published Post — which does have content — is to call approve on a PendingReviewPost, and the only way to get a PendingReviewPost is to call request_review on a DraftPost. We’ve now encoded the blog post workflow into the type system.

main needs small changes too. request_review and approve return new instances rather than modifying the struct they’re called on, so we add more let post = shadowing assignments to save the returned instances. We also can’t — and needn’t — assert that draft and pending posts’ contents are empty strings: code that tries to use the content of posts in those states no longer compiles.

Trading encapsulation for compile-time guarantees

Reassigning post in main means this implementation doesn’t quite follow the object-oriented state pattern anymore: the transformations between the states are no longer encapsulated entirely within the Post implementation. However, invalid states are now impossible because of the type system and the type checking that happens at compile time! Certain bugs, such as displaying the content of an unpublished post, are discovered before they make it to production.

Even though Rust is capable of implementing object-oriented design patterns, other patterns, such as encoding state into the type system, are also available, with different trade-offs. You might be very familiar with object-oriented patterns, but rethinking the problem to take advantage of Rust’s features can provide benefits, such as preventing some bugs at compile time. Object-oriented patterns won’t always be the best solution in Rust, due to features like ownership that object-oriented languages don’t have.

Chapter 18 · Summary

Chapter summary

Regardless of whether you think Rust is an object-oriented language after reading this chapter, you now know that:

  • you can use trait objects to get some object-oriented features in Rust;
  • dynamic dispatch can give your code some flexibility in exchange for a bit of runtime performance;
  • you can use this flexibility to implement object-oriented patterns that can help your code’s maintainability;
  • Rust also has other features, like ownership, that object-oriented languages don’t have.

An object-oriented pattern won’t always be the best way to take advantage of Rust’s strengths, but it is an available option.
