Chapter 15 · Introduction

Pointers, references and smart pointers

A pointer is a general concept for a variable that contains an address in memory; the address refers to, or “points at,” some other data. The most common kind of pointer in Rust is a reference (Chapter 4): indicated by the & symbol, it borrows the value it points to. References have no special capabilities other than referring to data, and they have no overhead.

Definition 15.1 (Smart pointer). A data structure that acts like a pointer but also has additional metadata and capabilities.

Smart pointers aren’t unique to Rust: they originated in C++ and exist in other languages as well. Rust’s standard library defines a variety of them, providing functionality beyond that of references. One example in this chapter is a reference counting smart pointer, which lets data have multiple owners by keeping track of the number of owners and cleaning up the data when no owners remain.

With Rust’s ownership and borrowing there is one more difference: while references only borrow data, in many cases smart pointers own the data they point to.

Chapter 15 · Introduction

Deref, Drop, and the smart pointers in this chapter

Smart pointers are usually implemented using structs. Unlike an ordinary struct, they implement the Deref and Drop traits. Deref lets an instance of the smart pointer struct behave like a reference, so you can write code that works with either references or smart pointers. Drop lets you customize the code that runs when an instance goes out of scope.

The smart pointer pattern is a general design pattern used frequently in Rust; many libraries have their own, and you can write your own. The chapter covers the most common ones in the standard library:

  • Box<T>, for allocating values on the heap;
  • Rc<T>, a reference counting type that enables multiple ownership;
  • Ref<T> and RefMut<T>, accessed through RefCell<T>, a type that enforces the borrowing rules at runtime instead of compile time.

It also covers the interior mutability pattern, where an immutable type exposes an API for mutating an interior value, and reference cycles: how they can leak memory and how to prevent them.

Chapter 15 · 15.1 Using Box<T> to Point to Data on the Heap

Boxes and when to use them

Definition 15.2 (Box). The most straightforward smart pointer, of type Box<T>. A box stores data on the heap rather than the stack; what remains on the stack is the pointer to the heap data (stack vs. heap: Chapter 4).

Boxes have no performance overhead other than storing their data on the heap instead of the stack — but they don’t have many extra capabilities either. You’ll use them most often in these situations:

  1. When you have a type whose size can’t be known at compile time, and you want to use a value of that type in a context that requires an exact size.
  2. When you have a large amount of data, and you want to transfer ownership but ensure that the data won’t be copied when you do so.
  3. When you want to own a value, and you care only that it’s a type that implements a particular trait rather than being of a specific type.

Enabling recursive types with boxes

Definition 15.3 (Recursive type). A type whose values can have another value of the same type as part of themselves.

Recursive types pose an issue because Rust needs to know at compile time how much space a type takes up, yet the nesting of values could theoretically continue infinitely. Because boxes have a known size, we can enable recursive types by inserting a box in the recursive type definition.

The example is the cons list, a data type commonly found in functional programming languages. It is straightforward except for the recursion, so its concepts carry over to more complex recursive types.

Definition 15.4 (Cons list). A data structure from the Lisp programming language and its dialects, made up of nested pairs: the Lisp version of a linked list. Its name comes from Lisp’s cons function (short for construct function), which constructs a new pair from its two arguments. Calling cons on a pair of a value and another pair builds cons lists of recursive pairs.

Understanding the cons list

A pseudocode representation of a cons list containing the list 1, 2, 3, with each pair in parentheses:

(1, (2, (3, Nil)))

  • Each item contains two elements: the value of the current item and the next item.
  • The last item contains only a value called Nil, without a next item. A cons list is produced by recursively calling the cons function, and the canonical name for the base case of the recursion is Nil.
  • This is not the same as the “null” or “nil” concept of Chapter 6, which is an invalid or absent value.

The cons list isn’t commonly used in Rust: most of the time, Vec<T> is a better choice for a list of items. Other, more complex recursive data types are useful in various situations, but starting with the cons list lets us explore how boxes enable a recursive data type without much distraction.

Computing the size of a non-recursive type

The type “has infinite size” because List has a variant that is recursive: it holds another value of itself directly, so Rust can’t figure out how much space a List needs. First, how does Rust size a non-recursive type? Recall the Message enum of Listing 6.2:

enum Message {

    Quit,

    Move { x: i32, y: i32 },

Rust goes through each variant to see which needs the most space: Message::Quit needs none, Message::Move needs enough for two i32 values, and so forth. Because only one variant will be used, the most space a Message value needs is the space of its largest variant.

Getting a recursive type with a known size

Definition 15.5 (Indirection). Instead of storing a value directly, changing the data structure to store the value indirectly, by storing a pointer to the value instead.

Because a Box<T> is a pointer, Rust always knows how much space it needs: a pointer’s size doesn’t change based on the amount of data it points to. Following the reference to the value

A regular reference is a type of pointer; think of a pointer as an arrow to a value stored somewhere else. Listing 15.6 creates a reference to an i32 and uses the dereference operator to follow it to the value.

Listing 15.6: Using the dereference operator to follow a reference to an i32 value — src/main.rs

fn main() {

Implementing the Deref trait

To implement a trait we provide implementations for its required methods (“Implementing a Trait on a Type,” Chapter 10). The standard library’s Deref trait requires one method named deref that borrows self and returns a reference to the inner data. Listing 15.10 adds an implementation of Deref to the definition of MyBox<T>.

Listing 15.10: Implementing Deref on MyBox<T> — src/main.rs

use std::ops::Deref;

 

impl<T> Deref for MyBox<T> {

    type Target = T;

 

    fn deref(&self) -> &Self::Target {

        &self.0

    }

}

The type Target = T; syntax defines an associated type for the Deref trait to use. Associated types are a slightly different way of declaring a generic parameter; you don’t need to worry about them for now — Chapter 20 covers them in more detail.

What *y really runs

The body of deref is &self.0, so deref returns a reference to the value we want to access with the * operator (.0 accesses the first value in a tuple struct — “Creating Different Types with Tuple Structs,” Chapter 5). The main function of Listing 15.9 that calls * on the MyBox<T> value now compiles, and the assertions pass!

Without Deref, the compiler can only dereference & references. The deref method gives it the ability to take a value of any type that implements Deref and call deref to get a reference it knows how to dereference. When we entered *y in Listing 15.9, behind the scenes Rust actually ran this code:

*(y.deref())

Rust substitutes the * operator with a call to the deref method and then a plain dereference, so we don’t have to think about whether or not to call deref. This lets us write code that functions identically whether we have a regular reference or a type that implements Deref.

Why deref returns a reference, and substitutes only once

A reference, because of ownership

The reason deref returns a reference to a value — and that the plain dereference outside the parentheses in *(y.deref()) is still necessary — has to do with the ownership system. If deref returned the value directly instead of a reference to it, the value would be moved out of self. We don’t want to take ownership of the inner value inside MyBox<T> in this case, or in most cases where we use the dereference operator.

One substitution per *

Each time we use a * in our code, it is replaced with a call to deref and then a call to the * operator just once. Because the substitution does not recurse infinitely, we end up with data of type i32, which matches the 5 in assert_eq! in Listing 15.9.

Deref coercion in functions and methods

Definition 15.7 (Deref coercion). A conversion of a reference to a type that implements the Deref trait into a reference to another type. For example, it can convert &String to &str, because String implements Deref such that it returns &str.

  • It is a convenience Rust performs on arguments to functions and methods, and works only on types that implement Deref.
  • It happens automatically when we pass a reference to a particular type’s value as an argument to a function or method whose parameter type doesn’t match it.
  • A sequence of calls to the deref method converts the type we provided into the type the parameter needs.

Deref coercion was added to Rust so that programmers writing function and method calls don’t need to add as many explicit references and dereferences with & and *. It also lets us write more code that can work for either references or smart pointers.

When the Deref trait is defined for the types involved, Rust analyzes the types and uses Deref::deref as many times as necessary to get a reference that matches the parameter’s type. The number of insertions is resolved at compile time, so there is no runtime penalty for taking advantage of deref coercion!

Deref coercion with mutable references

Just as the Deref trait overrides the * operator on immutable references, the DerefMut trait overrides the * operator on mutable references. Rust does deref coercion when it finds types and trait implementations in three cases:

Table 15.1: The three cases of deref coercion

CaseFrom → toWhen
1&T → &UT: Deref<Target=U>
2&mut T → &mut UT: DerefMut<Target=U>
3&mut T → &UT: Deref<Target=U>

The first two cases are the same except that the second implements mutability. The first says that if you have a &T, and T implements Deref to some type U, you can get a &U transparently. The second says the same deref coercion happens for mutable references.

Mutable to immutable, never the reverse

The third case is trickier: Rust will also coerce a mutable reference to an immutable one. But the reverse is not possible: immutable references will never coerce to mutable references.

  • Because of the borrowing rules, if you have a mutable reference, that mutable reference must be the only reference to that data (otherwise, the program wouldn’t compile).
  • So converting one mutable reference to one immutable reference will never break the borrowing rules.
  • Converting an immutable reference to a mutable reference would require that the initial immutable reference is the only immutable reference to that data — but the borrowing rules don’t guarantee that.
  • Therefore, Rust can’t assume that converting an immutable reference to a mutable reference is possible.

The Drop trait

The second trait important to the smart pointer pattern is Drop, which lets you customize what happens when a value is about to go out of scope. You can implement Drop on any type, and that code can be used to release resources like files or network connections.

Drop is introduced with smart pointers because its functionality is almost always used when implementing one. For example, when a Box<T> is dropped, it deallocates the space on the heap that the box points to.

In some languages, for some types, the programmer must call code to free memory or resources every time they finish using an instance — for example file handles, sockets, and locks. If they forget, the system might become overloaded and crash. In Rust, you can specify that a particular bit of code be run whenever a value goes out of scope, and the compiler inserts this code automatically. So you don’t need to place cleanup code everywhere an instance of a particular type is finished with — and you still won’t leak resources!

Multiple owners and reference counting

In the majority of cases, ownership is clear: you know exactly which variable owns a given value. But a single value might have multiple owners. In graph data structures, for example, multiple edges might point to the same node, and that node is conceptually owned by all of the edges pointing to it; it shouldn’t be cleaned up unless no edges point to it, so it has no owners.

Definition 15.10 (Rc<T>). The type, short for reference counting, that enables multiple ownership explicitly. It keeps track of the number of references to a value to determine whether the value is still in use; with zero references, the value can be cleaned up without any references becoming invalid.

Example 15.11. Imagine Rc<T> as a TV in a family room. When one person enters to watch TV, they turn it on. Others can come into the room and watch. When the last person leaves the room, they turn off the TV because it’s no longer being used. If someone turned it off while others were still watching, there would be an uproar from the remaining TV watchers!

The interior mutability pattern

Definition 15.12 (Interior mutability). A design pattern in Rust that allows you to mutate data even when there are immutable references to that data — an action normally disallowed by the borrowing rules.

To mutate data, the pattern uses unsafe code inside a data structure to bend Rust’s usual rules that govern mutation and borrowing. Unsafe code indicates to the compiler that we’re checking the rules manually instead of relying on the compiler to check them for us (Chapter 20 discusses unsafe code).

We can use types that follow the interior mutability pattern only when we can ensure that the borrowing rules will be followed at runtime, even though the compiler can’t guarantee that. The unsafe code involved is then wrapped in a safe API, and the outer type is still immutable.

We explore this concept through the RefCell<T> type, which follows the interior mutability pattern.

Chapter 15 · 15.5 RefCell<T> and the Interior Mutability Pattern

Enforcing borrowing rules at runtime

Unlike Rc<T>, the RefCell<T> type represents single ownership over the data it holds. So what makes it different from a type like Box<T>? Recall the borrowing rules of Chapter 4:

  • At any given time, you can have either one mutable reference or any number of immutable references (but not both).
  • References must always be valid.

With references and Box<T>, these invariants are enforced at compile time; break them and you get a compiler error. With RefCell<T>, they are enforced at runtime; break them and your program will panic and exit.

Checking at compile time catches errors sooner in the development process, with no impact on runtime performance, because all the analysis is completed beforehand. That makes it the best choice in the majority of cases, which is why it is Rust’s default.

Why check at runtime: a conservative compiler

Checking the borrowing rules at runtime instead allows certain memory-safe scenarios that the compile-time checks would have disallowed. Static analysis, like the Rust compiler, is inherently conservative: some properties of code are impossible to detect by analyzing the code. The most famous example is the Halting Problem, which is beyond the scope of the book but an interesting topic to research.

Because some analysis is impossible, if the compiler can’t be sure the code complies with the ownership rules, it might reject a correct program. If Rust accepted an incorrect program, users couldn’t trust its guarantees; if it rejects a correct program, the programmer is inconvenienced, but nothing catastrophic can occur. RefCell<T> is useful when you’re sure your code follows the borrowing rules but the compiler is unable to understand and guarantee that.

Remark. Like Rc<T>, RefCell<T> is only for single-threaded scenarios, and gives a compile-time error if you try using it in a multithreaded context. Chapter 16 shows how to get its functionality in a multithreaded program.

Tracking borrows at runtime

To create immutable and mutable references we use the & and &mut syntax. With RefCell<T>, we use the borrow and borrow_mut methods, part of its safe API.

Definition 15.16 (Ref<T> and RefMut<T>). The smart pointer types returned by RefCell<T>’s borrow and borrow_mut methods, respectively. Both implement Deref, so we can treat them like regular references.

The RefCell<T> keeps track of how many Ref<T> and RefMut<T> smart pointers are currently active. Every call to borrow increases its count of active immutable borrows; when a Ref<T> goes out of scope, the count goes down by 1. Just like the compile-time borrowing rules, RefCell<T> lets us have many immutable borrows or one mutable borrow at any point in time.

If we violate these rules, rather than a compiler error, the implementation of RefCell<T> panics at runtime. Listing 15.23 modifies send from Listing 15.22 to deliberately create two mutable borrows active for the same scope.

Memory leaks are memory safe

Definition 15.17 (Memory leak). Memory that is never cleaned up.

Rust’s memory safety guarantees make it difficult, but not impossible, to accidentally create a memory leak. Preventing memory leaks entirely is not one of Rust’s guarantees, meaning memory leaks are memory safe in Rust. Using Rc<T> and RefCell<T>, it’s possible to create references where items refer to each other in a cycle. This creates memory leaks, because the reference count of each item in the cycle will never reach 0, and the values will never be dropped.

Consequences, and how to avoid cycles

If you uncomment the last println! and run the program, Rust tries to print the cycle — a pointing to b pointing to a, and so forth — until it overflows the stack.

Here the consequences aren’t very dire: right after we create the cycle, the program ends. But a more complex program that allocated lots of memory in a cycle and held onto it for a long time would use more memory than it needed, and might overwhelm the system, running out of available memory.

Creating reference cycles is not easily done, but not impossible. If you have RefCell<T> values containing Rc<T> values, or similar nested combinations of interior mutability and reference counting, you must ensure you don’t create cycles; you can’t rely on Rust to catch them. A cycle is a logic bug, to minimize with automated tests, code reviews, and other software development practices.

Another solution is reorganizing data structures so that some references express ownership and some don’t: cycles can then mix ownership and non-ownership relationships, and only ownership relationships affect whether a value can be dropped. In Listing 15.25, Cons variants must always own their list, so that isn’t possible; a graph of parent and child nodes shows when non-ownership relationships are appropriate.

Preventing reference cycles using Weak<T>

So far, calling Rc::clone increases the strong_count of an Rc<T> instance, and an Rc<T> instance is only cleaned up if its strong_count is 0. You can also create a weak reference to the value within an Rc<T> instance by calling Rc::downgrade and passing a reference to the Rc<T>.

Definition 15.18 (Strong reference). A reference through which you share ownership of an Rc<T> instance (counted in strong_count).

Definition 15.19 (Weak reference). A reference that doesn’t express an ownership relationship; its count doesn’t affect when an Rc<T> instance is cleaned up.

Weak references won’t cause a reference cycle, because any cycle involving some weak references will be broken once the strong reference count of the values involved is 0.

Weak<T>, weak_count, and upgrade

Calling Rc::downgrade gives a smart pointer of type Weak<T>. Instead of increasing the strong_count of the Rc<T> instance by 1, it increases the weak_count by 1. Rc<T> uses weak_count to keep track of how many Weak<T> references exist, similar to strong_count. The difference: weak_count doesn’t need to be 0 for the Rc<T> instance to be cleaned up.

Because the value a Weak<T> references might have been dropped, to do anything with it you must make sure the value still exists. Call the upgrade method on a Weak<T> instance, which returns an Option<Rc<T>>: Some if the Rc<T> value has not been dropped yet, and None if it has. Because upgrade returns an Option<Rc<T>>, Rust ensures that both the Some and None cases are handled, and there won’t be an invalid pointer.

Reading the counts

  • After leaf is created, its Rc<Node> has a strong count of 1 and a weak count of 0.
  • In the inner scope, we create branch and associate it with leaf. The Rc<Node> in branch then has a strong count of 1 and a weak count of 1 (for leaf.parent pointing to branch with a Weak<Node>).
  • The counts in leaf show a strong count of 2, because branch now has a clone of the Rc<Node> of leaf stored in branch.children, but still a weak count of 0.
  • When the inner scope ends, branch goes out of scope and the strong count of its Rc<Node> decreases to 0, so its Node is dropped. The weak count of 1 from leaf.parent has no bearing on whether or not Node is dropped, so we don’t get any memory leaks!

By specifying in the definition of Node that the relationship from a child to its parent should be a Weak<T> reference, parent nodes can point to child nodes and vice versa without creating a reference cycle and memory leaks.

Chapter 15 · Summary

Chapter summary

Smart pointers make different guarantees and trade-offs from those Rust makes by default with regular references:

  • Box<T> has a known size and points to data allocated on the heap.
  • Rc<T> keeps track of the number of references to data on the heap, so that the data can have multiple owners.
  • RefCell<T>, with its interior mutability, gives a type to use when we need an immutable type but must change an inner value of it; it enforces the borrowing rules at runtime instead of at compile time.
  • The Deref and Drop traits enable a lot of the functionality of smart pointers.
  • Reference cycles can cause memory leaks; Weak<T> prevents them.

To implement your own smart pointers, “The Rustonomicon” has more useful information.
