Chapter 7

Packages, Crates, and Modules

As programs grow, organizing code matters: group related functionality, separate distinct features, and split one module in one file into multiple modules and then multiple files. A package can contain multiple binary crates and optionally one library crate; parts can be extracted into separate crates that become external dependencies (very large sets of interrelated packages use Cargo workspaces, Chapter 14). Encapsulation lets other code call yours through its public interface while private details stay yours to change. Scope decides which names are defined at each spot; two items can’t share a name in one scope. Together these features form the module system:

  • Packages: a Cargo feature that lets you build, test, and share crates
  • Crates: a tree of modules that produces a library or executable
  • Modules and use: control the organization, scope, and privacy of paths
  • Paths: a way of naming an item, such as a struct, function, or module

Chapter 7 · 7.1 Packages and Crates

Crates: binary and library

The first parts of the module system are packages and crates.

Definition 7.1 (Crate). The smallest amount of code that the Rust compiler considers at a time. Even if you run rustc rather than cargo on a single source file (as in Chapter 1), the compiler considers that file to be a crate. Crates can contain modules, and the modules may be defined in other files that get compiled with the crate.

A crate comes in one of two forms:

Definition 7.2 (Binary crate). A program you can compile to an executable that you can run, such as a command line program or a server. Each must have a function called main that defines what happens when the executable runs. All the crates created so far have been binary crates.

Definition 7.3 (Library crate). A crate with no main function that doesn’t compile to an executable; it defines functionality intended to be shared with multiple projects — e.g. the rand crate from Chapter 2, which generates random numbers.

Most of the time when Rustaceans say “crate,” they mean library crate, and they use “crate” interchangeably with the general programming concept of a “library.”

Chapter 7 · 7.1 Packages and Crates

Crate roots and packages

Definition 7.4 (Crate root). A source file that the Rust compiler starts from and that makes up the root module of your crate (modules are explained in 7.2).

Definition 7.5 (Package). A bundle of one or more crates that provides a set of functionality. A package contains a Cargo.toml file that describes how to build those crates.

Cargo itself is a package: it contains the binary crate for the command line tool you’ve been using to build your code, and also a library crate that the binary crate depends on. Other projects can depend on the Cargo library crate to use the same logic the Cargo command line tool uses.

Rules on what a package may contain:

  • as many binary crates as you like;
  • at most only one library crate;
  • at least one crate, whether that’s a library or binary crate.

Chapter 7 · 7.1 Packages and Crates

How Cargo finds crate roots

Cargo follows conventions instead of listing crate roots in Cargo.toml, and passes the crate root files to rustc to build the library or binary.

Table 7.1: Cargo’s crate-root conventions

File in the packageMeaning
src/main.rsCrate root of a binary crate with the same name as the package
src/lib.rsCrate root of a library crate with the same name as the package
src/bin/*.rsEach file is a separate binary crate
  • Our my-project package only contains src/main.rs, so it only contains a binary crate named my-project.
  • If a package contains src/main.rs and src/lib.rs, it has two crates: a binary and a library, both with the same name as the package.
  • A package can have multiple binary crates by placing files in the src/bin directory: each file will be a separate binary crate.

Chapter 7 · 7.2 Control Scope and Privacy with Modules

Modules cheat sheet: crate root and modules

This section covers modules and the other parts of the module system: paths, which name items; the use keyword that brings a path into scope; the pub keyword to make items public; plus the as keyword, external packages, and the glob operator.

First, a quick reference on how modules, paths, use and pub work in the compiler, and how most developers organize their code — a place to refer back to as a reminder:

  • Start from the crate root. When compiling a crate, the compiler first looks in the crate root file (usually src/lib.rs for a library crate and src/main.rs for a binary crate) for code to compile.
  • Declaring modules. In the crate root file, you can declare new modules; say you declare a “garden” module with mod garden;. The compiler looks for the module’s code in these places:
    • inline, within curly brackets that replace the semicolon following mod garden;
    • in the file src/garden.rs;
    • in the file src/garden/mod.rs.

Chapter 7 · 7.2 Control Scope and Privacy with Modules

Modules cheat sheet: submodules, paths, privacy, use

  • Declaring submodules. In any file other than the crate root, you can declare submodules — e.g. mod vegetables; in src/garden.rs. The compiler looks for the submodule’s code within the directory named for the parent module: inline, directly following mod vegetables, within curly brackets instead of the semicolon; in the file src/garden/vegetables.rs; in the file src/garden/vegetables/mod.rs.
  • Paths to code in modules. Once a module is part of your crate, you can refer to code in that module from anywhere else in that same crate, as long as the privacy rules allow, using the path to the code. An Asparagus type in the garden vegetables module would be found at crate::garden::vegetables::Asparagus.
  • Private vs. public. Code within a module is private from its parent modules by default. To make a module public, declare it with pub mod instead of mod. To make items within a public module public as well, use pub before their declarations.
  • The use keyword. Within a scope, use creates shortcuts to items to reduce repetition of long paths. In any scope that can refer to crate::garden::vegetables::Asparagus, use crate::garden::vegetables::Asparagus; creates a shortcut, and from then on you only need to write Asparagus in the scope.

Chapter 7 · 7.2 Control Scope and Privacy with Modules

Grouping related code in modules

Definition 7.6 (Module). A unit that organizes code within a crate for readability and easy reuse. Modules also control the privacy of items: code within a module is private by default.

Private items are internal implementation details not available for outside use. We can choose to make modules and the items within them public, which exposes them to allow external code to use and depend on them.

As an example, we write a library crate that provides the functionality of a restaurant. We define the signatures of functions but leave their bodies empty, to concentrate on the organization of the code rather than the implementation of a restaurant. In the restaurant industry:

  • Front of house is where customers are: where the hosts seat customers, servers take orders and payment, and bartenders make drinks.
  • Back of house is where the chefs and cooks work in the kitchen, dishwashers clean up, and managers do administrative work.

We organize its functions into nested modules; create the library with cargo new restaurant --lib.

Defining modules with mod

Listing 7.1: A front_of_house module containing other modules that then contain functions — src/lib.rs

mod front_of_house {

    mod hosting {

        fn add_to_waitlist() {}

 

        fn seat_at_table() {}

    }

        fn take_order() {}

        fn take_payment() {}

    }

}

This code, entered into src/lib.rs, is the front of house section.

  • A module is defined with the mod keyword followed by its name (here front_of_house); its body goes inside curly brackets.
  • Modules can hold other modules (here hosting and serving) and definitions of other items: structs, enums, constants, traits, and functions.
  • Grouping related definitions names why they’re related: readers navigate by group instead of reading every definition, and contributors know where to place new code to keep the program organized.

Chapter 7 · 7.2 Control Scope and Privacy with Modules

Reading the module tree

The tree in Listing 7.2 shows how modules relate:

  • Nesting. Some modules nest inside other modules; for example, hosting nests inside front_of_house.
  • Siblings. Modules defined in the same module are siblings: hosting and serving are siblings defined within front_of_house.
  • Child and parent. If module A is contained inside module B, module A is the child of module B, and module B is the parent of module A.
  • Root. The entire module tree is rooted under the implicit module named crate.

Example 7.8. The module tree is like the filesystem’s directory tree on your computer — a very apt comparison. Just like directories in a filesystem, you use modules to organize your code. And just like files in a directory, we need a way to find our modules: that is what paths are for (7.3).

Chapter 7 · 7.3 Paths for Referring to an Item in the Module Tree

Absolute and relative paths

To show Rust where to find an item in a module tree, we use a path in the same way we use a path when navigating a filesystem. To call a function, we need to know its path. A path can take two forms:

Definition 7.9 (Absolute path). The full path starting from a crate root. For code from an external crate, the absolute path begins with the crate name; for code from the current crate, it starts with the literal crate.

Definition 7.10 (Relative path). A path that starts from the current module and uses self, super, or an identifier in the current module.

Both absolute and relative paths are followed by one or more identifiers separated by double colons (::).

Returning to Listing 7.1: say we want to call the add_to_waitlist function. This is the same as asking: what’s the path of the add_to_waitlist function?

Chapter 7 · 7.3 Paths for Referring to an Item in the Module Tree

Absolute or relative: which to choose

First call: absolute

add_to_waitlist is in the same crate as eat_at_restaurant, so the path can start with the crate keyword, then include each successive module down to add_to_waitlist. Filesystem equivalent: /front_of_house/hosting/add_to_waitlist — starting with crate is like starting from the filesystem root / in your shell.

Second call: relative

The path starts with front_of_house, the name of the module defined at the same level of the module tree as eat_at_restaurant. Filesystem equivalent: front_of_house/hosting/add_to_waitlist. Starting with a module name means that the path is relative.

The choice depends on whether you’re more likely to move an item’s definition separately from or together with the code that uses it:

  • Move front_of_house and eat_at_restaurant together into a module customer_experience: the absolute path must be updated; the relative path stays valid.
  • Move only eat_at_restaurant into a module dining: the absolute path stays the same; the relative path must be updated.

The book generally prefers absolute paths: it’s more likely we’ll want to move definitions and item calls independently.

Chapter 7 · 7.3 Paths for Referring to an Item in the Module Tree

Everything is private by default

The errors say module hosting is private. We have the correct paths for the hosting module and the add_to_waitlist function, but Rust won’t let us use them because it doesn’t have access to the private sections.

Definition 7.11 (Privacy rule). In Rust, all items (functions, methods, structs, enums, modules, and constants) are private to parent modules by default. Items in a parent module can’t use the private items inside child modules, but items in child modules can use the items in their ancestor modules. To make an item like a function or struct private, put it in a module.

Why: child modules wrap and hide their implementation details, but they can see the context in which they’re defined. Rust made hiding inner implementation details the default, so you know which parts of the inner code you can change without breaking the outer code. The pub keyword is the option to expose inner parts of child modules to outer ancestor modules.

Example 7.12. Think of the privacy rules as the back office of a restaurant: what goes on in there is private to restaurant customers, but office managers can see and do everything in the restaurant they operate.

A public module doesn’t make its contents public

What happened? Adding the pub keyword in front of mod hosting makes the module public. With this change, if we can access front_of_house, we can access hosting.

But the contents of hosting are still private; making the module public doesn’t make its contents public. The pub keyword on a module only lets code in its ancestor modules refer to it, not access its inner code.

Because modules are containers, there’s not much we can do by only making the module public; we need to go further and choose to make one or more of the items within the module public as well.

Remark. The errors in Listing 7.6 say that the add_to_waitlist function is private. The privacy rules apply to structs, enums, functions, and methods as well as modules.

Why both paths now work

The absolute path

  1. It starts with crate, the root of our crate’s module tree.
  2. front_of_house is defined in the crate root. It isn’t public, but eat_at_restaurant is defined in the same module (they are siblings), so we can refer to it.
  3. hosting is marked pub, and we can access its parent module, so we can access hosting.
  4. add_to_waitlist is marked pub, and we can access its parent module, so this function call works!

The relative path

Same logic except the first step: the path starts from front_of_house, which is defined within the same module as eat_at_restaurant. Then, because hosting and add_to_waitlist are pub, the rest of the path works, and the call is valid!

Public APIs, and packages with a binary and a library

If you share your library crate so other projects can use your code, your public API is your contract with users of your crate: it determines how they can interact with your code. Managing changes to a public API so people can depend on your crate is beyond the scope of this book; see the Rust API Guidelines (rust-lang.github.io/api-guidelines).

Best practices for packages with a binary and a library

  • A package can contain both a src/main.rs binary crate root and a src/lib.rs library crate root; both crates have the package name by default.
  • Typically the binary crate has just enough code to start an executable that calls code defined in the library crate, so other projects benefit from the most functionality, because the library crate’s code can be shared.
  • Define the module tree in src/lib.rs. Public items can then be used in the binary crate by starting paths with the name of the package.
  • The binary crate becomes a user of the library crate just like a completely external crate: it can only use the public API. This helps you design a good API — you’re not only the author but also a client!

Remark. Chapter 12 demonstrates this organizational practice with a command line program containing both a binary crate and a library crate.

Starting relative paths with super

Definition 7.13 (super). A keyword at the start of a path that makes it a relative path beginning in the parent module, rather than the current module or the crate root — like starting a filesystem path with .. to go to the parent directory.

Listing 7.8: Calling a function using a relative path starting with super — src/lib.rs

fn deliver_order() {}

 

mod back_of_house {

    fn fix_incorrect_order() {

        cook_order();

        super::deliver_order();

    }

 

    fn cook_order() {}

}

Using super references an item we know is in the parent module, which makes rearranging the module tree easier when the module is closely related to the parent but the parent might be moved elsewhere someday.

A chef fixes an incorrect order and personally brings it out. From back_of_house, super goes to its parent — crate, the root — where deliver_order is found. Success!

back_of_house and deliver_order are likely to stay in the same relationship and get moved together, so super leaves fewer places to update if the code moves.

Importing items with the glob operator

Definition 7.17 (Glob operator). The * written after a path in a use statement; it brings all public items defined in that path into scope.

use std::collections::*;

This use statement brings all public items defined in std::collections into the current scope. Be careful when using the glob operator:

  • Glob can make it harder to tell what names are in scope and where a name used in your program was defined.
  • If the dependency changes its definitions, what you’ve imported changes as well — e.g. compiler errors when you upgrade a dependency that adds a definition with the same name as one of yours in the same scope.

Glob is often used when testing, to bring everything under test into the tests module (Chapter 11), and sometimes as part of the prelude pattern (see the standard library documentation).

Chapter 7 · Summary

Chapter summary

Rust lets you organize code and control what other code can see:

  • split a package into multiple crates, and a crate into modules, so that you can refer to items defined in one module from another module;
  • refer to items by specifying absolute paths (starting from crate or a crate name) or relative paths (starting from self, super, or an identifier in the current module);
  • bring paths into scope with a use statement, so you can use a shorter path for multiple uses of the item in that scope;
  • rely on module code being private by default, and make definitions public by adding the pub keyword.
