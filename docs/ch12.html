Chapter 12 · Introduction

Why a command line tool: our own grep

Rust’s speed, safety, single binary output, and cross-platform support make it an ideal language for creating command line tools. So for our project we’ll make our own version of the classic command line search tool grep.

Definition 12.1 (grep). Globally search a regular expression and print. In the simplest use case, grep takes a file path and a string as its arguments; it reads the file, finds the lines in that file that contain the string argument, and prints those lines.

Along the way, our tool will use the terminal features that many other command line tools use:

  • We’ll read the value of an environment variable to allow the user to configure the behavior of our tool.
  • We’ll print error messages to the standard error console stream (stderr) instead of standard output (stdout), so that, for example, the user can redirect successful output to a file while still seeing error messages onscreen.

Chapter 12 · 12.1 Accepting Command Line Arguments

Bringing std::env into scope, and invalid Unicode

First, we bring the std::env module into scope with a use statement so that we can use its args function. Notice that std::env::args is nested in two levels of modules.

  • As discussed in Chapter 7, when the desired function is nested in more than one module, we’ve chosen to bring the parent module into scope rather than the function.
  • By doing so, we can easily use other functions from std::env.
  • It’s also less ambiguous than adding use std::env::args and then calling the function with just args, because args might easily be mistaken for a function that’s defined in the current module.

The args function and invalid Unicode

Remark. std::env::args will panic if any argument contains invalid Unicode. If your program needs to accept arguments containing invalid Unicode, use std::env::args_os instead: it returns an iterator that produces OsString values instead of String values. The book uses std::env::args for simplicity, because OsString values differ per platform and are more complex to work with than String values.

It works — but with two flaws to fix early

After reading the file, we again added a temporary println! statement that prints the value of contents, so that we can check that the program is working so far. Great! The code read and then printed the contents of the file.

But the code has a few flaws:

  1. The main function has multiple responsibilities. Generally, functions are clearer and easier to maintain if each function is responsible for only one idea.
  2. We’re not handling errors as well as we could.

The program is still small, so these flaws aren’t a big problem, but as the program grows it will be harder to fix them cleanly.

Remark. It’s good practice to begin refactoring early on when developing a program, because it’s much easier to refactor smaller amounts of code. We do that next.

Chapter 12 · 12.3 Refactoring to Improve Modularity and Error Handling

Four problems to fix (1–2): structure

To improve our program, we fix four problems that have to do with the program’s structure and how it handles potential errors.

1. main performs two tasks

Our main function now parses arguments and reads files. As the program grows, the number of separate tasks main handles will increase. As a function gains responsibilities, it becomes more difficult to reason about, harder to test, and harder to change without breaking one of its parts. It’s best to separate functionality so that each function is responsible for one task.

2. Configuration and logic variables are mixed

query and file_path are configuration variables, while variables like contents are used to perform the program’s logic. The longer main becomes, the more variables we bring into scope, and the harder it is to keep track of the purpose of each. It’s best to group the configuration variables into one structure to make their purpose clear.

Four problems to fix (3–4): error handling

3. One unhelpful message for every read failure

We use expect to print an error message when reading the file fails, but it just prints Should have been able to read the file. Reading a file can fail in a number of ways — the file could be missing, or we might not have permission to open it. Regardless of the situation we’d print the same message, which wouldn’t give the user any information!

4. Error handling is scattered and unclear

If the user runs our program without specifying enough arguments, they get an index out of bounds error from Rust that doesn’t clearly explain the problem. It would be best if all the error-handling code were in one place, so future maintainers had only one place to consult if the error-handling logic needed to change. That also ensures we print messages that are meaningful to our end users.

We address these four problems by refactoring our project.

Chapter 12 · 12.3 Refactoring to Improve Modularity and Error Handling

Separating concerns in binary projects

Allocating responsibility for multiple tasks to main is a problem common to many binary projects. So many Rust programmers split up the separate concerns of a binary program when main starts getting large.

The process

  • Split your program into a main.rs file and a lib.rs file, and move your program’s logic to lib.rs.
  • As long as your command line parsing logic is small, it can remain in main.
  • When the parsing logic starts getting complicated, extract it from main into other functions or types.

What stays in main

  • Calling the command line parsing logic with the argument values
  • Setting up any other configuration
  • Calling a run function in lib.rs
  • Handling the error if run returns an error

Why split main.rs and lib.rs

This pattern is about separating concerns:

main.rs handles running the program.

lib.rs handles all the logic of the task at hand.

  • You can’t test the main function directly; this structure lets you test all of your program’s logic by moving it out of main.
  • The code that remains in main will be small enough to verify its correctness by reading it.

We can take another small step to improve parse_config. Two signs show we don’t have the right abstraction yet:

Returning a Config struct: the struct and parse_config

Listing 12.6 (continued) — src/main.rs

struct Config {

    query: String,

    file_path: String,

fn parse_config(args: &[String]) -> Config {

    let query = args[1].clone();

    let file_path = args[2].clone();

 

    Config { query, file_path }

}

We added a struct named Config with fields query and file_path; parse_config now returns a Config value.

Config now contains owned String values instead of slices referencing args. The args variable in main owns the argument values and only lets parse_config borrow them, so we’d violate Rust’s borrowing rules if Config tried to take ownership of them.

Managing the String data with clone

There are a number of ways we could manage the String data. The easiest, though somewhat inefficient, route is to call the clone method on the values:

  • It makes a full copy of the data for the Config instance to own, which takes more time and memory than storing a reference to the string data.
  • But cloning also makes our code very straightforward, because we don’t have to manage the lifetimes of the references.
  • In this circumstance, giving up a little performance to gain simplicity is a worthwhile trade-off.

The trade-offs of using clone

Remark. Many Rustaceans tend to avoid using clone to fix ownership problems because of its runtime cost; Chapter 13 shows more efficient methods for this type of situation. For now it’s okay to copy a few strings to keep making progress, because you make these copies only once and your file path and query string are very small. It’s better to have a working program that’s a bit inefficient than to try to hyperoptimize code on your first pass. As you become more experienced with Rust it gets easier to start with the most efficient solution, but for now it’s perfectly acceptable to call clone.

Returning a Result instead of calling panic!

We can instead return a Result value that contains a Config instance in the successful case and describes the problem in the error case.

  • We also change the function name from new to build, because many programmers expect new functions to never fail.
  • When Config::build is communicating to main, we can use the Result type to signal there was a problem.
  • Then we can change main to convert an Err variant into a more practical error for our users, without the surrounding text about thread 'main' and RUST_BACKTRACE that a call to panic! causes.

impl Config {

    fn build(args: &[String]) -> Result<Config, &'static str> {

        if args.len() < 3 {

        }

        let file_path = args[2].clone();

 

        Ok(Config { query, file_path })

    }

}

  • In the body, we return an Err instead of calling panic!, and wrap the Config return value in an Ok.

Definition 12.6 (Test-driven development, TDD). A process that repeats these steps:

Why search needs the lifetime 'a

pub fn search<'a>(query: &str, contents: &'a str) -> Vec<&'a str>

We define an explicit lifetime 'a in the signature of search and use it with the contents argument and the return value. Recall from Chapter 10 that lifetime parameters specify which argument lifetime is connected to the lifetime of the return value.

  • Here, the returned vector should contain string slices that reference slices of the argument contents (rather than the argument query).

Remark. This is important! The data referenced by a slice needs to be valid for the reference to be valid; if the compiler assumed we were making string slices of query rather than contents, it would do its safety checking incorrectly.

How the lowercase comparison works

search_case_insensitive is almost the same as search; the only difference is that we lowercase the query and each line.

  1. We lowercase the query string and store it in a new variable with the same name, shadowing the original. Whether the user’s query is "rust", "RUST", "Rust", or "rUsT", we treat it as if it were "rust" and are insensitive to the case.
  2. query is now a String rather than a string slice, because to_lowercase creates new data rather than referencing existing data: the slice "rUsT" doesn’t contain a lowercase u or t for us to use, so we must allocate a new String containing "rust". Passing query to contains now needs an ampersand, because contains is defined to take a string slice.
  3. We call to_lowercase on each line to lowercase all characters. With both line and query lowercased, we find matches no matter what the case of the query is.

Remark. While to_lowercase handles basic Unicode, it won’t be 100 percent accurate. A real application would need a bit more work here, but this section is about environment variables, not Unicode.

Standard output and standard error

At the moment, we’re writing all of our output to the terminal using the println! macro. In most terminals, there are two kinds of output:

Definition 12.9 (Standard output and standard error). Two output streams of a terminal program: standard output (stdout) for general information, and standard error (stderr) for error messages.

Remark. The println! macro is only capable of printing to standard output, so we have to use something else to print to standard error.

fn main() {

    }
