Chapter 17 · Introduction

Doing other work while we wait

Many operations we ask the computer to do can take a while to finish. It would be nice to do something else while we’re waiting for those long-running processes to complete. Modern computers offer two techniques for working on more than one operation at a time: parallelism and concurrency.

Our programs’ logic, however, is written in a mostly linear fashion. We’d like to specify the operations a program should perform and the points at which a function could pause and some other part of the program could run instead — without specifying up front exactly the order and manner in which each bit of code should run.

Definition 17.1 (Asynchronous programming). An abstraction that lets us express our code in terms of potential pausing points and eventual results, and that takes care of the details of coordination for us.

This chapter builds on Chapter 16’s use of threads for parallelism and concurrency by introducing an alternative approach: Rust’s futures, streams, and the async and await syntax that let us express how operations could be asynchronous, and the third-party crates that implement asynchronous runtimes — code that manages and coordinates the execution of asynchronous operations.

Chapter 17 · Introduction

Two long-running operations

Exporting a video

Say you’re exporting a video you’ve created of a family celebration, an operation that could take anywhere from minutes to hours. The export will use as much CPU and GPU power as it can. If you had only one CPU core and your operating system didn’t pause that export until it completed — that is, if it executed the export synchronously — you couldn’t do anything else on your computer while it ran. Fortunately, the operating system can, and does, invisibly interrupt the export often enough to let you get other work done simultaneously.

Downloading a video

Now say you’re downloading a video shared by someone else. This can also take a while but does not take up as much CPU time: the CPU has to wait for data to arrive from the network. You can start reading the data once it starts to arrive, but it might take some time for all of it to show up — and even then, loading a large video could take a second or two. That is a very long time for a modern processor, which can perform billions of operations every second. Again, the OS invisibly interrupts your program so the CPU can do other work while the network call finishes.

Chapter 17 · Introduction

CPU-bound and I/O-bound operations

Definition 17.2 (CPU-bound or compute-bound operation). An operation limited by the computer’s potential data processing speed within the CPU or GPU, and by how much of that speed it can dedicate to the operation. The video export is one.

Definition 17.3 (I/O-bound operation). An operation limited by the speed of the computer’s input and output: it can only go as fast as the data can be sent across the network. The video download is one.

In both examples, the operating system’s invisible interrupts provide a form of concurrency. That concurrency happens only at the level of the entire program, though: the operating system interrupts one program to let other programs get work done.

In many cases, because we understand our programs at a much more granular level than the operating system does, we can spot opportunities for concurrency that the operating system can’t see.

Chapter 17 · Introduction

Blocking calls

If we’re building a tool to manage file downloads, we should be able to write our program so that starting one download won’t lock up the UI, and users should be able to start multiple downloads at the same time. Many operating system APIs for interacting with the network are blocking, though.

Definition 17.4 (Blocking). A blocking call blocks the program’s progress until the data it’s processing is completely ready.

Remark. This is how most function calls work, if you think about it. However, the term blocking is usually reserved for function calls that interact with files, the network, or other resources on the computer, because those are the cases where an individual program would benefit from the operation being non-blocking.

We could avoid blocking our main thread by spawning a dedicated thread to download each file. However, the overhead of the system resources used by those threads would eventually become a problem. It would be preferable if the call didn’t block in the first place: instead, we could define a number of tasks we’d like our program to complete and allow the runtime to choose the best order and manner in which to run them.

Chapter 17 · Parallelism and Concurrency

Concurrency: one person, several tasks

So far we’ve treated parallelism and concurrency as mostly interchangeable; now we need to distinguish them precisely, because the differences will show up as we work. Consider how a team could split up work on a software project: assign a single member multiple tasks, assign each member one task, or use a mix of the two.

Definition 17.5 (Concurrency). An individual works on several different tasks before any of them is complete.

One way to implement concurrency is like having two different projects checked out on your computer: when you get bored or stuck on one, you switch to the other. You’re just one person, so you can’t make progress on both at the exact same time, but you can multitask, making progress on one at a time by switching between them.

Chapter 17 · Parallelism and Concurrency

Where they intersect, in teams and in hardware

Parallelism and concurrency can intersect with each other, too. If you learn that a colleague is stuck until you finish one of your tasks, you’ll probably focus all your efforts on that task to “unblock” your colleague. You and your coworker are no longer able to work in parallel, and you’re also no longer able to work concurrently on your own tasks.

The same basic dynamics come into play with software and hardware:

  • On a machine with a single CPU core, the CPU can perform only one operation at a time, but it can still work concurrently. Using tools such as threads, processes, and async, the computer can pause one activity and switch to others before eventually cycling back to the first.
  • On a machine with multiple CPU cores, it can also do work in parallel. One core can perform one task while another core performs a completely unrelated one, and those operations actually happen at the same time.

Running async code in Rust usually happens concurrently. Depending on the hardware, the operating system, and the async runtime we are using (more on runtimes shortly), that concurrency may also use parallelism under the hood.

Chapter 17 · 17.1 Futures and the Async Syntax

Futures, async and await

The key elements of asynchronous programming in Rust are futures and Rust’s async and await keywords.

Definition 17.8 (Future). A value that may not be ready now but will become ready at some point in the future. (Other languages have the same concept, sometimes called a task or a promise.) In Rust, futures are types that implement the Future trait.

Rust provides the Future trait as a building block so that different async operations can be implemented with different data structures but with a common interface. Each future holds its own information about the progress that has been made and what “ready” means.

You can apply the async keyword to blocks and functions to specify that they can be interrupted and resumed. Within an async block or async function, you can use the await keyword to await a future (that is, wait for it to become ready). Any point where you await a future within an async block or function is a potential spot for that block or function to pause and resume.

Definition 17.9 (Polling). The process of checking with a future to see if its value is available yet.

Defining the page_title function

The goal: a little command line web scraper that fetches two web pages concurrently, pulls the <title> element from each, and prints the title of whichever page finishes that whole process first.

We start with a function that takes one page URL, makes a request to it, and returns the text of the <title> element.

    let response = trpl::get(url).await;

    let response_text = response.text().await;

    Html::parse(&response_text)

        .select_first("title")

        .map(|title| title.inner_html())

}

Chapter 17 · 17.1 Futures and the Async Syntax

Awaiting get and text: futures are lazy

We mark page_title with the async keyword. We use trpl::get to fetch whatever URL is passed in and add await to await the response. To get the text of the response, we call its text method and once again await it. Both steps are asynchronous:

  • for get, we wait for the server to send back the first part of its response, which includes HTTP headers, cookies, and so on and can be delivered separately from the response body;
  • especially if the body is very large, it can take some time for it all to arrive; because we have to wait for the entirety of the response, text is also async.

We have to explicitly await both futures, because futures in Rust are lazy: they don’t do anything until you ask them to with await. (Rust even shows a compiler warning if you don’t use a future.) This mirrors iterators (Chapter 13), which do nothing unless you call their next method — directly, or via for loops or methods such as map that use next under the hood. This laziness allows Rust to avoid running async code until it’s actually needed.

await is a postfix keyword

Rust’s await keyword goes after the expression you’re awaiting, not before it: it’s a postfix keyword. This may differ from what you’re used to in other languages, but in Rust it makes chains of methods much nicer to work with. We can chain the trpl::get and text calls with await between them:

Chapter 17 · 17.1 Futures and the Async Syntax

What an async fn compiles to

Rust compiles an async block into a unique, anonymous data type that implements the Future trait. It compiles an async function into a non-async function whose body is an async block; the function’s return type is the type of that anonymous data type.

So writing async fn is equivalent to writing a function that returns a future of the return type. To the compiler, async fn page_title in Listing 17.1 is roughly equivalent to:

use std::future::Future;

use trpl::Html;

 

fn page_title(url: &str) -> impl Future<Output = Option<String>> {

    async move {

        let text = trpl::get(url).await.text().await;

        Html::parse(&text)

            .select_first("title")

            .map(|title| title.inner_html())

    }

}

Chapter 17 · 17.1 Futures and the Async Syntax

Async code needs a runtime

The reason main can’t be marked async is that async code needs a runtime.

Definition 17.10 (Runtime). A Rust crate that manages the details of executing asynchronous code.

A program’s main function can initialize a runtime, but it’s not a runtime itself (we’ll see why in a bit). Every Rust program that executes async code has at least one place where it sets up a runtime that executes the futures.

Most languages that support async bundle a runtime, but Rust does not. Instead, there are many different async runtimes available, each of which makes different tradeoffs suitable to the use case it targets. For example, a high-throughput web server with many CPU cores and a large amount of RAM has very different needs than a microcontroller with a single core, a small amount of RAM, and no heap allocation ability.

The crates that provide those runtimes also often supply async versions of common functionality such as file or network I/O.

Running a future with trpl::block_on

Here, and throughout the rest of this chapter, we use the block_on function from the trpl crate:

  • It takes a future as an argument and blocks the current thread until this future runs to completion.
  • Behind the scenes, calling block_on sets up a runtime using the tokio crate, which is used to run the future passed in. (trpl’s block_on behaves similarly to other runtime crates’ block_on functions.)
  • Once the future completes, block_on returns whatever value the future produced.

We could pass the future returned by page_title directly to block_on and, once it completed, match on the resulting Option<String> as we tried to do in Listing 17.3. Await points and the hidden state machine

Phew — we finally have some working async code! Before we race two sites against each other, let’s turn back briefly to how futures work.

Definition 17.11 (Await point). Any place where the code uses the await keyword. Each await point represents a place where control is handed back to the runtime.

To make that work, Rust needs to keep track of the state involved in the async block, so that the runtime could kick off some other work and then come back when it’s ready to try advancing the first one again. This is an invisible state machine, as if you’d written an enum like this to save the current state at each await point:

Who runs the state machine: runtimes and executors

Writing the state transitions by hand would be tedious and error-prone, especially as you add more functionality and states later. Fortunately, the compiler creates and manages the state machine data structures for async code automatically. The normal borrowing and ownership rules still apply, and the compiler checks them and gives useful error messages.

Ultimately, something has to execute this state machine, and that something is a runtime.

Definition 17.12 (Executor). The part of a runtime responsible for executing the async code.

This is why main can’t be async (Listing 17.3): something else would need to manage the state machine for whatever future main returned, but main is the starting point of the program! Instead, we call trpl::block_on in main to set up a runtime and run the future returned by the async block until it’s done.

Remark. Some runtimes provide macros so you can write an async main. Those macros rewrite async fn main() { ... } to be a normal fn main, which does what we did by hand in Listing 17.4: call a function that runs a future to completion the way trpl::block_on does.

trpl::select and the Either type

We call page_title for each user-supplied URL and save the resulting futures as title_fut_1 and title_fut_2. These don’t do anything yet: futures are lazy and we haven’t awaited them. Then we pass the futures to trpl::select, which returns a value to indicate which of the futures passed to it finishes first.

Remark. Under the hood, trpl::select is built on a more general select function defined in the futures crate. That function can do a lot of things trpl::select can’t, but it also has additional complexity we can skip over for now.

Either future can legitimately “win,” so it doesn’t make sense to return a Result. Instead, trpl::select returns trpl::Either. Like Result it has two cases, but there is no notion of success or failure baked in; it uses Left and Right to indicate “one or the other”:

enum Either<A, B> {

    Left(A),

    Right(B),

}

The select function returns Left with that future’s output if the first argument wins, and Right with the second future argument’s output if that one wins. This matches the order the arguments appear in the call: the first argument is to the left of the second argument.

How the async channel differs from the thread one

trpl::channel is an async version of the multiple-producer, single-consumer channel API used with threads in Chapter 16. It is only a little different:

  • it uses a mutable rather than an immutable receiver rx, and its recv method produces a future we need to await rather than producing the value directly;
  • we don’t have to spawn a separate thread or even a task; we merely need to await the rx.recv call.

The synchronous Receiver::recv in std::mpsc::channel blocks until it receives a message. trpl::Receiver::recv does not, because it is async: it hands control back to the runtime until either a message is received or the send side of the channel closes. By contrast, we don’t await the send call, because it doesn’t block — it doesn’t need to, since the channel we’re sending into is unbounded.

Remark. Because all of this async code runs in an async block in a trpl::block_on call, everything within it can avoid blocking. Receiving an unknown number of messages: while let

In Listing 16-10 we used a for loop to process all the items received from a synchronous channel. Rust doesn’t yet have a way to use a for loop with an asynchronously produced series of items, so we use the while let conditional loop — the loop version of the if let construct from Chapter 6. The loop continues executing as long as the pattern it specifies continues to match the value.

The rx.recv call produces a future, which we await. The runtime pauses the future until it is ready. Once a message arrives, the future resolves to Some(message), as many times as a message arrives. When the channel closes, regardless of whether any messages have arrived, the future instead resolves to None: there are no more values, so we should stop polling — that is, stop awaiting.

The while let loop pulls this together. If rx.recv().await gives Some(message), we can use the message in the loop body, just as with if let. If the result is None, the loop ends. Every time the loop completes, it hits the await point again, so the runtime pauses it again until another message arrives.

Why the program still never exits

The program never exits because of the way the while let loop interacts with trpl::join:

  1. The future returned from trpl::join completes only once both futures passed to it have completed.
  2. The tx_fut future completes once it finishes sleeping after sending the last message in vals.
  3. The rx_fut future won’t complete until the while let loop ends.
  4. The while let loop won’t end until awaiting rx.recv produces None.
  5. Awaiting rx.recv will return None only once the other end of the channel is closed.
  6. The channel will close only if we call rx.close or when the sender side, tx, is dropped.
  7. We don’t call rx.close anywhere, and tx won’t be dropped until the outermost async block passed to trpl::block_on ends.
  8. The block can’t end because it is blocked on trpl::join completing, which takes us back to the top of this list.

Yielding control to the runtime

At each await point, Rust gives a runtime a chance to pause the task and switch to another one if the future being awaited isn’t ready. The inverse is also true: Rust only pauses async blocks and hands control back to a runtime at an await point. Everything between await points is synchronous.

So if you do a bunch of work in an async block without an await point, that future will block any other futures from making progress.

Definition 17.14 (Starvation). A future starves other futures when it does work without reaching an await point, keeping them from making progress.

In some cases, that may not be a big deal. However, if you are doing some kind of expensive setup or long-running work, or if you have a future that will keep doing some particular task indefinitely, you’ll need to think about when and where to hand control back to the runtime.

Cooperative multitasking

Async can be useful even for compute-bound tasks, depending on what else your program is doing, because it provides a useful tool for structuring the relationships between different parts of the program — at the cost of the overhead of the async state machine.

The runtime polls futures and puts them to sleep

Instead of a blocking loop, Rust ensures that the loop can hand off control to something that can pause work on this future to work on other futures and then check this one again later.   • the runtime knows the future is ready, and advances it, when poll returns Poll::Ready(Some(message)) or Poll::Ready(None).

The exact details of how a runtime does that are beyond the scope of this book, but the key is the basic mechanics of futures: a runtime polls each future it is responsible for, putting the future back to sleep when it is not yet ready.

A type annotation on self, and the Pin wrapper

A type annotation for self works like type annotations for other function parameters, with two key differences:

  • it tells Rust what type self must be for the method to be called;
  • it can’t be just any type: it’s restricted to the type on which the method is implemented, a reference or smart pointer to that type, or a Pin wrapping a reference to that type.

More on this syntax in Chapter 18. For now: to poll a future to check whether it is Pending or Ready(Output), we need a Pin-wrapped mutable reference to the type.

Definition 17.19 (Pin). A wrapper for pointer-like types such as &, &mut, Box, and Rc. (Technically, Pin works with types that implement Deref or DerefMut, which is effectively equivalent to working only with references and smart pointers.)

Pin is not a pointer itself and doesn’t have any behavior of its own, like Rc and Arc do with reference counting; it’s purely a tool the compiler can use to enforce constraints on pointer usage.

Why poll needs a pinned self

Recalling that await is implemented in terms of calls to poll starts to explain the error message we saw earlier — but that was in terms of Unpin, not Pin. So how exactly does Pin relate to Unpin, and why does Future need self to be in a Pin type to call poll?

A series of await points in a future gets compiled into a state machine, and the compiler makes sure that state machine follows all of Rust’s normal rules around safety, including borrowing and ownership. To make that work, Rust looks at what data is needed between one await point and either the next await point or the end of the async block. It then creates a corresponding variant in the compiled state machine. Each variant gets the access it needs to the data used in that section of the source code, whether by taking ownership of that data or by getting a mutable or immutable reference to it.

So far, so good: if we get anything wrong about the ownership or references in a given async block, the borrow checker will tell us. When we want to move around the future that corresponds to that block — like moving it into a Vec to pass to join_all — things get trickier.

Moving a self-referential value is unsafe

By default, any object that has a reference to itself is unsafe to move, because references always point to the actual memory address of whatever they refer to. If you move the data structure itself, those internal references are left pointing to the old location — which is now invalid. For one thing, its value will not be updated when you change the data structure. For another, more important, thing, the computer is now free to reuse that memory for other purposes! Pinning: making sure the data doesn’t move

Theoretically, the compiler could try to update every reference to an object whenever it gets moved, but that could add a lot of performance overhead, especially if a whole web of references needs updating. If we could instead make sure the data structure doesn’t move in memory, we wouldn’t have to update any references. This is exactly what the borrow checker is for: in safe code, it prevents you from moving any item with an active reference to it.

Pin builds on that to give us the exact guarantee we need. When we pin a value by wrapping a pointer to that value in Pin, it can no longer move. Thus, with Pin<Box<SomeType>>, you actually pin the SomeType value, not the Box pointer.

Most types are safe to move: Unpin

However, most types are perfectly safe to move around, even if they happen to be behind a Pin pointer. We only need to think about pinning when items have internal references. Primitive values such as numbers and Booleans obviously don’t have any internal references; neither do most types you normally work with in Rust. You can move around a Vec, for example, without worrying.

Yet with a Pin<Vec<String>>, you’d have to do everything via the safe but restrictive APIs provided by Pin, even though a Vec<String> is always safe to move if there are no other references to it. We need a way to tell the compiler that it’s fine to move items around in cases like this — and that’s where Unpin comes into play.

Definition 17.21 (Unpin). A marker trait informing the compiler that a given type does not need to uphold any guarantees about whether the value in question can be safely moved.

Like Send and Sync from Chapter 16, Unpin has no functionality of its own. Marker traits exist only to tell the compiler it’s safe to use the type implementing a given trait in a particular context.

Unpin is the normal case; !Unpin the special one

Just as with Send and Sync, the compiler implements Unpin automatically for all types where it can prove it is safe. The special case is where Unpin is not implemented for a type, written impl !Unpin for SomeType, where SomeType is a type that does need to uphold those guarantees to be safe whenever a pointer to it is used in a Pin.

Two things to keep in mind about Pin and Unpin: first, Unpin is the “normal” case, and !Unpin is the special case. Second, whether a type implements Unpin or !Unpin only matters when you’re using a pinned pointer to that type, like Pin<&mut SomeType>.

Concretely, a String has a length and the Unicode characters that make it up. We can wrap a String in Pin, but String automatically implements Unpin, as do most other types in Rust.

The Stream trait: Iterator meets Future

Streams are similar to asynchronous iterators. Unlike Iterator and Future, however, Stream has no definition in the standard library as of this writing, but there is a very common definition from the futures crate used throughout the ecosystem.

From Iterator, we have the idea of a sequence: its next method provides an Option<Self::Item>. From Future, we have the idea of readiness over time: its poll method provides a Poll<Self::Output>. To represent a sequence of items that become ready over time, a Stream trait puts those features together.

use std::pin::Pin;

use std::task::{Context, Poll};

 

trait Stream {

    type Item;

 

    fn poll_next(

        self: Pin<&mut Self>,

        cx: &mut Context<'_>

    ) -> Poll<Option<Self::Item>>;

}

Item and poll_next

The associated type Item is the type of the items produced: zero to many, as with Iterator, unlike Future’s always-single Output (even if it’s the unit type ()).

The method is called poll_next to make clear that it polls in the same way Future::poll does and produces a sequence of items in the same way Iterator::next does. Its return type combines Poll with Option: the outer type is Poll, because it has to be checked for readiness, just as a future does; the inner type is Option, because it needs to signal whether there are more messages, just as an iterator does.

Something very similar to Stream will likely end up in Rust’s standard library. Meanwhile, it’s part of the toolkit of most runtimes, so you can rely on it.

The real next, and why the traits are separate

Remark. The actual definition we used earlier in the chapter looks slightly different, because it supports versions of Rust that did not yet support async functions in traits:

fn next(&mut self) -> Next<'_, Self> where Self: Unpin;

That Next type is a struct that implements Future and lets us name the lifetime of the reference to self with Next<'_, Self>, so that await can work with this method.

StreamExt is also the home of all the interesting methods available to use with streams. It is automatically implemented for every type that implements Stream, but the traits are defined separately so the community can iterate on convenience APIs without affecting the foundational trait.

In the trpl version of StreamExt, the trait not only defines next but also supplies a default implementation that correctly handles the details of calling Stream::poll_next. So even when you write your own streaming data type, you only have to implement Stream; anyone who uses your type can use StreamExt and its methods with it automatically.

Threads or async? Often both

Chapter 16 showed threads as one approach to concurrency; this chapter showed another, async with futures and streams. When to choose one over the other? It depends! And in many cases, the choice isn’t threads or async but rather threads and async.

Many operating systems have supplied threading-based concurrency models for decades, and many programming languages support them as a result. But they have tradeoffs: on many operating systems, they use a fair bit of memory for each thread. Threads are also only an option when your OS and hardware support them. Unlike mainstream desktop and mobile computers, some embedded systems don’t have an OS at all, so they also don’t have threads.

The async model provides a different — and ultimately complementary — set of tradeoffs. In the async model, concurrent operations don’t require their own threads. Instead, they can run on tasks, as when we used trpl::spawn_task to kick off work from a synchronous function.

Definition 17.22 (Task). A unit of concurrent work similar to a thread, but managed by library-level code — the runtime — instead of by the operating system.

Threads are somewhat “fire and forget”: they have no native equivalent to a future, so they simply run to completion without being interrupted except by the operating system itself.

Work stealing, and rules of thumb

Threads and tasks often work very well together, because tasks can (at least in some runtimes) be moved around between threads. In fact, under the hood, the runtime we’ve been using — including the spawn_blocking and spawn_task functions — is multithreaded by default!

Definition 17.23 (Work stealing). An approach many runtimes use to transparently move tasks around between threads, based on how the threads are currently being utilized, to improve the system’s overall performance. It requires threads and tasks, and therefore futures.

When thinking about which method to use when, consider these rules of thumb:

  • If the work is very parallelizable (that is, CPU-bound), such as processing a bunch of data where each part can be processed separately, threads are a better choice.
  • If the work is very concurrent (that is, I/O-bound), such as handling messages from a bunch of different sources that may come in at different intervals or different rates, async is a better choice.

Combining a thread with async

If you need both parallelism and concurrency, you don’t have to choose between threads and async: use them together freely, letting each play the part it’s best at. Listing 17.25 shows a fairly common example of this kind of mix in real-world Rust code.

Listing 17.25: Sending messages with blocking code in a thread and awaiting the messages in an async block — src/main.rs

use std::{thread, time::Duration};

 

fn main() {

    let (tx, mut rx) = trpl::channel();

 

    thread::spawn(move || {

        for i in 1..11 {

            tx.send(i).unwrap();

            thread::sleep(Duration::from_secs(1));

        }

    });

 

    trpl::block_on(async {

        while let Some(message) = rx.recv().await {

            println!("{message}");

        }

    });

}
